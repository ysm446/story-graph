# MCP — 外部の LLM が制作チャットと同じ操作をする

作成日時: 2026-11-25 00:02
更新日時: 2026-11-25 00:04

**状態: 設計のみ、未実装。** 2026-11-24〜25 のユーザーとの相談をまとめたもの。
実装するときは、取り込み JSON([import-json.md](import-json.md))を削除してこれに置き換える(§10)。
決まっていない点は §12。

## 1. 目的

外部の LLM(Claude Code、Claude Desktop、Codex など)から、アプリの中の物語を直接読み書きできるようにする。

- **きっかけ**(ユーザー): 取り込み JSON は「1 つの話をまとめて入れて、それきり」になる。
  0 から相談しながら進めたり、既存の話を編集したりしたい。いま制作チャットでやっていることを、外部の LLM でできるとよい
- **できること**: 制作チャットと同じ範囲(シーンの作成・編集・削除・並べ替え・分岐、キャラクター・場所・設定資料、章)に、
  イベントと章のまとめの書き込みを足す
- **ローカル LLM は使わない**(ユーザー): 外部の LLM を使うときは llama-server を落としておける。
  イベントと章のまとめの更新も、外部の LLM に任せる
- **アプリ内の制作チャットは残す**: ローカル LLM だけで完結する経路はそのまま

## 2. 方針

**制作チャットのツールを、MCP のツールとしてそのまま出す。** 会話と文脈は外部のクライアントが持ち、
アプリは「道具」と「結果を映す画面」になる。

これができるのは、制作チャットのツールがローカル LLM のループから既に切り離されているため。

| 役割 | いまの場所 |
|---|---|
| 読み取り | `chat_agent.dispatch_tool`(本文・状態・記憶の検索・設定資料)、`production_library.read`、`production_chapters.read` |
| 書き込み | `production_agent.apply_edit`(シーン)。資料庫と章は `production_library.apply` / `production_chapters.apply` へ振り分ける |
| 守り | 保護・変更範囲(`production_policy`)、重複シーンの拒否、大半を失う全文置換の拒否(`production_guard`)、競合の検出(`NodeVersions`) |

採らなかった案:

| 案 | 理由 |
|---|---|
| 取り込み JSON を広げる(既存の作品への追加、分岐) | 書く → 検査 → 取り込む、の往復が残り、相談しながら少しずつ直す使い方に合わない。LLM が現状を読めない |
| 外部の LLM に HTTP の API を直接叩かせる | 画面用の API は内部の形(type / payload、座標、派生の印)がそのまま出ていて、説明と守りを別に書くことになる。ツールの形なら制作チャットで磨いた説明と検査を使い回せる |
| DB(SQLite)へ直接書く | 検索用の索引・埋め込み・変更履歴・dirty の伝播が抜ける([import-json.md](import-json.md) §2 と同じ理由) |
| 制作チャットの LLM の接続先を外部の API に替える | アプリが API キーと課金を持つことになる。ハーネスは ctx 8192 のローカル LLM 向けに組んであり、外部の LLM には要らない制御が多い。クライアント側の会話・文脈管理をそのまま使うほうが軽い |

### 載せないもの

ローカル LLM のための制御は、MCP には持ち込まない。外部のクライアントが自分で持っているため。

- ツールの出し分け(`use_tools`)と `TOOL_GROUPS` — ツール定義の量を気にしなくてよい
- プロンプトの予算、読み取り結果の切り詰め(`fit_recent_results`)
- 停滞の監視・同じ読み取りの繰り返しの検出(`production_guard.RunMonitor`)
- 作業メモ(`update_work_memory`)、計画(`production_plan`)、途中指示、手動編集への切替
- 相談 / 実行の送信モード — 書いてよいかどうかは、外部のクライアントの承認の仕組みが受け持つ

## 3. 全体の形

```
外部のクライアント(Claude Code など)
        │ stdio(MCP)
┌───────▼──────────────┐
│ backend/mcp_bridge.py │  クライアントが起動する小さな橋。中身を持たない
└───────┬──────────────┘
        │ HTTP(127.0.0.1、起動中の sidecar を探して繋ぐ)
┌───────▼── FastAPI sidecar ─────────────────────────┐
│ GET  /external/tools   ツールの定義                 │
│ POST /external/call    ツールの実行                 │
│ backend/external_tools.py  振り分けと、外部向けの追加 │
│        │                                            │
│        ├─ 読み取り: chat_agent / production_library  │
│        ├─ 書き込み: production_agent.apply_edit      │
│        └─ イベント・まとめ: store.replace_events /   │
│                             store.save_group_digest │
└───────┬────────────────────────────────────────────┘
        │ 変更の通し番号(§9)
┌───────▼── renderer ───┐
│ 番号が変わったら読み直す │
└───────────────────────┘
```

ツールの中身はすべて sidecar 側に置く。橋は「定義を取ってきて並べる」「呼び出しを転送する」だけ。

## 4. 接続の方式

**stdio の橋を挟む。** sidecar に MCP の口(HTTP)を直接付ける案は採らない。

| 方式 | 採否 | 理由 |
|---|---|---|
| stdio の橋 + sidecar の普通の HTTP | **採用** | 下の 4 点 |
| sidecar に MCP(HTTP)を直接マウント | 不採用 | ポートが変わると繋がらない。stdio しか使えないクライアントがある |

採用の理由:

1. **ポートが固定でない。** sidecar は 8765 から 20 ポートぶんの空きを探して起動する(`src/main/index.ts`)。
   クライアントの設定に URL を書く方式だと、ずれた日に繋がらない。橋なら、Electron と同じ手順で
   health を叩いて起動中の sidecar を見つけられる
2. **どのクライアントでも使える。** stdio はほぼすべての MCP クライアントが対応している
3. **sidecar 側が普通のハンドラで済む。** `async def` のハンドラ 2 本なので、直列実行の約束([overview.md](overview.md) §5)が
   そのまま守られ、MCP のライブラリ無しで pytest から検査できる
4. **アプリが起動していないときの案内を出せる。** 橋が「story-graph を起動してください」と返す

- 橋は公式の Python SDK(`mcp`)で書き、`.venv` の Python で動かす。依存に `mcp` を足す
- クライアントへの登録は、`.venv/Scripts/python.exe backend/mcp_bridge.py` を起動コマンドとして書く。
  設定画面に、登録用のコマンド(コピーできる形)を出す
- sidecar は 127.0.0.1 だけで待ち受けているので、口を足しても外からは届かない(いまの API と同じ)

## 5. ツール

名前と引数は制作チャットのものを変えない(説明文と検査が実モデルで磨いてあるため)。**太字**が今回足すもの。

| 種類 | ツール |
|---|---|
| 読む(物語) | `get_beats` / `get_state` / `search_memories` / **`get_events`**(シーンのイベント) |
| 読む(資料・章) | `read_library` / `search_setting_documents` / `read_setting_document` / 章の一覧 |
| シーン | `insert_scene` / `branch_scene` / `update_scene` / `patch_scene` / `delete_scene` / `reconnect_scene` |
| 資料庫 | `create_` / `update_` / `delete_` × `character` / `place`、`create_setting_document` / `update_setting_document` |
| 章 | `create_chapter` / `rename_chapter` / `add_scenes_to_chapter` / `remove_scenes_from_chapter` / `delete_chapter` |
| イベント | **`set_scene_events`**(シーンのイベントを置き換える) |
| 章のまとめ | **`set_chapter_digest`** |
| 確認 | **`list_pending`**(イベント未作成・要更新のシーン、まとめ要更新の章) |

制作チャットから変える点:

- **読み取りの範囲は物語全体**(制作チャットと同じ。アンカーは持たない)
- **シーンを作る・直すツールに `events` を足す**(省略可)。本文と一緒に渡せば、1 回の呼び出しで済む
- **`emotional_core`(感情の核)を書けるようにする。** いまの制作のツールには無い。取り込み JSON にはあり、
  外部の LLM なら書ける
- **経過と場所は必ず外部の LLM が指定する。** ローカル LLM による推測(`infer_scene_setting`)は呼ばない
- **`reason` は必須のまま残す。** 変更履歴に残り、後から「なぜ変えたか」を追える

MCP のサーバー説明(クライアントが最初に読む文)には、作業の型を短く書く:
「読んでから書く」「シーンを書いたらイベントも書く」「終わりに `list_pending` で残りを確かめる」。

## 6. ローカル LLM を呼ばない

`apply_edit` は、いま 3 か所でローカル LLM を呼ぶ。MCP の経路ではどれも止める。

| 呼び出し | いまの止め方 | 必要な変更 |
|---|---|---|
| イベントの抽出(`generation.extract_events`) | `extract=False` | 無し |
| 経過・場所の推測(`infer_and_record`) | `infer=False` | 無し |
| 追加候補の前後照合(`production_continuity.check`) | 止められない(新規シーンで必ず呼ぶ) | 止める引数を足す |

- 前後照合は「直前・直後の本文と矛盾しないか」を LLM に見せる検査。外部の LLM は前後を読んでから書くので、
  同じ検査を二重にしない。重複シーンの拒否・保護・競合の検出(LLM を使わない検査)はそのまま効かせる
- **設定のスイッチは足さない。** MCP の経路が呼ばないだけで、llama-server が動いていても落ちていても同じ結果になる
- 記憶の検索に使う埋め込み(Ruri)は CPU で別に動くので、llama-server が無くても `search_memories` は働く

## 7. イベントと章のまとめ

### 7.1 イベント

- **書きやすい形で受けて、内部の形へ変換する。** 取り込み JSON の形(`memory` / `relation` / `fact` / `retire`)を使う。
  内部の type / payload をそのまま書かせるより間違えにくいことは、取り込みの設計で決めた判断([import-json.md](import-json.md) §8)
- **人物は ID で指す。** 取り込みは ID が無い前提で名前を使ったが、MCP では `read_library` で ID が分かり、
  ほかのツール(`cast`)も ID なので揃える
- **変換と検査は取り込みから移す。** `importer._events` と、イベントの項目の検査。新しい置き場は `backend/external_events.py`
- **質の目安はツールの説明文に書く。** 重要度の目安、関係の変化の幅、秘密は世界の事実にしない、居場所を事実として書かない
  ([import-json.md](import-json.md) §5.4 の内容)
- **保存は既存の経路。** `store.replace_events`(`source="llm"`)。必須項目の検査(`validation.payload_errors`)と
  シーンの検証(`store.validate`)を通す
- **`apply_edit` に `events` を渡せるようにする。** コピー上で本文とイベントを入れて検証し、通ったものだけを確定する
  (いまの抽出ありの経路と同じ流れで、抽出の代わりに渡されたイベントを使う)

### 7.2 古さの印が安全網になる

イベントの古さは、イベントを書いたときの本文の指紋と、いまの本文の指紋を比べて決まる
([event-staleness.md](event-staleness.md))。フラグを立てる方式ではないので、MCP 側に特別な処理は要らない。

- 外部の LLM が本文だけ直してイベントを書かなければ、そのシーンは「イベント要更新」になる
- 新しいシーンをイベント無しで作れば「イベント未作成」になる
- `set_scene_events` で書けば、いまの本文に合わせたものとして印が消える
- 書き込みの結果に、そのシーンの印の状態を添える(忘れに気付けるように)。`list_pending` でまとめて確かめられる

画面の「まとめて更新」は印の付いたシーンだけを拾うので、外部の LLM が書いたイベントを勝手に上書きしない。
後で本文を手で直して更新をかければ、そのシーンはローカルの抽出結果に置き換わる(これは普通の動き)。

### 7.3 章のまとめ

- 保存は `store.save_group_digest`。使える型は `memory_compress` と `fact_set`
- 形は、ローカルの生成(`generation.generate_group_digest`)が作るものに合わせる。こちらも書きやすい形を決めて変換する
- 章の中身を変えると「まとめ要更新」が付く(既存の動き)。`list_pending` に出る

## 8. 取り消し・排他・保護

### 取り消し

制作チャットは「1 回の依頼」の前にスナップショットを取り、作業単位で戻せる。MCP は呼び出しがばらばらに届き、
作業の始まりと終わりが無い。

- **書き込みの前に `snapshots.auto` を呼ぶ**(ラベル「外部 LLM の編集の前」、間隔 10 分)。
  同じ理由の保存は 10 分に 1 回までなので、続けて書いても保存は 1 つ。イベント編集の前の保存と同じ型
- 戻すのは、設定のスナップショット一覧から。**会話の中の「元に戻す」ボタンは作らない**(会話がアプリの外にあるため)
- 採らなかった案: 接続ごとに 1 つ保存する。長い作業だと最初の時点にしか戻れない

### 排他

- **制作チャットの作業中は、MCP の書き込みを断る。** 既存の `ProductionMiddleware` は、作業中の POST を
  409 で止める。`/external/call` も POST なので、そのままだと読み取りまで止まる。読み取りのツールの呼び出しは
  通すよう、ミドルウェアに例外を足す
- **MCP が書いている間、手での編集は止めない。** 作業の区切りが無いので、止める期間を決められない
- 代わりに、呼び出しごとの検査で守る: `apply_edit` はコピー上で検証してから確定し、対象が消えていれば断る。
  外部の LLM が古い内容を元に `patch_scene` を呼べば、置換元が見つからず断られる

### 保護

制作チャットの保護指定と変更範囲は、依頼ごとに画面で選ぶもので、保存されていない。
MCP の最初の版では持たない(§12)。

## 9. 画面への反映

いま、外から書かれた変更を画面へ伝える経路は無い。制作チャットは自分の SSE の中で変更を受け取り、
`notifyGraphChanged()`(構造)と `workspace.changed()`(資料庫)を呼んで読み直している。

**変更の通し番号をポーリングする。**

- sidecar は、MCP の書き込みが成功するたびに番号を 1 つ進める。物語(シーン・イベント・章)と資料庫で番号を分ける
- renderer は番号を定期的に取り、変わっていたら `notifyGraphChanged()` / `workspace.changed()` を呼ぶ。
  読み直しの処理は制作チャットと同じものを使う
- 取り方は、ステータスバーが 2 秒ごとに叩いている `systemResources` の応答に番号を添える(新しい通信を足さない)

採らなかった案: **常時つなぐ SSE**。即時に反映できるが、接続の張り直しと、ライブラリ切替時の扱いが増える。
2 秒の遅れは、外部のクライアントの画面を見ながら使う用途では気にならない。足りなければ後で替えられる。

注意が要る点:

- **手で編集している途中の下書き。** 詳細欄で未保存のまま、同じシーンが外から書き替わる場合がある。
  読み直しで下書きを消さない(制作チャットの手動編集と同じ扱いにする)。保存時に内容が変わっていたら知らせる
- **どこが変わったか。** 制作チャットは作業中のシーンへ画面が追従する(`active_node`)。MCP では追従させず、
  ステータスバーに「外部から変更: <シーン名>」を短く出すだけにする(作者が別の場所を見ている可能性が高い)
- **鑑賞モード。** 開いている清書は「要更新」の印が付くだけで、勝手には書き替わらない(既存の動き)

## 10. 取り込み JSON の削除

MCP を入れるときに、取り込みを削除する。

| もの | 扱い |
|---|---|
| 設定の取り込み画面(`modes/settings/ImportSection.tsx`)と API | 削除 |
| `backend/importer.py` | イベントの変換と検査を `external_events.py` へ移して、残りを削除 |
| `backend/import_check.py` | 削除 |
| [docs/reference/import-format.md](../reference/import-format.md) / `import-example.json` | 削除。質の目安はツールの説明文へ移す |
| [import-json.md](import-json.md) | 冒頭に「MCP に置き換えて削除した」と書いて残す(判断の経緯を追えるように) |
| テスト、`unconfirmed.md` の該当行 | 削除 |

失うもの:

- **全部か無しかの保証。** 取り込みは 1 回で全部を入れ、失敗したら全部を取り消した。MCP は 1 つずつ確定する。
  途中で止まっても、10 分ごとのスナップショットと `list_pending` で続きから直せる
- **チャットだけの LLM(ブラウザ版)の経路。** MCP に繋げないクライアントでは使えなくなる
- **映画 1 本をまとめて入れるときの速さ。** 40〜60 シーンで数百回の呼び出しになる。必要になったら、
  複数シーンを 1 回で受けるツールを足す(§12)

## 11. 段階

**段階 1(最初の版)**

1. sidecar: `external_tools.py` と `/external/tools`・`/external/call`。読み取りと既存の書き込み
2. `apply_edit` の変更: 前後照合を止める引数、`events` の受け渡し、`emotional_core`
3. `external_events.py`: イベントの書きやすい形の検査と変換(取り込みから移す)。`set_scene_events` / `get_events`
4. `set_chapter_digest` / `list_pending`
5. 書き込み前の `snapshots.auto`
6. 変更の通し番号と、renderer の読み直し
7. 橋(`mcp_bridge.py`)と、設定画面の登録用コマンド
8. 取り込みの削除(§10)

検証は `data/test/` の隔離ライブラリで行う。ユーザーのライブラリには繋がない。
pytest は `/external/call` を直接叩く。橋を通した確認は、Claude Code から隔離ライブラリの sidecar に繋いで行う。

**段階 2(使ってから決める)**

- 画像の予約(`generate_images`。ComfyUI は LLM と別なので動く)
- 保護と変更範囲
- 清書を外部の LLM に書かせるか(原則 4 は守れるが、文体プリセットの渡し方を決める必要がある)
- 正史の切替、結末ノードの操作
- 複数シーンをまとめて受けるツール

## 12. 決まっていないこと

- **保護の持ち方。** 外部の LLM に触らせたくないシーンを、どこで指定するか。案: シーンに保存する印として持つ
  (制作チャットの保護も同じ印を使うように揃える)。最初の版では持たない
- **章のまとめの書きやすい形。** `memory_compress` は置き換える記憶の ID を持つ。外部の LLM に ID を書かせるか、
  章の中の記憶をアプリ側で対応付けるか
- **読み取りの量。** 制作チャットの読み取りは ctx 8192 向けに絞ってある(記憶は 1 キャラ数件など)。
  外部の LLM 向けに上限を緩めるか、そのままにするか。最初はそのままにして、足りない場面を見てから決める
- **書き込みの許可。** 「読むだけ」で繋ぐ設定を持つか。クライアント側の承認で足りるなら不要
- **どのライブラリに書くか。** MCP はアプリで開いているライブラリに書く。外部の LLM に、いま開いている
  ライブラリの名前を最初に知らせる(間違った作品に書かないように)。ライブラリの切替は MCP からはさせない
- **変更履歴での見分け。** 外部の LLM の変更を、ローカルの制作(`source="llm"`)と分けて記録するか

## 13. 目的・原則との関係

- **goals の「すべてローカルで完結」との関係。** アプリ自身は外部へ通信しない点は変わらない。ただし、
  外部のクライアントを繋ぐと、物語の内容がそのクライアントの LLM の提供元へ送られる。使うかどうかは作者が
  クライアントを登録するかで決まる。実装するときに、[goals.md](../plan/goals.md) の追加の目標へこの機能を足し、
  「外部の LLM は任意で、繋がなければ従来どおりローカルで完結する」と書く
- **原則 1・2(ビートが正史、状態は導出)。** 書くのはシーンとイベントだけ。状態は fold で導出される
- **原則 5(LLM 由来の変更も同じイベントとして記録)。** 外部の LLM のイベントも、同じ events テーブルに同じ型で入る
- **原則 4(レンダリングは状態を変更しない)。** 清書には触らない(段階 1)
