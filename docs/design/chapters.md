# 章グループ設計 — エピソード単位のまとめと stale 遮断

作成日時: 2026-08-01 05:57
更新日時: 2026-08-01 05:57

直列につながるノードを「章(エピソード)」のグループとして扱い、
章境界に「個々の記憶よりぼんやりしたまとめ」を中間状態として置く構想の設計メモ。
2026-08-01 のユーザー発案。実装前の設計段階。

動機(ユーザーの言葉から):

- ノードをエピソードや章の単位でまとめたい。構造モードでは**グループ枠でノードを囲み**、
  **鑑賞モードでも章で階層分け表示**したい
- いまは 1 ノードを変えるだけで下流のノードが全部 stale になる。章単位の
  「まとめの記憶」を下流が引き継ぐ形にして、章の中の編集を章の中に閉じたい

## 1. 現状の仕組みと課題

| 仕組み | 実装 | 課題 |
|---|---|---|
| 状態の導出 | fold は「親の全状態 + 自ノードのイベント」の畳み込み([fold.py](../../backend/fold.py) `fold()`)。`input_hash` に**親の状態ハッシュが連鎖**する(`input_hash`) | 上流が 1 文字変わると下流全ノードの入力が変わる構造 |
| dirty / stale 伝播 | [store.py](../../backend/store.py) `mark_dirty_downstream()` が下流全ノードの `state_cache.dirty` と `renders.stale` を**一括で**立てる。`update_node` はどのフィールドの編集でも呼ぶ | beat の誤字修正(状態に影響しない)でも下流の全清書が stale になる |
| 記憶 | `memory_add` はキャラ × 出来事 1 件の粒度。`memory_compress`(古い記憶群→要約 1 件に置換)は**イベント型として存在するが自動化は未実装**(Phase 6 予定) | 長編では記憶が伸び続ける。「ぼんやりしたまとめ」に相当する層がない |
| 生成コンテキスト | シーン生成は「全キャラ・全 facts・全関係 + 直近 3 ビート + 記憶検索 top5」([generation.py](../../backend/generation.py) `_build_messages`) | 全量を積むのでキャラ・シーンが増えると肥大化(progress.md 既知課題) |
| グループ概念 | 章・エピソードに相当する概念は**存在しない**。近いのは「島(detached)」と右クリックの一括操作のみ | — |

実害の大半は「再 fold のコスト」ではなく「**下流の清書(LLM 再生成)が全部 stale 扱いになる**」こと。
遮断すべきは主に renders.stale の伝播で、state の再 fold 自体は軽い。

## 2. 設計方針

goals.md の設計原則との整合を最優先にする:

1. **状態は保存せず、常に導出** — 章のまとめも fold への入力(イベント相当)として持ち、
   導出の連鎖は壊さない。「まとめを適用した状態」もルートからの畳み込みで再現できること。
2. **LLM 由来も手動修正も同じイベント** — まとめは LLM に生成させた後、作者が
   手で直せる(既存の EventsEditor と同じ編集体験)。
3. **まとめは自動では変わらない(凍結)** — 章内を編集してもまとめは自動更新しない。
   まとめに「要更新」バッジを出し、**作者が更新して内容が実際に変わったときだけ**下流へ波及する。
   これが stale 遮断の本体。

## 3. データモデル

### groups テーブル + nodes.group_id

```sql
CREATE TABLE groups(
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,            -- 章タイトル(鑑賞モードの見出しにも使う)
  color TEXT,                     -- 構造モードの枠の色(NULL = 既定)
  digest_events TEXT,             -- 章じまいのまとめ(イベント配列 JSON。NULL = 未作成)
  digest_stale INTEGER DEFAULT 0, -- 章内が編集されてまとめが古い(要更新バッジ)
  created_at TEXT
);
-- nodes には冪等 ALTER で追加
ALTER TABLE nodes ADD COLUMN group_id TEXT;  -- NULL = どの章にも属さない
```

- 章は「**正史パス上の連続区間**」を前提とする。DB では強制せず、章に入れる API 側で
  連続性を検証する(非連続になったら UI で警告)。章の順序は正史パス順から導出できるので
  position 列は持たない。
- **分岐ノードは分岐元の章に表示上属す**(group_id は付けず、描画時に親の章の枠内に入れるだけ)。
  分岐が正史化されて章の区間が変わるケースは「章の割り当てを外す」に倒す(まず単純に)。
- **島には章を付けない**(島はそれ自体がまとまり。本編に接続したときに章へ入れる)。
- 章の入れ子(部・章・節)は**やらない**。1 階層のみ。

### まとめ(digest)を groups 側に持つ理由

まとめの置き場所は 3 案を比較した:

| 案 | 内容 | 問題 |
|---|---|---|
| A. 章末尾に専用の「章じまいノード」を挟む | canon_path に混ざり、清書対象・シーン数・スライディングウィンドウに影響。各所に除外処理が要る | 却下 |
| B. **groups.digest_events(採用)** | ノードの events と独立。「イベント作り直し」(replace_events)で消えない。fold には「章末尾ノードの適用後に digest を適用」のフックを 1 箇所足すだけ | fold の入力が nodes 外に増える(input_hash に digest のハッシュを混ぜて整合を取る) |
| C. 章末尾ノードの events に混ぜる | そのノードで「イベント作り直し」をすると消える。抽出結果とまとめが同じ配列に同居して紛らわしい | 却下 |

### まとめの中身は memory_compress を主役にする

- まとめの実体は既存イベント型で表現する: **`memory_compress`**(章内の各キャラの記憶
  → キャラごと 1〜数件の要約記憶に**置換**)+ 必要なら `fact_set`(世界・キャラの要約的な事実)。
  新イベント型は増やさない。fold の適用ロジックがそのまま使える。
- **置換(replaces)であることが重要**: 下流の状態は章内の生の記憶に依存しなくなり、
  まとめが変わらない限り「記憶の観点では」下流の状態が変わらない。
- facts / relationships(関係値)は生のまま下流へ流す。これらは積算値・キーバリューで
  既に「まとめ」的であり、章内でこれらを変える編集は物語の状態変更そのものなので、
  下流へ波及するのが正しい。**「ぼんやりさせる」対象は記憶に絞る。**
- Phase 6 予定だった「memory_compress の自動要約圧縮」は、この「章じまい」を
  実行タイミングとして実装する(独立機能としては作らない)。

前提として先に潰すもの: **イベント ID が置換のたびに再発行される既知課題**
(progress.md「レビューで見送った既知の課題」)。`memory_compress.replaces` が
イベント ID 参照のため、再抽出で ID が変わると置換対象が宙に浮く。
digest 導入前に `EventIn` への id 引き継ぎを入れる。

## 4. fold と stale 遮断

### fold のフック

`store.get_state()` のパス畳み込みで、ノード n が**章の末尾**(その章に属す正史パス上の
最後のノード)なら、n のイベント適用後に `groups.digest_events` を続けて適用する。
`input_hash` の計算には digest のハッシュを混ぜる(digest が変われば下流は再 fold される。
逆に digest が同じなら記憶まわりの入力は同じ)。

### stale 伝播の変更(2 段階)

**Step 1 — early cutoff(章がなくても効く)**: 再 fold 時に、そのノードの新しい
`state_hash` が旧値と一致したら、それより下流の `renders.stale` を立てない
(状態に影響しない編集 — 誤字修正など — で下流の清書が stale にならなくなる)。
あわせて `update_node` の dirty 契機を「状態に効くフィールド」と「プロンプト文面に
効くだけのフィールド」に分離する(場所編集は既にこの分離をしている)。

**Step 2 — 章境界での遮断**: 章内のノードを編集したとき:

1. 同じ章の中の下流ノードは従来どおり dirty + stale
2. 章の `digest_stale = 1` を立てる(UI に「まとめが古い」バッジ)
3. **章より下流へは伝播しない**(digest は凍結されているため、下流の入力は変わっていない)
4. 作者が「まとめを更新」を実行し、新しい digest の内容が旧 digest と異なるときだけ、
   下流の章へ dirty + stale を伝播する(同一なら何も起きない = early cutoff)

注意: facts / relationships は digest を経由しない(生のまま流れる)ので、
それらに効く編集は従来どおり下流へ波及する。遮断されるのは
「記憶の増減・文面変更」と「状態に影響しない編集」。この非対称は UI の説明文で明示する。

## 5. コンテキスト構築の 2 層化

「前の章まで = ぼんやりしたまとめ、いまの章 = 詳細」でプロンプトを組む。

| 対象 | 現状 | 変更 |
|---|---|---|
| シーン生成([generation.py](../../backend/generation.py)) | 全キャラ・全状態 + 直近 3 ビート + 記憶検索 top5 | 状態は fold 済みを使うので**自動的にまとめ後の記憶**になる。加えて「直近 3 ビート」を「**当章のビート全部(上限あり)+ 前章までは章タイトル 1 行ずつ**」に変えると、章のあらすじ層がプロンプトに乗る |
| 清書([rendering.py](../../backend/rendering.py)) | 直前散文の末尾 1400 字 + state(記憶末尾 8 件) | state 経由で自動的にまとめ後になる。章の先頭シーンでは「前章のあらすじ」(digest の要約記憶)を明示ブロックで渡すと接続が安定する |
| チャット([chat_agent.py](../../backend/chat_agent.py)) | get_state / search_memories | fold 済み state を読むので自動的に反映。get_beats に章情報(章タイトル・区切り)を含めると「第2章を要約して」が効くようになる |

記憶検索(retrieval)は「そのノード時点の state にある記憶 id」に候補を絞っているため、
置換後は要約記憶が検索対象になる。生の記憶を掘りたいときのために、チャットの
search_memories には「圧縮前も含める」オプションを検討(任意)。

## 6. UI

### 構造モード: グループ枠

- **描画**: React Flow の group ノード / parentNode は使わず、**同一章の連続ノードの
  外接矩形 + 章タイトルのラベルを背景レイヤーに描く**(自前レイアウトと `pos_x/pos_y` の
  焼き付けに干渉させない。既存レイアウトは正史一直線 + 分岐レーンの自前計算のため)。
  枠は選択・ドラッグ対象にしない(ノード操作を邪魔しない)。
- **作成**: 範囲選択 → 右クリック「章にまとめる」(名前を入力)。既存の一括操作メニューに追加。
  単一ノードの右クリックに「章から外す」「章の名前を変更」。
- **章じまい**: 章枠の右端(末尾ノードの近く)に小さなバッジを置く:
  - まとめ未作成 → 「まとめを作る」ボタン
  - `digest_stale = 1` → 「まとめが古い」バッジ + 「更新」ボタン
  - まとめあり → クリックで内容を表示・編集(EventsEditor を流用した読み書き UI)
- 一括操作との連携: 章の右クリックに「この章を一括清書」「この章のイベントを作り直す」
  (既存の一括操作を章の区間に適用するだけ)。

### 鑑賞モード: 章の階層分け表示

- `GET /renders` の各エントリ(SceneEntry)に章情報(group_id / 章タイトル / 章の先頭か)を
  付け、章の変わり目に**章見出し**を挟む:
  - **縦読み / 挿絵分割**: 章の変わり目に見出しブロック(章番号 + タイトル)を挿入
  - **ページモード**: 章の**扉ページ**(タイトルのみのページ)を差し込む
- **目次**: コントロールバーに章ジャンプ(章タイトルのドロップダウン or サイドの目次)。
  ページモードのシークバーに章の区切り目盛りを打つ。
- **Markdown エクスポート**: `# 章タイトル` / `## シーンタイトル` の階層にする
  (現状はシーン見出しのみ)。
- 章に属さないノードは従来どおりフラットに表示(見出しなし)。

## 7. 実装フェーズ

| フェーズ | 内容 | 単体で価値が出るか |
|---|---|---|
| **A. stale 粒度改善** | early cutoff(state_hash 不変なら下流 renders を stale にしない)+ update_node の契機分離 | ○(章がなくても誤字修正で全 stale が消える) |
| **B. 章の構造と表示** | groups テーブル + nodes.group_id + 構造モードの枠 + 鑑賞モードの章見出し・目次・エクスポート階層化 | ○(整理・表示だけでも要望の半分を満たす) |
| **C. 章じまいのまとめ** | イベント ID 引き継ぎ修正 → digest 生成(LLM)+ fold フック + digest_stale バッジ + 章境界遮断 | ○(Phase 6 の memory_compress 自動化を兼ねる) |
| **D. 仕上げ(任意)** | 2 層コンテキスト(前章あらすじブロック)、章の折りたたみ表示、チャット get_beats の章対応 | — |

A → B → C の順。A と B は独立なので並行可能。

## 8. 未解決の論点

- **digest 生成のプロンプト設計**: 章内の何を渡すか(ビート列 + 発行済み memory_add か、
  清書済み散文か)。まずはビート + イベントで作り、清書ベースは後で検討。
- **分岐が章の途中から生える場合の正史切替**: 切替で章の区間が非連続になったら
  章割り当てを自動で外す、で始める(データを壊さない最小対応)。
- **「前章の生記憶を見たい」ニーズ**: memory_compress は置換なので、圧縮後は
  fold 状態から生記憶が消える(memories テーブルには行が残る)。事実タブ・関係図の
  ドリルダウンで過去の生イベントは追えるため当面は足りる想定だが、鑑賞・執筆中に
  「章をほどく(digest を無効化して生に戻す)」操作が要るかは使ってみて判断。
- **digest の版管理**: まとめを更新したとき旧まとめを残すか。スナップショット
  (自動保存)があるので専用の履歴は持たない、で始める。
