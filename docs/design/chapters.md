# 章グループ設計 — エピソード単位のまとめと stale 遮断

作成日時: 2026-08-01 05:57
更新日時: 2026-08-02 00:20

直列につながるノードを「章(エピソード)」のグループとして扱い、
章境界に「個々の記憶を**まとめた要約**」を中間状態として置く構想の設計メモ。
2026-08-01 のユーザー発案。実装前の設計段階。

動機(ユーザーの言葉から):

- ノードをエピソードや章の単位でまとめたい。構造モードでは章単位のまとまりとして
  扱い(当初は「グループ枠で囲む」案 → **章ノードの中に入るドリルダウン型の階層表示**に
  変更。§6)、**鑑賞モードでも章で階層分け表示**したい
- いまは 1 ノードを変えるだけで下流のノードが全部 stale になる。章単位の
  「まとめの記憶」を下流が引き継ぐ形にして、章の中の編集を章の中に閉じたい
- 「まとめ」は**要約する**という意味(曖昧・不正確にするという意味ではない)。
  個々の記憶より粒度が粗いだけで、内容は章を正しく代表する要約であること(2026-08-01 補足)
- **基本の作業スタイルは「章の中でノードを編集する」**。章をまたぐ編集は例外的。
  だからこそ「章内の編集は章内に閉じ、下流は凍結されたまとめだけに依存する」設計が効く

## 1. 現状の仕組みと課題

| 仕組み | 実装 | 課題 |
|---|---|---|
| 状態の導出 | fold は「親の全状態 + 自ノードのイベント」の畳み込み([fold.py](../../backend/fold.py) `fold()`)。`input_hash` に**親の状態ハッシュが連鎖**する(`input_hash`) | 上流が 1 文字変わると下流全ノードの入力が変わる構造 |
| dirty / stale 伝播 | [store.py](../../backend/store.py) `mark_dirty_downstream()` が下流全ノードの `state_cache.dirty` と `renders.stale` を**一括で**立てる。`update_node` はどのフィールドの編集でも呼ぶ | beat の誤字修正(状態に影響しない)でも下流の全清書が stale になる |
| 記憶 | `memory_add` はキャラ × 出来事 1 件の粒度。`memory_compress`(古い記憶群→要約 1 件に置換)は**イベント型として存在するが自動化は未実装**(Phase 6 予定) | 長編では記憶が伸び続ける。「章単位の要約」に相当する層がない |
| 生成コンテキスト | シーン生成は「全キャラ・全 facts・全関係 + 直近 3 ビート + 記憶検索 top5」([generation.py](../../backend/generation.py) `_build_messages`) | 全量を積むのでキャラ・シーンが増えると肥大化(progress.md 既知課題) |
| グループ概念 | 章・エピソードに相当する概念は**存在しない**。近いのは「島(detached)」と右クリックの一括操作のみ | — |

実害の大半は「再 fold のコスト」ではなく「**下流の清書(LLM 再生成)が全部 stale 扱いになる**」こと。
遮断すべきは主に renders.stale の伝播で、state の再 fold 自体は軽い。

## 2. 設計方針

goals.md の設計原則との整合を最優先にする:

1. **状態は保存せず、常に導出** — 章のまとめも fold への入力(イベント相当)として持ち、
   導出の連鎖は壊さない。「まとめを適用した状態」もルートからの畳み込みで再現できること。
2. **LLM 由来も手動修正も同じイベント** — まとめは LLM に生成させた後、作者が
   手で直せる(既存の EventsEditor と同じ編集体験)。
3. **まとめは自動では変わらない(凍結)** — 章内を編集してもまとめは自動更新しない。
   まとめに「要更新」バッジを出し、**作者が更新して内容が実際に変わったときだけ**下流へ波及する。
   これが stale 遮断の本体。

## 3. データモデル

> **2026-08-01 一般化**: 当初「章 = 正史パス上の連続区間」としていたが、結末ノード方式の
> 導入で正史は「選択中のルート」に過ぎなくなったため、**章 = 親子で一続きにつながった
> シーンの列(正史・分岐・島のどこでも可)**に緩めた(ユーザー要望)。`on_canon` で
> 区別し、正史依存で残るのは並べ替えと鑑賞モードの見出しだけ。島の章は章ビューに
> 「別ルートの章」の破線カードとして出る。以下の記述の「正史パス上の連続区間」は
> この一般化を踏まえて読むこと。

### groups テーブル + nodes.group_id

```sql
CREATE TABLE groups(
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,            -- 章タイトル(鑑賞モードの見出しにも使う)
  color TEXT,                     -- 構造モードの枠の色(NULL = 既定)
  digest_events TEXT,             -- 章じまいのまとめ(イベント配列 JSON。NULL = 未作成)
  digest_stale INTEGER DEFAULT 0, -- 章内が編集されてまとめが古い(要更新バッジ)
  created_at TEXT
);
-- nodes には冪等 ALTER で追加
ALTER TABLE nodes ADD COLUMN group_id TEXT;  -- NULL = どの章にも属さない
```

- 章は「**正史パス上の連続区間**」を前提とする。DB では強制せず、章に入れる API 側で
  連続性を検証する(非連続になったら UI で警告)。章の順序は正史パス順から導出できるので
  position 列は持たない。
- **分岐ノードは分岐元の章に表示上属す**(group_id は付けず、描画時に親の章の枠内に入れるだけ)。
  分岐が正史化されて章の区間が変わるケースは「章の割り当てを外す」に倒す(まず単純に)。
- **島には章を付けない**(島はそれ自体がまとまり。本編に接続したときに章へ入れる)。
- 章の入れ子(部・章・節)は**やらない**。1 階層のみ。

### まとめ(digest)を groups 側に持つ理由

まとめの置き場所は 3 案を比較した:

| 案 | 内容 | 問題 |
|---|---|---|
| A. 章末尾に専用の「章じまいノード」を挟む | canon_path に混ざり、清書対象・シーン数・スライディングウィンドウに影響。各所に除外処理が要る | 却下 |
| B. **groups.digest_events(採用)** | ノードの events と独立。「イベント作り直し」(replace_events)で消えない。fold には「章末尾ノードの適用後に digest を適用」のフックを 1 箇所足すだけ | fold の入力が nodes 外に増える(input_hash に digest のハッシュを混ぜて整合を取る) |
| C. 章末尾ノードの events に混ぜる | そのノードで「イベント作り直し」をすると消える。抽出結果とまとめが同じ配列に同居して紛らわしい | 却下 |

### まとめの中身は memory_compress を主役にする

- まとめの実体は既存イベント型で表現する: **`memory_compress`**(章内の各キャラの記憶
  → キャラごと 1〜数件の要約記憶に**置換**)+ 必要なら `fact_set`(世界・キャラの要約的な事実)。
  新イベント型は増やさない。fold の適用ロジックがそのまま使える。
- **置換(replaces)であることが重要**: 下流の状態は章内の生の記憶に依存しなくなり、
  まとめが変わらない限り「記憶の観点では」下流の状態が変わらない。
- facts / relationships(関係値)は生のまま下流へ流す。これらは積算値・キーバリューで
  既に「まとめ」的であり、章内でこれらを変える編集は物語の状態変更そのものなので、
  下流へ波及するのが正しい。**要約(まとめ)の対象は記憶に絞る。**
- Phase 6 予定だった「memory_compress の自動要約圧縮」は、この「章じまい」を
  実行タイミングとして実装する(独立機能としては作らない)。

前提として先に潰すもの: **イベント ID が置換のたびに再発行される既知課題**
(progress.md「レビューで見送った既知の課題」)。`memory_compress.replaces` が
イベント ID 参照のため、再抽出で ID が変わると置換対象が宙に浮く。
digest 導入前に `EventIn` への id 引き継ぎを入れる。

## 4. fold と stale 遮断

### fold のフック

`store.get_state()` のパス畳み込みで、ノード n が**章の末尾**(その章に属す正史パス上の
最後のノード)なら、n のイベント適用後に `groups.digest_events` を続けて適用する。
`input_hash` の計算には digest のハッシュを混ぜる(digest が変われば下流は再 fold される。
逆に digest が同じなら記憶まわりの入力は同じ)。

### stale 伝播の変更(2 段階)

**Step 1 — early cutoff(章がなくても効く)**: **実装済み(2026-08-01。フェーズ A)**。
`update_node` の契機を分離: 状態(fold)に効くノードフィールドは cast のみで、
title / beat / emotional_core / location / story_time はプロンプト文面のみ
→ **自ノードの清書だけ stale**(下流の状態・清書は保つ)。cast の編集は
再 fold して**状態ハッシュが変わったときだけ**下流へ波及(early cutoff。
並べ替えや登場済みキャラの追加は波及しない)。

制限: イベント編集(replace_events)は従来どおり下流まで波及する。置換のたびに
イベント ID が再発行されて状態ハッシュが必ず変わるため cutoff が効かず、また
状態は記憶を event_id 参照で持つので「文面だけの変更」をハッシュでは検出できない
(記憶の文面は memories テーブル側にあり、下流のプロンプトに効く)。
イベント編集への cutoff は、ID 引き継ぎ(フェーズ C の前提作業)とあわせて設計する。

**Step 2 — 章境界での遮断**: 章内のノードを編集したとき:

1. 同じ章の中の下流ノードは従来どおり dirty + stale
2. 章の `digest_stale = 1` を立てる(UI に「まとめが古い」バッジ)
3. **章より下流へは伝播しない**(digest は凍結されているため、下流の入力は変わっていない)
4. 作者が「まとめを更新」を実行し、新しい digest の内容が旧 digest と異なるときだけ、
   下流の章へ dirty + stale を伝播する(同一なら何も起きない = early cutoff)

注意: facts / relationships は digest を経由しない(生のまま流れる)ので、
それらに効く編集は従来どおり下流へ波及する。遮断されるのは
「記憶の増減・文面変更」と「状態に影響しない編集」。この非対称は UI の説明文で明示する。

## 5. コンテキスト構築の 2 層化

「前の章まで = 章単位の要約、いまの章 = 詳細」でプロンプトを組む。

| 対象 | 現状 | 変更 |
|---|---|---|
| シーン生成([generation.py](../../backend/generation.py)) | 全キャラ・全状態 + 直近 3 ビート + 記憶検索 top5 | 状態は fold 済みを使うので**自動的にまとめ後の記憶**になる。加えて「直近 3 ビート」を「**当章のビート全部(上限あり)+ 前章までは章タイトル 1 行ずつ**」に変えると、章のあらすじ層がプロンプトに乗る |
| 清書([rendering.py](../../backend/rendering.py)) | 直前散文の末尾 1400 字 + state(記憶末尾 8 件) | state 経由で自動的にまとめ後になる。章の先頭シーンでは「前章のあらすじ」(digest の要約記憶)を明示ブロックで渡すと接続が安定する |
| チャット([chat_agent.py](../../backend/chat_agent.py)) | get_state / search_memories | fold 済み state を読むので自動的に反映。get_beats に章情報(章タイトル・区切り)を含めると「第2章を要約して」が効くようになる |

### まとめと生データの役割分担(2026-08-01 追記)

章から下流へは**両方引き継ぐが、経路を分ける**(ユーザー確認済みの方針):

| 層 | 内容 | stale 遮断との関係 |
|---|---|---|
| **状態(fold)** | まとめ(要約記憶)+ 生の facts / 関係値 | 下流の状態はこれだけに依存。**遮断はこの経路を見る** |
| **アーカイブ** | 生の記憶(memory_compress は fold 状態から外すだけで、`memories` テーブルと events には全部残る) | 検索で引く。状態の依存関係には含めない |

清書(レンダリング)は「まとめで骨格を保ちつつ、生の詳細も使う」二段構えにする:

1. facts / 関係値はもともと生のまま届く
2. 記憶は「前章まで = まとめ、当章 = 生」が既定。ただし**記憶検索(ハイブリッド top-k)の
   対象に圧縮済みの生記憶も含める**ことで、そのシーンに関係する過去の細部
   (序盤の約束の正確な文言など)をピンポイントで注入できる
3. 直前シーンの散文末尾 1400 字(既存のスライディングウィンドウ)は生の文章そのもの

全生データを常に流すとコンテキストが肥大化して遮断も無意味になるため、
生データは**検索経由の動的注入**に限る。さらに、注入の既定を工程で使い分ける
(2026-08-01 ユーザー方針: 「作業中はまとめだけでいい」):

| 工程 | 前章までのコンテキスト | 理由 |
|---|---|---|
| **作業中**(ビート生成・編集、チャット) | **まとめだけ**(既定) | 軽く・速く。stale 遮断もフルに効く。作業のテンポを守る層 |
| **清書**(レンダリング) | まとめ + **検索で生記憶を注入**(既定オン) | 品質優先の層。清書はもともと LLM が重いので検索の追加コストは誤差 |
| チャットで細部を掘るとき | ツール(search_memories / recall)の「圧縮前も含める」オプションを明示的に使う | 必要なときだけ |

トレードオフ: 検索で注入した生記憶はプロンプトへの動的注入なので、生記憶を後から
直しても、それを引用していた下流の清書は自動では stale にならない。精密化するなら、
清書時に使った記憶 id を `renders.meta` に記録し(prompt_messages 保存の仕組みを流用。
2026-07-31 実装)、**その記憶が変わったときだけ該当清書を stale にする**個別追跡が
将来の拡張として可能。

## 6. UI

### 構造モード: 章ビュー ⇄ 章内ビューの 2 階層(2026-08-01 変更)

当初案は「同一キャンバスに全シーンを並べて章の枠を背景に描く」だったが、
基本の作業スタイルが「章の中で編集する」であることから、
**ドリルダウン型の階層表示に変更**(ユーザー決定)。
**データモデルは変えない**(章の実体ノードは作らず、真実はシーンノード + シーン間エッジ +
groups ラベルのまま。章ビューは導出された表示)。

- **章ビュー(上の階層)**: 章ノードだけが章同士のエッジでつながって並ぶ。
  - 章ノードと章間エッジは**表示のための導出**。章間のつながりは
    「章 N の末尾シーン → 章 N+1 の先頭シーン」の正史エッジから導く
  - 章ノードに出す情報: タイトル / シーン数 / 清書・stale の集計 /
    まとめ(digest)の状態バッジ(未作成・要更新・作成済み)。
    章間エッジは「まとめの受け渡し」の場所なので、**stale の管理単位と画面の単位が一致する**
  - **章カードの表紙(サムネイル)**(2026-08-01 追加。ユーザー要望): 章のシーンの挿絵を
    1 枚出す。どのシーンを使うかは `groups.cover_node_id`(NULL = 自動)に持ち、
    **指定が無ければ章の中で最初に挿絵があるシーン**を使う。挿絵の実体はシーン側の
    ままで、章は「どれを表紙にするか」だけを持つ(章専用の画像は持たない)。
    指定はシーンの右クリック「🖼 この挿絵を章の表紙にする」か章パネルのシーン一覧から。
    表紙のシーンが章から外れた・消えたときは `list_groups` が NULL に読み替えて返す
    (自動導出に戻る)。見え方はシーンカードと同じで、**切り抜かず元の比率のまま**
    (ユーザー指定。16:9 に統一する案は却下)。
    **常時アニメーション(章内の挿絵のクロスフェード)はやらない**: 章ビューは探すための
    俯瞰画面で、表紙は「いつ見ても同じ絵」であるほど章の識別子として働くため。
    中身をのぞく用途が実際に要るなら、ホバー中だけの再生として後から足す
  - 章に属さないシーン(書き始め・作り置きの島)は「未分類」領域として章ビューに出す
  - ダブルクリック(または「開く」)で章の中へ
  - **章カードの位置は作者が自由に置ける**(2026-08-01 変更。ユーザー報告「章カードを
    ドラッグしても元に戻る」)。位置は `groups.pos_x/pos_y` に保存し、まだ動かして
    いない章だけ導出位置 = **先頭シーンの位置**(正史・島とも同じ)に置く。
    ⟲(整列)は**章ビューでは章カードと未分類ノードだけを並べ、章の中には触らない**
    (2026-08-02 変更。ユーザー要望「章の方で整列を押したら章の中身は無視してほしい」)。
    章カードを 1 枚のノードに畳んだ導出グラフを並べて `groups.pos_x/pos_y` に焼き付ける。
    手動配置をすべて捨てる全体リセットはフラット表示の ⟲ のまま。
    **ドラッグと並べ替えは兼ねない** —
    ドラッグを並べ替えとして解釈していた頃は、並びが変わらない落とし方をすると
    カードが導出位置へ戻り「動かせない」ように見えていた。並べ替えは右クリック(§8)で、
    **入れ替えた 2 章のカード位置も一緒に交換**する(両方とも導出位置のままなら、
    並びに従って自然に入れ替わるので何も書き込まない)
  - **矢印キーの移動は「いま画面に出ているつながり」を辿る**(2026-08-01 修正。ユーザー報告
    「章ビューで左右キーを押しても次のノードに移らない」)。章ビューでは ← → が章から章へ
    (エッジの端点を章カードへ畳んだ導出グラフを辿る)、↑ ↓ が分岐レーン。章カードへ移ると
    右のインスペクタも章パネルに切り替わる。章内ビューではその章に見えているシーンの中だけを移動する
- **章内ビュー**: その章のシーンノードだけをフィルタ表示。パンくず(章タイトル)で章ビューへ戻る。
  - 分岐は分岐元シーンのある章の中に表示(§3 の方針どおり)
  - ⟲(整列)は**その章に見えているシーンだけ**を並べ直す(2026-08-02 変更。ユーザー要望。
    以前は全体リセットに落ちていて、章の外まで動いていた)。2 つ以上選択していれば
    従来どおり選択分だけ
  - 文脈のために**前章の末尾 2〜3 シーンを薄く表示**することを検討(清書の
    スライディングウィンドウと同じ発想。読み取り専用)
- **章じまい(まとめ)の UI は、章ノードを選択したときの右インスペクタ**に置く
  (2026-08-01 ユーザー決定。シーン選択 → インスペクタという既存の操作体系に合わせる。
  当初の「章内ビューの末尾」案から変更):
  1. 章の情報: タイトル(名前の変更)/ メンバーのシーン一覧(クリックで選択)/ 解除
     (呼び名は「解散」→「解除」に変更。2026-08-01 ユーザー指摘)
  2. まとめ(digest): 状態バッジ(未作成 / 最新 / 要更新)+「まとめを作る / 更新する」
     ボタン。生成された memory_compress / fact_set は **EventsEditor を流用したフォーム**で
     表示・手直しできる(キャラごとの要約記憶が並ぶ)
  3. まとめの更新で内容が実際に変わったときだけ下流の章へ stale が波及(§4)
- **フラット表示(現状の全シーン表示)への切替を残す**: 相談チャットのアンカー選択・
  正史切替など全体を俯瞰したい場面のため。表示の切替であってデータは同じ
- **作成**: フラット表示 or 未分類で範囲選択 → 右クリック「章にまとめる」(名前を入力)。
  章内ビューからは「章から外す」「章の名前を変更」
- 一括操作との連携: 章ビューの章ノード右クリックに「この章を一括清書」
  「この章のイベントを作り直す」(既存の一括操作を章の区間に適用するだけ)。

### 鑑賞モード: 章の階層分け表示

- `GET /renders` の各エントリ(SceneEntry)に章情報(group_id / 章タイトル / 章の先頭か)を
  付け、章の変わり目に**章見出し**を挟む:
  - **縦読み / 挿絵分割**: 章の変わり目に見出しブロック(章番号 + タイトル)を挿入
  - **ページモード**: 章の**扉ページ**(タイトルのみのページ)を差し込む
- **目次**: コントロールバーに章ジャンプ(章タイトルのドロップダウン or サイドの目次)。
  ページモードのシークバーに章の区切り目盛りを打つ。
- **Markdown エクスポート**: `# 章タイトル` / `## シーンタイトル` の階層にする
  (現状はシーン見出しのみ)。
- 章に属さないノードは従来どおりフラットに表示(見出しなし)。

## 9. 検討中: 章の in / out マーカー(2026-08-01 ユーザー発案)

章に**入口(in)と出口(out)のマーカーノード**を置き、**`out` が繋がっている先から
根へ辿った道をその章のルート(章ローカルの正史)**とする案。`out` を別の枝へ繋ぎ替えれば、
章の中でルートを差し替えられる。**未着手・未決定**(この節は記録)。

```
        ┌─ 章「港の夜」─────────────────┐
  …→ in ─→ A ─→ B ─→ C ──→ out ─→ (次章の in)
        │         └→ B' ─→ C'  ←候補(章の正式メンバー)
        └───────────────────────────┘
```

[endings.md](endings.md) の「正史 = アクティブな結末から根への逆引き」と**完全に同型**で、
それを章スコープに降ろしたもの。思想としては一貫している。

### 効くところ

1. **候補(分岐)が章の正式メンバーになれる**。現状は章 = 一続きの鎖という制約のため
   分岐に `group_id` を付けられず(§3)、章内ビューに表示されるだけで、章のシーン一覧にも
   一括操作の対象にも入らない
2. **章ローカルの正史切替**。いまルートを変えるには結末の切替しかなく粒度が物語全体。
   `out` の付け替えなら章の中で完結する
3. **空の章を器として先に作れる**。現状の章は既存シーンのラベルなので、メンバーが 0 に
   なると `list_groups` から消える。in/out という実体があれば「第3章を先に置いて中身は
   後で書く」ができる(プロット先行の書き方)
4. **章の付け替え・並べ替えが単純になる**。`move_group` の「連続区間のつなぎ替え」が、
   in の親と out の子の差し替えだけになる
5. **digest の適用点が実体になる**。いまは「章末尾ノードを導出してその後に適用」だが、
   `out` に適用すると言い切れる

### 決めること

- **不変条件「章の外へ出るときは必ず out を通る」**。崩れると章の境界が意味を失う。
  裏返すと、章間エッジは導出をやめて実体(out → 次章の in)にできる
- **グローバル正史との整合**。アクティブな結末からの逆引きが章を通過するときは
  「章の中では out の指すルートを通る」と定義すれば二重定義にならない。ただし
  「out は枝 B' を指しているのに結末は C の下流」という状態は作れてしまうので、
  **out の付け替え時に下流の結末も追従させる**(`make_canon` 相当)か、
  ⚠ バッジで知らせるかを決める必要がある
- **in は要るか**。out だけでも章のルートは決まる(入口は逆引きで一意)。ただし
  上の 3 と 4 は in があって初めて成立する。「はじまり / 結末」と対称になるので
  **両方置く**のが有力
- **既存の章の移行**。kind 導入時と同じ無停止移行(既存の章に in/out を自動生成)

### コスト

**フェーズ B・C の作り直しに近い**。§3 で「章じまいノードを挟む案 A」を却下した判断
(章の実体は作らない)をひっくり返すことになり、`create_group` / `list_groups` /
`move_group` / digest の合流点 / 章ビュー / 章内ビュー / 一括操作の対象 / 鑑賞モードが
全部影響を受ける。ただし当時と違い、**結末方式でマーカーノードの概念と除外処理は
すでに全体に入っている**ので、案 A 却下時の見積もりよりは安い。
