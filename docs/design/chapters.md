# 章グループ設計 — エピソード単位のまとめと stale 遮断

作成日時: 2026-08-01 05:57
更新日時: 2026-08-02 12:10

直列につながるノードを「章(エピソード)」のグループとして扱い、
章境界に「個々の記憶を**まとめた要約**」を中間状態として置く構想の設計メモ。
2026-08-01 のユーザー発案。実装前の設計段階。

動機(ユーザーの言葉から):

- ノードをエピソードや章の単位でまとめたい。構造モードでは章単位のまとまりとして
  扱い(当初は「グループ枠で囲む」案 → **章ノードの中に入るドリルダウン型の階層表示**に
  変更。§6)、**鑑賞モードでも章で階層分け表示**したい
- いまは 1 ノードを変えるだけで下流のノードが全部 stale になる。章単位の
  「まとめの記憶」を下流が引き継ぐ形にして、章の中の編集を章の中に閉じたい
- 「まとめ」は**要約する**という意味(曖昧・不正確にするという意味ではない)。
  個々の記憶より粒度が粗いだけで、内容は章を正しく代表する要約であること(2026-08-01 補足)
- **基本の作業スタイルは「章の中でノードを編集する」**。章をまたぐ編集は例外的。
  だからこそ「章内の編集は章内に閉じ、下流は凍結されたまとめだけに依存する」設計が効く

## 1. 現状の仕組みと課題

| 仕組み | 実装 | 課題 |
|---|---|---|
| 状態の導出 | fold は「親の全状態 + 自ノードのイベント」の畳み込み([fold.py](../../backend/fold.py) `fold()`)。`input_hash` に**親の状態ハッシュが連鎖**する(`input_hash`) | 上流が 1 文字変わると下流全ノードの入力が変わる構造 |
| dirty / stale 伝播 | [store.py](../../backend/store.py) `mark_dirty_downstream()` が下流全ノードの `state_cache.dirty` と `renders.stale` を**一括で**立てる。`update_node` はどのフィールドの編集でも呼ぶ | beat の誤字修正(状態に影響しない)でも下流の全清書が stale になる |
| 記憶 | `memory_add` はキャラ × 出来事 1 件の粒度。`memory_compress`(古い記憶群→要約 1 件に置換)は**イベント型として存在するが自動化は未実装**(Phase 6 予定) | 長編では記憶が伸び続ける。「章単位の要約」に相当する層がない |
| 生成コンテキスト | シーン生成は「全キャラ・全 facts・全関係 + 直近 3 ビート + 記憶検索 top5」([generation.py](../../backend/generation.py) `_build_messages`) | 全量を積むのでキャラ・シーンが増えると肥大化(progress.md 既知課題) |
| グループ概念 | 章・エピソードに相当する概念は**存在しない**。近いのは「島(detached)」と右クリックの一括操作のみ | — |

実害の大半は「再 fold のコスト」ではなく「**下流の清書(LLM 再生成)が全部 stale 扱いになる**」こと。
遮断すべきは主に renders.stale の伝播で、state の再 fold 自体は軽い。

## 2. 設計方針

goals.md の設計原則との整合を最優先にする:

1. **状態は保存せず、常に導出** — 章のまとめも fold への入力(イベント相当)として持ち、
   導出の連鎖は壊さない。「まとめを適用した状態」もルートからの畳み込みで再現できること。
2. **LLM 由来も手動修正も同じイベント** — まとめは LLM に生成させた後、作者が
   手で直せる(既存の EventsEditor と同じ編集体験)。
3. **まとめは自動では変わらない(凍結)** — 章内を編集してもまとめは自動更新しない。
   まとめに「要更新」バッジを出し、**作者が更新して内容が実際に変わったときだけ**下流へ波及する。
   これが stale 遮断の本体。

## 3. データモデル

> **2026-08-01 一般化**: 当初「章 = 正史パス上の連続区間」としていたが、結末ノード方式の
> 導入で正史は「選択中のルート」に過ぎなくなったため、**章 = 親子で一続きにつながった
> シーンの列(正史・分岐・島のどこでも可)**に緩めた(ユーザー要望)。`on_canon` で
> 区別し、正史依存で残るのは並べ替えと鑑賞モードの見出しだけ。島の章は章ビューに
> 「別ルートの章」の破線カードとして出る。以下の記述の「正史パス上の連続区間」は
> この一般化を踏まえて読むこと。

### groups テーブル + nodes.group_id

```sql
CREATE TABLE groups(
  id TEXT PRIMARY KEY,
  title TEXT NOT NULL,            -- 章タイトル(鑑賞モードの見出しにも使う)
  color TEXT,                     -- 構造モードの枠の色(NULL = 既定)
  digest_events TEXT,             -- 章じまいのまとめ(イベント配列 JSON。NULL = 未作成)
  digest_stale INTEGER DEFAULT 0, -- 章内が編集されてまとめが古い(要更新バッジ)
  created_at TEXT
);
-- nodes には冪等 ALTER で追加
ALTER TABLE nodes ADD COLUMN group_id TEXT;  -- NULL = どの章にも属さない
```

> **2026-08-02 変更(§9 Step 1)**: 章は「メンバーシップ(ラベル)」と
> 「ルート(読む道)」の 2 層になった。以下の 3 点は当初案で、いまは無効:
> ~~章 = 正史パス上の連続区間~~ / ~~分岐は group_id を付けず表示上だけ章に属す~~ /
> ~~島には章を付けない~~。

- **メンバーは `nodes.group_id` のラベルで、一続きである必要はない**。章の中の分岐も、
  まだどこにも繋いでいない島も入れられる(「章の中で書いたものは章のもの」)。
  章の順序は正史パス順から導出できるので position 列は持たない。
- **ルート(読む道)は `list_groups` が導出する**: メンバーのうち正史パスに乗っている
  もの(正史順)。1 つも無ければメンバーの中の一続き(島の章)。鑑賞モード /
  まとめの適用点 / 並べ替え / 章カードのピンは**ルート**を、章パネル / 一括操作 /
  章カードへの畳み込みは**メンバー**を見る。
- ルートが正史の上で分断されている(間に別の章・未分類のシーンが挟まる)ときだけ
  **⚠ 要確認バッジ**。島や分岐がメンバーに居ることは異常ではないので警告しない。
- 章の入れ子(部・章・節)は**やらない**。1 階層のみ。

### まとめ(digest)を groups 側に持つ理由

まとめの置き場所は 3 案を比較した:

| 案 | 内容 | 問題 |
|---|---|---|
| A. 章末尾に専用の「章じまいノード」を挟む | canon_path に混ざり、清書対象・シーン数・スライディングウィンドウに影響。各所に除外処理が要る | 却下 |
| B. **groups.digest_events(採用)** | ノードの events と独立。「イベント作り直し」(replace_events)で消えない。fold には「章末尾ノードの適用後に digest を適用」のフックを 1 箇所足すだけ | fold の入力が nodes 外に増える(input_hash に digest のハッシュを混ぜて整合を取る) |
| C. 章末尾ノードの events に混ぜる | そのノードで「イベント作り直し」をすると消える。抽出結果とまとめが同じ配列に同居して紛らわしい | 却下 |

### まとめの中身は memory_compress を主役にする

- まとめの実体は既存イベント型で表現する: **`memory_compress`**(章内の各キャラの記憶
  → キャラごと 1〜数件の要約記憶に**置換**)+ 必要なら `fact_set`(世界・キャラの要約的な事実)。
  分量は**キャラごと 1〜3 件・1 件あたり 2〜4 文**を既定にし、件数は章の規模
  (シーン数)で決める(2026-08-02 変更。ユーザー要望「もう少し長くてもいい」。
  従来は「キャラごと 1 件・1〜3 文」で、章の記憶のすべてを代表するには短すぎた)。
  **焦点ごとに項目を分ける**のは検索のため — まとめは `memories` 行になって
  ハイブリッド検索に乗るので、長い 1 段落より焦点の違う 2〜3 件のほうが想起が効く。
  同じキャラの項目にはどれにも同じ `replaces` を持たせる(fold は 1 件目で生の記憶を
  落として自分を積み、2 件目以降は追加だけ。あとで 1 件消しても生の記憶が復活しない)。
  新イベント型は増やさない。fold の適用ロジックがそのまま使える。
- **置換(replaces)であることが重要**: 下流の状態は章内の生の記憶に依存しなくなり、
  まとめが変わらない限り「記憶の観点では」下流の状態が変わらない。
- facts / relationships(関係値)は生のまま下流へ流す。これらは積算値・キーバリューで
  既に「まとめ」的であり、章内でこれらを変える編集は物語の状態変更そのものなので、
  下流へ波及するのが正しい。**要約(まとめ)の対象は記憶に絞る。**
- Phase 6 予定だった「memory_compress の自動要約圧縮」は、この「章じまい」を
  実行タイミングとして実装する(独立機能としては作らない)。

前提として先に潰すもの: **イベント ID が置換のたびに再発行される既知課題**
(progress.md「レビューで見送った既知の課題」)。`memory_compress.replaces` が
イベント ID 参照のため、再抽出で ID が変わると置換対象が宙に浮く。
digest 導入前に `EventIn` への id 引き継ぎを入れる。

## 4. fold と stale 遮断

### fold のフック

`store.get_state()` のパス畳み込みで、ノード n が**章の末尾**(その章に属す正史パス上の
最後のノード)なら、n のイベント適用後に `groups.digest_events` を続けて適用する。
`input_hash` の計算には digest のハッシュを混ぜる(digest が変われば下流は再 fold される。
逆に digest が同じなら記憶まわりの入力は同じ)。

### stale 伝播の変更(2 段階)

**Step 1 — early cutoff(章がなくても効く)**: **実装済み(2026-08-01。フェーズ A)**。
`update_node` の契機を分離: 状態(fold)に効くノードフィールドは cast のみで、
title / beat / emotional_core / location / story_time はプロンプト文面のみ
→ **自ノードの清書だけ stale**(下流の状態・清書は保つ)。cast の編集は
再 fold して**状態ハッシュが変わったときだけ**下流へ波及(early cutoff。
並べ替えや登場済みキャラの追加は波及しない)。

制限: イベント編集(replace_events)は従来どおり下流まで波及する。置換のたびに
イベント ID が再発行されて状態ハッシュが必ず変わるため cutoff が効かず、また
状態は記憶を event_id 参照で持つので「文面だけの変更」をハッシュでは検出できない
(記憶の文面は memories テーブル側にあり、下流のプロンプトに効く)。
イベント編集への cutoff は、ID 引き継ぎ(フェーズ C の前提作業)とあわせて設計する。

**Step 2 — 章境界での遮断**: 章内のノードを編集したとき:

1. 同じ章の中の下流ノードは従来どおり dirty + stale
2. 章の `digest_stale = 1` を立てる(UI に「まとめが古い」バッジ)
3. **章より下流へは伝播しない**(digest は凍結されているため、下流の入力は変わっていない)
4. 作者が「まとめを更新」を実行し、新しい digest の内容が旧 digest と異なるときだけ、
   下流の章へ dirty + stale を伝播する(同一なら何も起きない = early cutoff)

注意: facts / relationships は digest を経由しない(生のまま流れる)ので、
それらに効く編集は従来どおり下流へ波及する。遮断されるのは
「記憶の増減・文面変更」と「状態に影響しない編集」。この非対称は UI の説明文で明示する。

## 5. コンテキスト構築の 2 層化

「前の章まで = 章単位の要約、いまの章 = 詳細」でプロンプトを組む。

| 対象 | 現状 | 変更 |
|---|---|---|
| シーン生成([generation.py](../../backend/generation.py)) | 全キャラ・全状態 + 直近 3 ビート + 記憶検索 top5 | 状態は fold 済みを使うので**自動的にまとめ後の記憶**になる。加えて「直近 3 ビート」を「**当章のビート全部(上限あり)+ 前章までは章タイトル 1 行ずつ**」に変えると、章のあらすじ層がプロンプトに乗る |
| 清書([rendering.py](../../backend/rendering.py)) | 直前散文の末尾 1400 字 + state(記憶末尾 8 件) | state 経由で自動的にまとめ後になる。章の先頭シーンでは「前章のあらすじ」(digest の要約記憶)を明示ブロックで渡すと接続が安定する |
| チャット([chat_agent.py](../../backend/chat_agent.py)) | get_state / search_memories | fold 済み state を読むので自動的に反映。get_beats に章情報(章タイトル・区切り)を含めると「第2章を要約して」が効くようになる |

### まとめと生データの役割分担(2026-08-01 追記)

章から下流へは**両方引き継ぐが、経路を分ける**(ユーザー確認済みの方針):

| 層 | 内容 | stale 遮断との関係 |
|---|---|---|
| **状態(fold)** | まとめ(要約記憶)+ 生の facts / 関係値 | 下流の状態はこれだけに依存。**遮断はこの経路を見る** |
| **アーカイブ** | 生の記憶(memory_compress は fold 状態から外すだけで、`memories` テーブルと events には全部残る) | 検索で引く。状態の依存関係には含めない |

清書(レンダリング)は「まとめで骨格を保ちつつ、生の詳細も使う」二段構えにする:

1. facts / 関係値はもともと生のまま届く
2. 記憶は「前章まで = まとめ、当章 = 生」が既定。ただし**記憶検索(ハイブリッド top-k)の
   対象に圧縮済みの生記憶も含める**ことで、そのシーンに関係する過去の細部
   (序盤の約束の正確な文言など)をピンポイントで注入できる
3. 直前シーンの散文末尾 1400 字(既存のスライディングウィンドウ)は生の文章そのもの

全生データを常に流すとコンテキストが肥大化して遮断も無意味になるため、
生データは**検索経由の動的注入**に限る。さらに、注入の既定を工程で使い分ける
(2026-08-01 ユーザー方針: 「作業中はまとめだけでいい」):

| 工程 | 前章までのコンテキスト | 理由 |
|---|---|---|
| **作業中**(ビート生成・編集、チャット) | **まとめだけ**(既定) | 軽く・速く。stale 遮断もフルに効く。作業のテンポを守る層 |
| **清書**(レンダリング) | まとめ + **検索で生記憶を注入**(既定オン) | 品質優先の層。清書はもともと LLM が重いので検索の追加コストは誤差 |
| チャットで細部を掘るとき | ツール(search_memories / recall)の「圧縮前も含める」オプションを明示的に使う | 必要なときだけ |

トレードオフ: 検索で注入した生記憶はプロンプトへの動的注入なので、生記憶を後から
直しても、それを引用していた下流の清書は自動では stale にならない。精密化するなら、
清書時に使った記憶 id を `renders.meta` に記録し(prompt_messages 保存の仕組みを流用。
2026-07-31 実装)、**その記憶が変わったときだけ該当清書を stale にする**個別追跡が
将来の拡張として可能。

## 6. UI

### 構造モード: 章ビュー ⇄ 章内ビューの 2 階層(2026-08-01 変更)

当初案は「同一キャンバスに全シーンを並べて章の枠を背景に描く」だったが、
基本の作業スタイルが「章の中で編集する」であることから、
**ドリルダウン型の階層表示に変更**(ユーザー決定)。
**データモデルは変えない**(章の実体ノードは作らず、真実はシーンノード + シーン間エッジ +
groups ラベルのまま。章ビューは導出された表示)。

- **章ビュー(上の階層)**: 章ノードだけが章同士のエッジでつながって並ぶ。
  - 章ノードと章間エッジは**表示のための導出**。章間のつながりは
    「章 N の末尾シーン → 章 N+1 の先頭シーン」の正史エッジから導く
  - 章ノードに出す情報: タイトル / シーン数 / 清書・stale の集計 /
    まとめ(digest)の状態バッジ(未作成・要更新・作成済み)。
    章間エッジは「まとめの受け渡し」の場所なので、**stale の管理単位と画面の単位が一致する**
  - **章カードの表紙(サムネイル)**(2026-08-01 追加。ユーザー要望): 章のシーンの挿絵を
    1 枚出す。どのシーンを使うかは `groups.cover_node_id`(NULL = 自動)に持ち、
    **指定が無ければ章の中で最初に挿絵があるシーン**を使う。挿絵の実体はシーン側の
    ままで、章は「どれを表紙にするか」だけを持つ(章専用の画像は持たない)。
    指定はシーンの右クリック「🖼 この挿絵を章の表紙にする」か章パネルのシーン一覧から。
    表紙のシーンが章から外れた・消えたときは `list_groups` が NULL に読み替えて返す
    (自動導出に戻る)。見え方はシーンカードと同じで、**切り抜かず元の比率のまま**
    (ユーザー指定。16:9 に統一する案は却下)。
    **常時アニメーション(章内の挿絵のクロスフェード)はやらない**: 章ビューは探すための
    俯瞰画面で、表紙は「いつ見ても同じ絵」であるほど章の識別子として働くため。
    中身をのぞく用途が実際に要るなら、ホバー中だけの再生として後から足す
  - 章に属さないシーン(書き始め・作り置きの島)は「未分類」領域として章ビューに出す
  - **章カードに畳むのは「章の中のシーンから生える分岐」まで**(`chapterSeq`)。
    章のメンバー + 入口 / 出口を起点に、draft かつ未分類の部分木を章カードへ写す。
    ただし**出口の子は辿らない**(2026-08-02 修正。ユーザー報告「独立シーンを作って
    章ノードをそこに繋いだら独立シーンが消えた」): 出口の先は定義上**章の外**なので、
    そこまで畳むと章の後ろに繋いだシーンが章カードに吸い込まれ、章内エッジとして
    捨てられて画面から完全に消える(データは無事なので、フラット表示には出ている)
  - ダブルクリック(または「開く」)で章の中へ
  - **章カードの位置は作者が自由に置ける**(2026-08-01 変更。ユーザー報告「章カードを
    ドラッグしても元に戻る」)。位置は `groups.pos_x/pos_y` に保存し、まだ動かして
    いない章だけ導出位置 = **先頭シーンの位置**(正史・島とも同じ)に置く。
    ⟲(整列)は**章ビューでは章カードと未分類ノードだけを並べ、章の中には触らない**
    (2026-08-02 変更。ユーザー要望「章の方で整列を押したら章の中身は無視してほしい」)。
    章カードを 1 枚のノードに畳んだ導出グラフを並べて `groups.pos_x/pos_y` に焼き付ける。
    手動配置をすべて捨てる全体リセットはフラット表示の ⟲ のまま。
    **ドラッグと並べ替えは兼ねない** —

## 9. 検討中: メンバーシップとルートの分離(章の in / out マーカー)

2026-08-01 ユーザー発案の in/out マーカー案を、2026-08-02 のユーザー指摘
「**途中で分岐しているノードや島も章の中に許容する構造**」で拡張したもの。
**未着手・未決定**(この節は設計の記録)。

### 9.1 中心の考え: 2 つの層に分ける

いまの章は「どのシーンが章のものか(メンバーシップ)」と「どう読むか(順番)」を
**同じもの = 一続きの鎖**で表している。これを分ける。

| 層 | 何で決まるか | 何に使うか |
|---|---|---|
| **メンバーシップ** | **ラベル**(`nodes.group_id`)。**鎖である必要をなくす**ので、分岐も島も入れられる | 章パネルのシーン一覧 / 一括操作 / 章カードへの畳み込み / 章ごとの移動 |
| **ルート** | **in → out の道**。`out` が繋がっている枝が「章の中の正史」 | 鑑賞モード / 清書の順番 / まとめ(digest)の適用点 |

```
        ┌─ 章「港の夜」───────────────────┐
  …→ in ─→ A ─→ B ─→ C ──→ out ─→ (次章の in)
        │         └→ B' ─→ C'   ←候補(メンバー。ルートには乗らない)
        │   ┌───┐                    ←島(メンバー。どこにも繋がっていない)
        │   │ D │
        │   └───┘
        └─────────────────────────────┘
```

**島があるので、メンバーシップを「in から out への到達可能性」で導出してはいけない**
(島は到達できない)。ラベルとして持ち続けるのが要点。ルートだけを in/out で決める。

[endings.md](endings.md) の「正史 = アクティブな結末から根への逆引き」と同型で、
それを章スコープに降ろしたもの。

### 9.2 なぜ要るか(2026-08-02 の不具合が示したこと)

同じ日に、この歪みから 2 件の不具合と 3 つの継ぎ足しが出た。分離すれば**全部要らなくなる**。

| いまの継ぎ足し | 分離後 |
|---|---|
| 章の中で作ったシーンに `group_id` を付ける処理(追加・接続の 2 経路)。`add_node_to_group` は鎖を壊さないための**隣接チェック**込み | 章の中で作ったらラベルを付けるだけ。隣接チェック不要 |
| 章のシーンから生える分岐(draft・未分類)を**章ビューでだけ章カードに畳む**規則 | 分岐が正式メンバーなので、畳む規則そのものが不要 |
| 右クリック「この章に入れる」(未分類のまま残ったシーンの拾い直し) | そもそも未分類にならない(残っても入れるだけ) |
| `list_groups` の「鎖が途切れている ⚠」 | 「**in から out へ到達できない ⚠**」という意味のある警告になる |

いちばん効くのは**説明できるようになる**こと。いまは章内ビューが「メンバー + 分岐」、
鑑賞モードの章スコープとまとめが「メンバーだけ」を見ており、
**同じ「章」なのに 2 つの意味がある**(ユーザー報告「章内ビューには見えるのに
鑑賞モードに出てこない」の正体)。分離後は「章内ビュー = メンバー」「鑑賞 = ルート」と
言い切れる。

### 9.3 そのほか効くところ

1. **章ローカルの正史切替**。いまルートを変えるには結末の切替しかなく粒度が物語全体。
   `out` の付け替えなら章の中で完結する
2. **空の章を器として先に作れる**。現状の章は既存シーンのラベルなので、メンバーが 0 に
   なると `list_groups` から消える。in/out という実体があれば「第3章を先に置いて中身は
   後で書く」ができる(プロット先行の書き方)
3. **章の付け替え・並べ替えが単純になる**。`move_group` の「連続区間のつなぎ替え」が、
   in の親と out の子の差し替えだけになる
4. **digest の適用点が実体になる**。いまは「章末尾ノードを導出してその後に適用」だが、
   `out` に適用すると言い切れる

### 9.4 決めること

- **不変条件「章の外へ出るときは必ず out を通る」**。崩れると章の境界が意味を失う。
  裏返すと、章間エッジは導出をやめて実体(out → 次章の in)にできる
- **グローバル正史との整合**。アクティブな結末からの逆引きが章を通過するときは
  「章の中では out の指すルートを通る」と定義すれば二重定義にならない。ただし
  「out は枝 B' を指しているのに結末は C の下流」という状態は作れてしまうので、
  **out の付け替え時に下流の結末も追従させる**(`make_canon` 相当)か、
  ⚠ バッジで知らせるかを決める
- **メンバーだけどルートに乗らないシーン**(島・落選した分岐)の扱い: 章パネルに
  「未接続のシーン」として並べる。**まとめ(digest)には入れない**
  (まとめはルート上の状態を要約するものなので)
- **in は要るか**。out だけでもルートは決まる(入口は逆引きで一意)。ただし
  9.3 の 2 と 3 は in があって初めて成立する。「はじまり / 結末」と対称になるので
  **両方置く**のが有力
- **1 シーンは 1 章まで**(いまと同じ)
- **既存の章の移行**。kind 導入時と同じ無停止移行(既存の章に in/out を自動生成)

### 9.5 進め方: 2 段に割る

| 当初 Step 2 に入れていたもの | 実際 |
|---|---|
| **章ローカルの正史切替**(out の付け替え) | **既存の `make_canon` がそのまま使える**。「out を別の枝へ」= 「その枝を通る道を正史にする」で、§9.4 の「out の付け替え時に下流の結末も追従させる」を選ぶなら**両者は同じ操作**になる → (a) として右クリックに出した |
| **空の章を器として先に作れる** | マーカーは要らなかった。`list_groups` が**メンバー 0 の章を捨てていた**のが理由だっただけ → (b) としてそのまま返すようにした |
| まとめの適用点を out に / 章間エッジを実体に / `move_group` の単純化 | 内部の整理で、作者から見た新しい価値は薄い。**保留** |
| 章の境界が画面上の物になる | 実体化の固有の価値。使ってみて必要と感じたら |

- **(a) 章の道の差し替え**(実装済み): 分岐のシーンを右クリック →
  **「★ この枝を章の道にする」**(章の外では「★ この道を正史にする」)。
  中身は `make_canon` で、鑑賞モードとまとめがその枝を通るようになる
- **(b) 空の章**(実装済み): `create_group(title, [])` で**器だけの章**を作れる。
  ノードエリアの右クリック「📖 空の章をここに作る」。メンバーが 0 になっても
  章は消えない(解除は明示操作のみ)。空の章の中で「＋ シーンを追加」すると
  **島として作ってその章に入れる**(物語のどこに置くかは後で決める)。
  章の中で作った島(⊕)も、その章のシーンになる

**Step 3 — マーカーの実体化(2026-08-02 着手。ユーザー判断)**

「他のツールもそうなっている」= **ノードグループの Input / Output**
(Blender のノードグループ、Unreal の Blueprint、Houdini の subnet)と同じ形にする、
という指摘で方針転換。**境界が配線できる実体になり、「out に何を繋ぐか」が
そのまま「章の道を選ぶ」操作になる**のが本質的な価値(メニュー項目とは体験が別物)。

- マーカーは**シーンと同じ `nodes` 行**(`kind = 'chapter_in' / 'chapter_out'`、
  `group_id` はその章)で、**エッジの鎖に挟み込む**:
  `… → 前章の out → in → A → B → out → 次章の in → …`。
  `canon_path()` は元から「`kind` が付いたノードは除く」ので、はじまり / 結末と
  同じ扱いでそのまま乗る(新しい除外処理がほとんど要らない)
- **空の章は「浮いた in → out のペア」**。あとで in に繋げば物語に挿し込まれる
- **Blender との違い**: あちらはグループが中身を隠すが、こちらはフラット表示で
  全部見えたまま。in/out は「隠蔽」ではなく**境界の宣言**なので、境界を意味ある
  ものにするには「章の外へ出るときは必ず out を通る」を守らせる必要がある(未実装)

**① 実体化と表示 → 実装済み(2026-08-02)**

- `ensure_group_markers` が入口 / 出口を作って鎖に挟む。`create_group` と、
  既存ライブラリ向けの `ensure_chapter_markers`(無停止移行。接続時に一度)から呼ぶ
- マーカーは**メンバーに数えない**(`node_ids` はシーンだけ)。`in_id` / `out_id` で返す
- 章の解除でマーカーを抜いて鎖を繋ぎ直す(`_splice_out_node`)。単独では消せない
- **`move_group` は `in → out` の区間ごと**動かすようになった(設計メモで予告していた単純化)
- 章の**末尾の後ろに割り込む = 出口の手前**なので、そのシーンは自動的に章の中に入る
  (マーカー導入前は未分類になっていた。`insert_node_after` の章引き継ぎがそのまま効く)
- UI: 入口 ⇥ / 出口 ↦ の小さなカード。章内ビューに表示し、章ビューでは章カードに畳む。
  **章カードのピンは in/out そのもの**になった。マーカーの右クリック操作は無し

**② 読む道を out から導出 → 実装済み(2026-08-02)**

- ルートは **`_route_from_markers`**: 出口の親から親をさかのぼり、入口で終わり。
  章のメンバーでないシーンに出たらそこで打ち切って警告(境界が破れている)
- **出口に繋ぎ替える = 章の道を選ぶ**。`attach_node` は繋ぎ先が `chapter_out` なら
  `make_canon(parent)` を呼び、**正史(アクティブな結末からの逆引き)もその道を通る**。
  ただし**その章が正史の上にあるときだけ**(2026-08-02 修正。ユーザー報告
  「島の章の中で編集したら、章の外でその章と結末が繋がっていた」)。島の章で追従させると
  `make_canon` が道の先に**新しい結末を作ってアクティブ化**するため、島が正史に化ける
- 逆向きの整合も取る: `make_canon` は**最初に** `_realign_group_out` で
  その章の出口を選んだ道の端へ繋ぎ替える。順序が要点で、あとで揃えると
  「出口が外れたままの枝の先に結末を作る」→ 章から先の物語が切り離される
- UI の「★ この枝を章の道にする」は `make_canon` ではなく
  **`POST /groups/{id}/route/{node_id}`**(`set_group_route`)を呼ぶ。
  出口の繋ぎ替えと「正史を追従させるかの判断」をサーバー側の 1 か所に集めている
- 新しい警告: 「出口に何も繋がっていません」「道が章の外のシーンを通っています」
  「道が入口まで繋がっていません」。**「正史の上で分断」は廃止**(配線で決まるため)
- 移行・マーカー設置のときだけ `_legacy_route`(正史に乗っているメンバー)を使う。
  `ensure_group_markers` が `list_groups` を呼ぶと循環する(出口が未配線なので
  常に空の道が返る)ため、位置決めはこちらで行う

**③ まとめの適用点と境界の担保 → 実装済み(2026-08-02)**

- **まとめ(digest)は章の出口で適用する**(`_digest_by_tail` / `_digest_boundary_for` /
  `_propagate_from_boundary` が out を見る)。出口を別の枝へ繋ぎ替えても、
  まとめは**章の境界に付いたまま**効く(従来は「ルートの末尾シーン」に付いていたので、
  道を差し替えると別のシーンへ移っていた)。early cutoff の比較も境界の状態で行う
- **境界の不変条件を警告にした**: 「章の外へ、出口を通らずに繋がっているシーンがあります」。
  **正史の流れ**が出口を迂回しているときだけ出す(分岐が外へ出るのは異常ではない)。
  禁止ではなく警告にしたのは「勝手に直さずバッジで知らせる」という既存方針に揃えたため
- **章間エッジは既に実体**(out → 次章の in の実エッジ)。章ビューの表示だけが
  「章の内部エッジを畳む」導出を続ける(これは表示の都合なので残す)

**③-2 入口へ繋ぐときの正規化(2026-08-02 追加)**

警告だけでは足りなかった。**フラット表示から「章の最後のシーン → 次章の入口」へ直接
ドラッグすると、出口を迂回する線が作れてしまう**(章ビューは端点を入口 / 出口に
解決するので生まれないが、その保護を通らない経路があった)。しかもこの警告は
**正史の線しか見ない**ので、作った時点では何も起きず、あとで**無関係な操作**で
正史がその線に乗った瞬間に、別の章の ⚠ と破線として現れる。ユーザーからは
「B→C を繋いだら A が壊れた」に見える(2026-08-02 ユーザー報告。実際に再現)。

対策は `attach_node` の入口での正規化(`_normalize_chapter_boundary`)。**繋ぎ元が
章のシーンで、繋ぎ先が別の章**なら、繋ぎ元を**出口に読み替える**。章ビューの
`resolveEndpoint` と同じことをサーバー側でも行い、どの経路からでも境界を保つ。

当初は「章の道の終わりから繋いだときだけ」に絞り、途中からの線は「そこから別の章へ
分岐する」正当な形として残していたが、**2026-08-02 のユーザー判断で章の途中からの線も
対象にした**(「章の途中のノードが出口以外に外とつなげられるのは不自然。そんな用途も
たぶんない」)。

**未分類のシーンへ繋ぐ場合は読み替えず、そのシーンを章に取り込む**
(`_adopt_into_group`)。`insert_node_after` は「前後が同じ章なら引き継ぐ」を持って
いたのに線を引く操作には無く、**章の道の真ん中に未分類のシーンが挟まって
「章の道が章の外のシーンを通っています」になっていた**(2026-08-02 ユーザー報告)。
章ビューはもともと未分類の draft 部分木を章カードに畳んで表示しているので、
データ側をその見え方に合わせる形になる。取り込むのは **draft かつ未分類の枝だけ**
(正史のシーンまで巻き込むと、繋ぎ直しただけで物語の残り全部が章に入ってしまう)。
**出口の先に繋いだものは取り込まない** — そこは定義上、章の外。

これで章の中の分岐(what-if)は従来どおり作れる(その章のシーンとして作られる)。

**シーンを作る側も同じ規則にした**(2026-08-02。ユーザー指摘「章の中で + シーンで作成した
ノードがなぜ未分類になっているのか」): `append_node` は**章を引き継ぐ処理を持っていなかった**。
章を割り当てていたのは UI の「何も選ばずに + シーン」の経路(`addNodeToGroup` を続けて呼ぶ)
だけで、**シーンを選んで + シーン**や生成の分岐は未分類のまま作られていた。以後
`append_node` は**章のシーンの子をその章のシーンにする**(出口の子は章の外なので継がない)。

**既存のライブラリは開いた時点で直す**(`_adopt_orphans_on_routes`。`ensure_chapter_markers`
から呼ぶ)。入口と出口のあいだに挟まっている未分類のシーンを章に取り込む。**出口から入口まで
辿り着けたときだけ**で、途中で別の章のシーンやマーカーに出たら本物の警告なので触らない。

警告の文面も変えた: 「章の道が章の外のシーンを通っています」は**「外の章に繋がっている」と
読まれてしまう**(ユーザー報告「どう見ても外の章につながっていない」)。実際は「この章に
入っていないシーンが章の道の途中にある」なので、そう書く。

**③-3 迂回は警告でなく自動修復にした(2026-08-02 変更)**

③-2 だけでは足りなかった。**章の中の分岐が別の章になっていて、その分岐が
正史になった**ときの迂回は、接続時の正規化では捕まえられない — 迂回線
(A のシーン → 寄り道章の入口)は**章を作った時点**でマーカーが挟み込まれて
できており、`attach_node` を通っていないからだ。正史が動いた瞬間に初めて
迂回が成立する。

そこで `_resync_canon` の頭で `_realign_boundaries` を回し、**正史が章の出口を
飛ばして外へ出ていたら、出口を実際の境界へ挟み直す**。

- 直すのは**マーカーの位置だけ**。入口 / 出口は `canon_path` から除かれるので
  **読み順は 1 シーンも変わらない**
- 章の道から外れたシーンは**章のメンバーのまま**残る(道に乗らない分岐として)
- 出口が章の途中に取り残されている形(道が章の外を通る)は、動かすと循環に
  なるので触らず、従来どおり `_route_from_markers` の警告に任せる
- 修正前に保存されたライブラリのために、`ensure_chapter_markers`(Store を
  開いたときと library 切替時)でも一度回す

**③ の警告を「勝手に直さずバッジで知らせる」方針から外した理由**: この ⚠ は
**操作した章とは別の章**に出るうえ、UI に直す手立てが無く、原因(どの線が
迂回なのか)も分からない。読み順を変えずに直せるなら直すほうが親切
(2026-08-02 ユーザー報告 2 件)。`_route_from_markers` の 3 つの警告は
作者の判断が要る形なので、警告のまま残す。

### 9.6 コスト

**フェーズ B・C の作り直しに近い**。§3 で「章じまいノードを挟む案 A」を却下した判断
(章の実体は作らない)をひっくり返すことになり、`create_group` / `list_groups` /
`move_group` / digest の合流点 / 章ビュー / 章内ビュー / 一括操作の対象 / 鑑賞モードが
全部影響を受ける。ただし当時と違い、**結末方式でマーカーノードの概念と除外処理は
すでに全体に入っている**ので、案 A 却下時の見積もりよりは安い。
Step 1 だけなら影響は「鎖の検証をやめる」まわりに閉じる。
