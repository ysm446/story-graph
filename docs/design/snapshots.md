# スナップショット(チェックポイント)設計

作成日時: 2026-07-30 00:45
更新日時: 2026-07-30 00:45

## 目的

undo の代わりに「時点に戻す」を提供する。危険な操作の直前に自動でライブラリ全体を
保存し、手動でも任意時点を保存できるようにする。将来の LLM 書き込みツール
(チャットからのプロット・キャラ操作)の安全網の前提でもある。

## なぜ操作単位の undo ではなくスナップショットか

- データ全体が 1 つの SQLite ファイル(`story-graph.db`、テキスト中心で数 MB)
- `VACUUM INTO` 1 文でアトミックに複製できる(WAL でも単一ファイルが出る)
- state_cache / memories は導出物で同じファイル内にあるため、ファイルごと戻せば
  整合性の心配が原理的にない
- 操作単位 undo は全書き込み API に逆操作が要る大工事。費用対効果が合わない

## 保存形式

```
<ライブラリルート>/
  story-graph.db
  snapshots/
    index.json                 … メタデータ(id / label / kind / created_at の配列)
    20260730-004512.db         … VACUUM INTO の出力(同秒衝突時は -2, -3 を付ける)
```

- kind: `auto`(操作前の自動保存)| `manual`(ユーザーの「今の状態を保存」)
- 世代管理: auto は直近 30 件まで(古いものから削除)。manual は無期限
  (ユーザーが UI から削除する)
- サイズは一覧時にファイルから読む(index には持たない)

## 自動スナップショットの契機(app.py のエンドポイント冒頭)

同じ契機の連打で埋まらないよう、契機ごとにスロットル(最短間隔)を持つ。
複数シーンの一括削除はフロントが DELETE を連打する実装なので、スロットルが
「一括操作の最初の 1 回だけ保存」として働く。

| 契機 | ラベル | 最短間隔 |
|---|---|---|
| DELETE /nodes/{id} | シーン削除の前 | 30 秒 |
| POST /nodes/{id}/make_canon | 正史切替の前 | なし(毎回) |
| PUT /nodes/{id}/events | イベント編集の前 | 10 分 |
| PATCH /nodes/{id} | シーン編集の前 | 10 分 |
| POST /nodes/{id}/detach, POST /edges | つなぎ替えの前 | 60 秒 |
| extract_events / reextract / reextract_chain | イベント作り直しの前 | 60 秒 |
| 復元の実行 | 復元の前 | なし(毎回) |

- スロットルはプロセス内メモリ((root, label) → 最終実行時刻)。sidecar の再起動でリセットされてよい
- 自動保存の失敗は操作を止めない(ログのみ)
- 位置保存・分量指定・挿絵などの装飾系、追加系(シーン追加・ブランチ生成)は対象外
  (追加は破壊しないため)

## 復元

1. 「復元の前」を自動保存(復元自体を取り消せるように)
2. `conn.commit()` → `conn.close()`(WAL はクローズ時にチェックポイントされる)
3. 残存 `-wal` / `-shm` を削除 → スナップショットを一時名でコピー → `os.replace` で差し替え
4. 再接続(`db.connect`。失敗してもファイルは差し替え済みなので finally で必ず再接続)
5. フロントは成功後に `location.reload()`(ライブラリ切替と同じ作法)

## API

- `GET /snapshots` — 一覧(新しい順。id / label / kind / created_at / size)
- `POST /snapshots` `{label?}` — 手動保存
- `POST /snapshots/{id}/restore` — 復元
- `DELETE /snapshots/{id}` — 削除
- ライブラリ未設定(root なし。テストの :memory: 等)では自動保存は no-op、API は 400

## UI

設定画面に「バックアップ」セクション:
- 「今の状態を保存」ボタン + 任意の名前入力
- 一覧(名前 / 自動・手動バッジ / 日時 / サイズ)と各行の「復元」「削除」
- 復元は確認ダイアログ(「現在の状態は『復元の前』として自動保存されます」)→ 成功で reload

## 制限・既知の注意

- **画像・動画(assets/)は DB の外**なので snapshots には含まれない。参照切れを防ぐため、
  `gc_assets` はスナップショット DB が参照するファイルも回収対象から除外する
- SSE ストリーム(清書・再抽出)進行中の復元は、ストリーム側の書き込みが
  復元後の DB に混ざり得る(ライブラリ切替と同じ既知の課題。progress.md 参照)
- スナップショットはライブラリごと。ライブラリを跨ぐ操作はない
