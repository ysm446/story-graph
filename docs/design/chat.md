# 相談チャット設計

作成日時: 2026-07-25 22:52
更新日時: 2026-07-25 23:30

物語について作者が相談する「相談チャット」の設計まとめ。仕様の出発点は
[docs/story-graph-spec.md](../story-graph-spec.md) §8、実装は `backend/chat_agent.py` と
`src/renderer/src/ChatDrawer.tsx`。システムプロンプト全体の位置づけは
[system-prompts.md](system-prompts.md) の一覧も参照。

## 1. 役割と原則

- **書き換えない。** チャットは物語の状態(ノード / イベント / 状態キャッシュ)を直接変更しない。
  変更が起きるのは、提案カードを作者が「⑂ ブランチとして挿入」したときだけ。
- **推測させず、確認させる。** 事実は必ずツール経由で取らせる(下記 §3)。
- **ネタバレを作らない。** アンカーより先の情報はモデルに渡さない(§2)。
- 立ち位置は「編集者との雑談」。判断は作者が行い、チャットは観察と選択肢を出す。

## 2. アンカーとスコープ

チャットは作成時に **アンカーノード**(その時点の選択ノード、無ければ正史の末尾)を固定して保存する。

| スコープ | 見える範囲 | 用途 |
|---|---|---|
| `upto`(既定) | アンカーまでのパス(`store.path_to(anchor)`) | 執筆中の相談。先の展開を知らない相手として使える |
| `all` | 正史全体(`store.canon_path()`) | 全体を俯瞰した診断。作者が明示的に切り替えたときのみ |

分岐上のノードをアンカーにすると、そのブランチのパスが見える範囲になる(分岐点までは正史と共有)。
スコープはチャット単位で `chats` テーブルに保存され、履歴を読み込むと復元される。

## 3. ツール(tool calling)

`backend/chat_agent.py` `build_tools()`。ループは news-picker 方式で `MAX_TOOL_STEPS = 8`、
上限に達したら打ち切らず「これ以上ツールは使えません」を渡してまとめさせる。温度 0.7。

| ツール | 内容 | 副作用 |
|---|---|---|
| `get_beats(from_index, to_index)` | 見えている範囲のシーン一覧(index は 1 始まり) | なし |
| `get_state(char_id?)` | fold 済みの状態(キャラの facts / 関係値 / 記憶参照、世界の facts) | なし |
| `search_memories(query, char_id?)` | 記憶のハイブリッド検索(意味 + キーワード、top 8) | なし |
| `propose_beats(proposals)` | この先の展開を最大 3 案、シーン下書きとして提出 | なし(UI に提案カードを出すだけ) |

`propose_beats` の結果は UI で提案カードになり、「⑂ ブランチとして挿入」でアンカーの子として
`draft` ノードが作られる(ここだけが唯一の書き込み経路)。挿入済みの案はボタンが無効化される。

ツール呼び出しは SSE で流れてくるので、UI 側は「🔧 get_state を確認中…」のような行として表示する。

## 4. UI 構成(`ChatDrawer.tsx`)

- 構造モードの**下段の分割ペイン**。開閉は左下の 💬 丸ボタン、境界のドラッグで高さ変更
  (ノードエリアは 160px 以上残す)。開閉と高さは `StructureMode` が持ち、`ChatDrawer` は
  `open` / `onClose` を受ける制御コンポーネント。高さが変わるときは React Flow のビューポートを
  差分の半分だけ動かし、ノードがチャットの裏に隠れないようにしている。
- ヘッダー行: アンカー表示 / スコープ切替 / `+ 新規` / 履歴プルダウン / 削除 / 全クリア / ✕ 閉じる。
- 本文: ユーザー吹き出し(右)、回答(左、Markdown 描画 + ストリーミング)、ツール行、提案カード。
- 入力行: 候補チップ(右寄せの縦積み)/ テキストエリア(Enter 送信 / Shift+Enter 改行)/ ⟳(候補の入れ替え)/ 送信。

## 5. 定型質問

`ChatDrawer.tsx` の `TEMPLATES` 定数。読み取り 3 ツールと `propose_beats` が一通り使われ、
「要約 → 状態 → 関係の変化 → 未回収 → 矛盾 → 提案」という相談の自然な進み方に沿う 6 件を選んだ。

| ラベル | 本文 | 主に使われるツール |
|---|---|---|
| 流れを要約 | ここまでの流れを3行で要約して。 | `get_beats` |
| 状態を要約 | 現在の各キャラの状態(facts と関係)を要約して。 | `get_state` |
| 関係の変化 | 関係値が大きく動いたところと、その理由を挙げて。 | `get_state` + `get_beats` |
| 未回収の伏線 | 未回収の伏線・約束・謎を洗い出して。 | `search_memories` |
| 矛盾チェック | キャラの言動と facts に矛盾がないか点検して。 | `get_state` + `get_beats` |
| 展開を提案 | この先の展開を3案提案して。 | `propose_beats` |

置き方の決定(`video-content-analyzer` の `qa-suggest-chip` を参考にした):

- **入力欄のすぐ上に常時表示**し、**右寄せで縦に積む**(ピル型、`chip-in` のフェードイン)。
  参考実装と同じ形。会話中も候補が視界にあるので、次の一手を思いつかないときに拾える。
- **クリックで即送信**(入力欄を経由しない)。候補はそれ単体で成立する文にしてある。
  条件を足したいときは文をタイプするか、送信後に追加で指示する。
- **同時に見せるのは 3 件**(`TEMPLATE_WINDOW`)。6 件すべて積むと 200px 近く縦を食い、
  高さ 440px の既定ペインでは会話が見えなくなる。送信ボタンの隣の **⟳** で次の 3 件に送る。
- **ランダム入れ替えはしない。** 候補が勝手に動くと「さっきの質問」を探す手間が増え、
  手が場所を覚えられない。⟳ は決まった順の巡回(offset += 3 の剰余)。
- 生成中(`busy`)はチップを無効化する。

## 5.1 内容から作る質問候補(オプション)

固定の候補に加えて、**物語の内容から質問を LLM に作らせる**(参考実装の
`POST /review/questions` に相当)。設定「相談チャット → 内容から質問候補を作る」で オン/オフ、
既定はオン。設定キーは `chat_dynamic_suggestions`(`'0'` でオフ)。

- API: `POST /chat/suggest_questions` `{chat_id, anchor_node, scope}` → `{questions: [...]}`。
  実装は `chat_agent.suggest_questions`。**ツールは使わせない**軽量な 1 回の呼び出しで、
  見えている範囲の末尾 12 シーン(タイトル + 冒頭 120 字)と、チャットがあれば直近 2 往復を渡す。
  出力は JSON schema(`questions`: 最大 3 件、各 6〜60 字)、温度 0.9。
- プロンプトの要点: 「作者が相談相手に投げる文」「固有名詞を使い、この物語にしか当てはまらない内容」
  「一般論や既に答えの出た質問は避ける」「3 件は違う切り口(内面 / 関係 / 未回収 / 次の展開)」。
- **失敗しても何も起きない設計。** 設定オフ・LLM 未起動(`llm.health` が偽)・生成エラーはすべて
  `{questions: []}` を返し、UI は固定の候補のまま。llama-server の自動起動もしない
  (`ensure_running` を呼ばない = 候補生成のためにモデルをロードしない)。
- 呼ぶタイミング: チャットを開いたとき / `+ 新規` / 履歴の読み込み / **回答が終わった直後**
  (会話を踏まえたフォローアップに差し替わる)。
- 表示: 3 枠のうち**下段(入力欄側)最大 2 件**を生成された質問に使い、上段は固定の候補を残す。
  生成分は **✨ 付き + アクセント色の枠**で区別する。固定の候補が消えないので、
  生成に失敗しても・オフでも操作の入り口は変わらない。

実測(12B, 既定ライブラリ)では「たかしが書類を忘れたのは、単なる不注意か、何か意図的な理由があるか
相談したい」のように固有名詞入りの質問が出る。作品ごとに違う質問が並ぶのが狙い。

## 5.2 将来の拡張

- 設定画面から固定の候補を編集・追加できるようにする(現状はコード内の定数)。
  キャラ名を埋める `{char}` のようなプレースホルダも検討候補。
- 生成された質問のキャッシュ(現状は毎回生成。同じアンカーで開き直すと作り直す)。

## 6. 保存

`chats` テーブルに LLM のメッセージ形式(`tool_calls` 含む)そのままで保存し、アンカーとスコープを
併記する。履歴プルダウンは「アンカーのタイトル: 冒頭の抜粋」で一覧表示。読み込むと表示用の
`DisplayItem` に組み直す(ツールへの内部指示メッセージは表示から除外)。

## 7. 今後の検討事項

- 定型質問のユーザー編集(設定画面)。
- チャットからの書き込み経路を増やすか(例: イベント案の提案 → 確認して適用)。現状は提案カードのみ。
- 長い履歴の圧縮(Phase 6 の `memory_compress` と同様の要約圧縮をチャット履歴にも入れるか)。
- 複数キャラ視点の「誰が何を知っているか」を専用ツールにするか(今は `get_state` で代替)。
