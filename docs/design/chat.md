# 相談チャット設計

作成日時: 2026-07-25 22:52
更新日時: 2026-10-04 02:54

物語について作者が相談する「相談チャット」の設計まとめ。仕様の出発点は
[docs/story-graph-spec.md](../story-graph-spec.md) §8、実装は `backend/chat_agent.py` と
`src/renderer/src/ChatDrawer.tsx`。システムプロンプト全体の位置づけは
[system-prompts.md](system-prompts.md) の一覧も参照。

## 1. 役割と原則

- **書き換えない。** チャットは物語の状態(ノード / イベント / 状態キャッシュ)を直接変更しない。
  展開の提案も通常の文章で返す。案数は固定せず、作者が指定した場合はその数に従う。
- **推測させず、確認させる。** 事実は必ずツール経由で取らせる(下記 §3)。
- **ネタバレを作らない。** アンカーより先の情報はモデルに渡さない(§2)。
- 立ち位置は「編集者との雑談」。判断は作者が行い、チャットは観察と選択肢を出す。

## 2. アンカーとスコープ

チャットは作成時に **アンカーノード**(その時点の選択ノード、無ければ正史の末尾)を固定して保存する。

**固定されるのは「会話が始まったとき」**(最初の発言を送って `chats` に保存された時点)。
それまではヘッダーのアンカー表示は構造モードの選択に追従する(2026-08-01 修正。
以前は `+ 新しい会話` や相手の切替の時点でアンカーを埋めていたため、
会話を始める前にシーンを選び直しても表示が変わらなかった)。
追従している間は、**選択が落ち着いてから(400ms)コンテキスト使用量リングも取り直す**。
`/chat/token_usage` は「見える範囲の fold + llama-server の `/tokenize`」を通るので、
1 選択 1 リクエストにはしない(矢印キーでシーンを渡り歩く間ずっと叩かないため)。
応答は追い越しがあるので、最後に投げた分だけを採用する。

**章カードを選んでいるときのアンカー候補は「その章の末尾シーン」**
(章カードはシーンではないので選択が空になり、そのままでは正史の末尾に落ちてしまう。
ヘッダーの「アンカー: ○○ まで」= その章の終わりまで、と読める)。

| スコープ | 見える範囲 | 用途 |
|---|---|---|
| `upto`(既定) | アンカーまでのパス(`store.path_to(anchor)`) | 執筆中の相談。先の展開を知らない相手として使える |
| `all` | 正史全体(`store.canon_path()`) | 全体を俯瞰した診断。作者が明示的に切り替えたときのみ |

分岐上のノードをアンカーにすると、そのブランチのパスが見える範囲になる(分岐点までは正史と共有)。
スコープはチャット単位で `chats` テーブルに保存され、履歴を読み込むと復元される。

## 3. ツール(tool calling)

`backend/chat_agent.py` `build_tools()`。ループは news-picker 方式で `MAX_TOOL_STEPS = 8`、
上限に達したら打ち切らず「これ以上ツールは使えません」を渡してまとめさせる。温度 0.7。

| ツール | 内容 | 副作用 |
|---|---|---|
| `get_beats(from_index, to_index)` | 見えている範囲のシーン一覧(index は 1 始まり) | なし |
| `get_state(char_id?)` | fold 済みの状態(キャラの facts / 関係値 / 記憶、世界の facts) | なし |
| `search_memories(query, char_id?)` | 記憶のハイブリッド検索(意味 + キーワード、top 8) | なし |

**`get_state` は生の state をそのまま返さない**(2026-08-03)。fold の state は記憶と関係の理由を
`event_id`、キャラと勢力を ID で持つので、素通しにするとツール結果が ID の羅列になる。LLM 側に
ID から本文を引く手段は無い(`search_memories` はクエリ検索)ため、記憶は「何件あるか」しか
伝わっていなかった。そこで `_char_state_view` で次の形に解決してから返す。

- キャラと関係の相手に `name` を付ける(勢力もシステムプロンプトの ID 一覧に無いので同様に解決)。
  キーは ID のまま残す — `get_state` / `search_memories` の `char_id` で LLM が ID を使うため。
- `memories` は本文に解決する。選び方はキャラモードと同じ `_select_memories`(重要 + 直近)。
  全体 state では 1 キャラあたり `STATE_OVERVIEW_MEMORIES = 5` 件ずつに絞り、残りは `omitted` で
  件数だけ伝える。`char_id` を指定したときは絞らない(`CHARACTER_MEMORY_LIMIT` まで)。
- 関係の `reasons`(`event_id` の配列)は落とし、更新回数 `updates` だけ残す。

展開提案用のツールとカード・挿入ボタンは 2026-10-03 に削除した。必要な事実を読み取りツールで確認し、
提案は本文の Markdown で返す。旧 `propose_beats` の保存済み履歴は、タイトル・本文・感情の核を文章として表示する。

ツール呼び出しは SSE で流れてくるので、UI 側は「🔧 get_state を確認中…」のような行として表示する。

## 4. UI 構成(`ChatDrawer.tsx`)

- 構造モードの**下段の分割ペイン**。開閉は左下の 💬 丸ボタン、境界のドラッグで高さ変更
  (ノードエリアは 160px 以上残す)。開閉と高さは `StructureMode` が持ち、`ChatDrawer` は
  `open` / `onClose` を受ける制御コンポーネント。高さが変わるときは React Flow のビューポートを
  差分の半分だけ動かし、ノードがチャットの裏に隠れないようにしている。
- **左サイドバー(幅 208px)**: これまでの会話一覧(更新の新しい順)。上部に `+ 新しい会話`、
  各項目は「見出し + アンカー名」の 2 行で、キャラチャットは 🎭 付き。表示中の会話はアクセント色。
  項目ホバーで **⋯ メニュー**(名前を変更 / 削除)。見出しは `chats.title`、未設定なら冒頭の発言 →
  アンカー名の順でフォールバック。名前の変更はインラインの入力欄(Enter 確定 / Escape 取消 /
  空で既定に戻す)。会話ごとに操作できるので「全クリア」は廃止した。
- ヘッダー行: 相手セレクタ / アンカー表示 / スコープ(またはインタビュー・劇中会話)切替 / 声 オン・オフ
  (読み上げ中は ■ 停止)/ ✕ 閉じる。返事の読み上げは [voice.md](voice.md) §6.1。
- 本文: ユーザー吹き出し(右)、回答(左、Markdown 描画 + ストリーミング)、ツール行。
  回答の下に**生成統計**の 1 行(lm-chat の qa-meta と同じ並び):
  `⚡ 38.3 tok/sec · 💬 10 tokens · 🕐 0.26s · Finish reason: stop`。ツールを使った返事は
  `🔧 N ステップ` も出す(ステップをまたいだトークン数と時間の合計を表示している)。
  出所は llama-server の最終チャンクの `timings`(無ければ `usage`)で、`llm._extract_stats` が
  読み取る。取れなかった項目は表示しない。統計は保存時に assistant メッセージの `meta` に
  入れるので履歴を読み直しても残る(**LLM に送るメッセージからは除外**する)。
- **メッセージのホバー操作**(lm-chat の `msg-action-btn` を移植。14px の線画アイコン):
  発言(右)に **✎ 編集 / ⟳ 再生成 / 🗑 削除**、返事(左)に **🔊 声で読む / 📄 送信内容 / 🗑 削除**。
  生成中は 🔊 と 🗑 を出さない。
  - 送信内容: その返事の生成時に **LLM へ実際に送った内容**(システムプロンプト + それまでの
    履歴 + ツール結果)を、設定画面「プロンプトログ」と同じ role ごとの形式のモーダルで表示する。
    生成時に assistant メッセージの `prompt_messages` に送信 messages の控えを丸ごと保存しており
    (相談・キャラ会話とも)、**LLM に送るメッセージからは `meta` / `ts` と同様に除外**する
    (控え自身は入れ子にならない)。返事ごとに全文を積むのでデータは嵩むが、途中の往復を後から
    削除しても当時の記録が正確に残ることを優先した(ユーザー決定)。控えの無い古い履歴では
    アイコンを出さない。
  - 編集: その場が入力欄になり、「送り直す」でその往復以降を作り直す(Escape で取消)。
  - 再生成: 同じ発言のまま返事だけ作り直す。どちらも `POST /chat/send` の `replace_from`
    (= その user 発言の位置)で履歴を巻き戻してから送る。
  - 削除: `DELETE /chats/{id}/turn/{index}`。`keep_user=true` なら返事だけ消して発言を残す
    (= 再生成の下準備)。ツール行もその往復の一部として一緒に消える。
  - 位置(`turn`)は保存済み `messages` の添字。ストリーミング中に積んだ項目は位置が未確定
    なので、往復が終わるたびに `syncItems` で保存済み履歴から組み直して揃える。
- 入力行: 候補チップ(右寄せの縦積み)/ テキストエリア(Enter 送信 / Shift+Enter 改行)/
  コンテキスト使用量リング / ⟳(候補の入れ替え)/ 送信。

## 5. 定型質問

`ChatDrawer.tsx` の `TEMPLATES` 定数。読み取り 3 ツールによる確認と文章での提案を含み、
「要約 → 状態 → 関係の変化 → 未回収 → 矛盾 → 提案」という相談の自然な進み方に沿う 6 件を選んだ。

| ラベル | 本文 | 主に使われるツール |
|---|---|---|
| 流れを要約 | ここまでの流れを3行で要約して。 | `get_beats` |
| 状態を要約 | 現在の各キャラの状態(facts と関係)を要約して。 | `get_state` |
| 関係の変化 | 関係値が大きく動いたところと、その理由を挙げて。 | `get_state` + `get_beats` |
| 未回収の伏線 | 未回収の伏線・約束・謎を洗い出して。 | `search_memories` |
| 矛盾チェック | キャラの言動と facts に矛盾がないか点検して。 | `get_state` + `get_beats` |
| 展開を提案 | この先の展開を提案して。 | 必要に応じて読み取りツールで確認し、文章で回答 |

置き方の決定(`video-content-analyzer` の `qa-suggest-chip` を参考にした):

- **入力欄のすぐ上に常時表示**し、**右寄せで縦に積む**(ピル型、`chip-in` のフェードイン)。
  参考実装と同じ形。会話中も候補が視界にあるので、次の一手を思いつかないときに拾える。
- **クリックで即送信**(入力欄を経由しない)。候補はそれ単体で成立する文にしてある。
  条件を足したいときは文をタイプするか、送信後に追加で指示する。
- **同時に見せるのは 3 件**(`TEMPLATE_WINDOW`)。6 件すべて積むと 200px 近く縦を食い、
  高さ 440px の既定ペインでは会話が見えなくなる。送信ボタンの隣の **⟳** で次の 3 件に送る。
- **ランダム入れ替えはしない。** 候補が勝手に動くと「さっきの質問」を探す手間が増え、
  手が場所を覚えられない。⟳ は決まった順の巡回(offset += 3 の剰余)。
- 生成中(`busy`)はチップを無効化する。

## 5.1 内容から作る質問候補(オプション)

固定の候補に加えて、**物語の内容から質問を LLM に作らせる**(参考実装の
`POST /review/questions` に相当)。設定「相談チャット → 内容から質問候補を作る」で オン/オフ、
既定はオン。設定キーは `chat_dynamic_suggestions`(`'0'` でオフ)。

- API: `POST /chat/suggest_questions` `{chat_id, anchor_node, scope}` → `{questions: [...]}`。
  実装は `chat_agent.suggest_questions`。**ツールは使わせない**軽量な 1 回の呼び出しで、
  見えている範囲の末尾 12 シーン(タイトル + 冒頭 120 字)と、チャットがあれば直近 2 往復を渡す。
  出力は JSON schema(`questions`: 最大 3 件、各 6〜60 字)、温度 0.9。
- プロンプトの要点: 「作者が相談相手に投げる文」「固有名詞を使い、この物語にしか当てはまらない内容」
  「一般論や既に答えの出た質問は避ける」「3 件は違う切り口(内面 / 関係 / 未回収 / 次の展開)」。
- **失敗しても何も起きない設計。** 設定オフ・LLM 未起動(`llm.health` が偽)・生成エラーはすべて
  `{questions: []}` を返し、UI は固定の候補のまま。llama-server の自動起動もしない
  (`ensure_running` を呼ばない = 候補生成のためにモデルをロードしない)。
- 呼ぶタイミング: チャットを開いたとき / `+ 新規` / 履歴の読み込み / **回答が終わった直後**
  (会話を踏まえたフォローアップに差し替わる)。
- 表示: 3 枠のうち**下段(入力欄側)最大 2 件**を生成された質問に使い、上段は固定の候補を残す。
  生成分は **✨ 付き + アクセント色の枠**で区別する。固定の候補が消えないので、
  生成に失敗しても・オフでも操作の入り口は変わらない。

実測(12B, 既定ライブラリ)では「たかしが書類を忘れたのは、単なる不注意か、何か意図的な理由があるか
相談したい」のように固有名詞入りの質問が出る。作品ごとに違う質問が並ぶのが狙い。

## 5.2 コンテキスト使用量のリング

「あと何往復くらい話せるか」の目安として、入力欄の右に**ドーナツ型のリング + パーセント**を出す
(lm-chat の `token-ring` を移植)。

- API: `POST /chat/token_usage` → `{token_count, ctx_size, estimated}`。実装は
  `chat_agent.token_usage`。**次のターンで送られる内容**を連結して数える:
  システムプロンプト + ツール定義(`build_tools` の JSON)+ 保存済み履歴(発言 / `tool_calls` /
  ツール結果)。トークン数は llama-server の `/tokenize`(`llm.count_tokens`)。
- `ctx_size` は設定「推論パラメータ → Context Length」の `llm_ctx_size`(= llama-server の
  `--ctx-size`)。相談チャット専用のコンテキスト設定はなく、全用途でこの窓を共有する。
- サーバー未起動時は `len(text) // 2` の概算に落として `estimated: true` を返し、UI は `≈` を付ける
  (lm-chat と同じフォールバック)。
- 色は 70% で警告(オレンジ)、90% で危険(赤)、それ未満はアクセント色。ホバーで
  会話トークン / 上限 / 使用中・残りを表示。
- 更新タイミングは質問候補と同じ(開いたとき / `+ 新規` / 履歴読み込み / 回答直後)。
- 注意: 相談チャットは 1 ターンの中でツール結果を積みながら最大 8 ステップ回すので、**ターン中の
  瞬間値はリングの表示より大きくなる**。リングは「次のターンの開始時点」の目安。

## 6. キャラクターと話す(キャラモード)

相談チャット(編集者視点)とは別に、**アンカー時点のキャラクター本人**と話すモード。
「シーン12時点のアヤ」と「シーン30時点のアヤ」は、渡す state が違うだけで別人格として立ち上がる。
fold 済みの facts / 関係 / 記憶をそのまま人格の材料に使う。

### 6.1 相談チャットとの違い

| | 相談チャット | キャラと話す |
|---|---|---|
| 視点 | 編集者(アンカーまでの全シーンが見える) | キャラ本人(自分の記憶・facts のみ) |
| システムプロンプト | 固定(`build_system`) | `build_character_system`: プロフィール + アンカー時点の facts / 関係(言語化) / 重要記憶 |
| ツール | get_beats / get_state / search_memories | `recall`(自分の記憶の検索)のみ |
| スコープ | upto / all | 常に upto(未来を知るキャラは成立しない。UI でトグル非表示) |
| 出力 | 観察と提案 | 一人称、キャラの声(voice)。メタ情報禁止 |

**シーン一覧(get_beats)は渡さない。** 居合わせていない場面を含むため。キャラの知識は
記憶システム経由のみ — これが「なぜそれを知ってるの?」という**設定の矛盾検出器**としても働く。
会話して違和感があれば、記憶や facts のデータが足りない・間違っているサイン。

### 6.2 会話の枠組み(mode)

- **interview(既定)**: 作者がキャラにインタビューする。「あのときどう思った?」に安定して答える。
  執筆の役に立ちやすい形。
- **roleplay(トグル)**: 劇中の一場面として、ユーザーを「見知らぬ相手」とした会話。没入感は上だが、
  会話自体は「起きていない出来事」なので、システムプロンプトで物語には含まれないことを明示する。

プロンプト上の差は数行(相手が作者か劇中人物か)。どちらも知識境界のルールは同一:
- facts / 記憶にあることだけを知っている。知らないことを聞かれたら「知らない」と答える
- 大きな新事実を発明しない(小さな脚色・言い回しは可)
- 未来(アンカーより先)は存在しない

### 6.3 実装

- DB: `chats` に冪等 ALTER で `char_id TEXT` / `mode TEXT` を追加。`char_id IS NULL` = 相談チャット。
  `mode` は 'interview' | 'roleplay'(キャラチャットのみ)。
- `build_character_system`: キャラ行(name / profile / appearance / voice)+ state の facts +
  relationships(相手名を解決し、score を「好意的/敵対的」などに言語化 + label)+
  記憶(合計 15 件を本文へ、残りは recall ツールで。選び方は §6.4)。
- `recall` ツール: `_tool_search_memories` を char_id 固定で呼ぶだけ。
- アイコン: `CharAvatar`(`characters.portrait_path` を `assetUrl` で表示、無い場合は
  キャラ色 + 頭文字の丸で代替)。ヘッダーの相手セレクタ横(20px)、回答バブルの左
  (56px、ストリーミング中も表示)、会話前の空状態(56px)に出す。
- 質問候補: 固定テンプレはキャラ用の別セット(「いま一番気がかりなことは?」など)。
  内容ベースの生成(§5.1)は相談モードのみ。展開提案用のカードはどちらのモードにも無い。
- コンテキストリング(§5.2)はキャラモードでも同様に動く(システム + recall 定義 + 履歴)。

### 6.4 本文に載せる記憶の選び方(2026-08-02)

キャラの記憶は fold 済み state の全件が候補だが、システムプロンプトに直接書けるのは
`CHARACTER_MEMORY_LIMIT = 15` 件。**内訳は「直近 5 件(`CHARACTER_RECENT_SLOTS`)を
先に確保 → 残り 10 件を重要度で埋める」**(`_select_memories`)。15 件以下なら分けずに
1 節で古い順に出す。

重要度だけで上位 15 件を取っていた頃は、**少し前の出来事を本人が「知らない」と答える**
問題があった(2026-08-02 ユーザー報告)。原因は 2 つ:

1. **プロンプト側に新しさの概念が無かった**。`retrieval.py` は `story_order` の半減期減衰
   (20 ビート)を持っているのに、本文の選抜は `ORDER BY importance DESC` だけ。
   記憶が N 件あるとカバー率は 15/N なので、長くなるほど悪化する
2. **章のまとめ(digest)の要約記憶は importance が高め**(既定 0.6。`generation.py`)。
   章を重ねるほどまとめが上位を占め、当章の生の記憶を押し出していた

並び順は retrieval に合わせ、分岐ノード上の記憶(`story_order < 0`)は「いま」扱いで最新側に置く。

あわせて**厳守ルールも直した**。従来の「上に書かれた記憶にあることだけを知っています。
それ以外を聞かれたら知らないと答える」は、**recall を呼ぶ前に打ち切らせる指示**になっていた
(本文は全記憶の一部でしかないのに)。現在は「まず recall で思い出そうとする →
それでも出てこなければ知らないと答える」の順にしている。

## 7. 保存

`chats` テーブルに LLM のメッセージ形式(`tool_calls` 含む)そのままで保存し、アンカー / スコープ /
`char_id` / `mode` / `title` を併記する。読み込むと表示用の `DisplayItem` に組み直す
(ツールへの内部指示メッセージは表示から除外)。

- 一覧(`GET /chats`)は更新の新しい順。各行に `title` と `snippet`(冒頭のユーザー発言 60 字)、
  `anchor_title`、`char_name` を返すので、サイドバーはこれだけで描ける。
- 会話名の変更は `PATCH /chats/{id}` `{title}`。空文字は NULL に戻す(= 既定の見出しに戻る)。
- 削除は `DELETE /chats/{id}`。表示中の会話を削除したら新規状態に戻す。

## 8. キャラ同士の会話室(mode='room')(2026-10-03 実験導入)

複数のキャラを同じ場に置いて会話させ、**作者は会話に参加せず、演出家として指示だけ出す**。
目的は**記憶と関係性の点検**: 片方しか知らないはずの秘密が漏れないか、関係値どおりの距離感で
話すか、記憶が噛み合っているか。会話を物語に戻す経路は作らない(state にも書かない)。

### 8.1 データ

- `chats.mode = 'room'`、`chats.participants`(JSON 配列の char_id、2〜6 人)。`char_id` は NULL のまま。
  スコープは常に `upto`(未来を知るキャラは成立しない)。参加者は会話の開始時に固定。
- 履歴に保存するのは **演出指示(`role: user`)とキャラの発言(`role: assistant` + `speaker`)だけ**。
  recall の往復は保存せず、発言ごとの `prompt_messages`(控え)と `tools_used`(ツール名)に残す。
  発言ごとに `meta`(生成統計)を付ける。
- 発言は 1 件ずつ独立していて往復の区切りが無いので、削除は `DELETE /chats/{id}/message/{index}`
  (1 件単位。`delete_chat_turn` の「user から次の user まで」は使わない)。

### 8.2 発言の作り方(`chat_agent.room_stream`)

`POST /chat/room/send` `{chat_id?, anchor_node?, participants?, instruction?, speaker?, turns, replace_from?}`。

1. `instruction` があれば演出指示として履歴に積む(空なら積まない。指示なしで進めてよい)。
2. `turns` 回(サーバー上限 `MAX_ROOM_TURNS = 8`)、話者を決めて 1 発言ずつ生成する。
   話者は最初だけ `speaker` の指名に従い、以後は**前の話者の次**(ラウンドロビン、`next_room_speaker`)。
   LLM に「次に誰が話すか」を決めさせない(空回りや独白の連鎖を避ける)。
3. 話者 1 人分のシステムプロンプトは `build_room_system`: 知識の節は `build_character_system` と同じ
   (facts / 関係 / 記憶 15 件 + recall)、**「この会話について」以降だけ会話室用に差し替える**。
   枠組み: 相手と同じ場所で話している / 試しの会話で本編ではない / 相手の発言は `名前「…」`、
   演出指示は `（演出: …）` で届く / 指示には従うが台詞にしない / 自分の発言だけを書く /
   数文にとどめる / この場で聞いたことは知ってよい、それ以外は記憶にあることだけ。
4. 履歴は話者の視点の messages にする(`_room_transcript_messages`): 自分の発言は assistant、
   他者の発言と演出指示は user に置き、user が続くところは 1 つにまとめる。末尾が user で終わるよう
   「あなたの番です」を補う。
5. ツールは `recall` のみ(キャラチャットと同じ)。往復はその発言の間だけ持つ。
6. 返事の先頭に `名前:` / `名前「…」` が付いていたら落とす(`_strip_speaker_prefix`)。
   発言 1 つの `max_tokens` は `ROOM_MAX_TOKENS = 512`。
7. **発言が確定するたびに保存**する。途中で止めても話し終えた発言までは残る。

SSE: `{chat_id}` → 発言ごとに `{speaker, turn}` → `{stage}` / `{delta, speaker}` / `{tool_call}` →
`{utterance: {speaker, text, stats, index}}` → 最後に `{done: true}`。

### 8.3 UI(`ChatDrawer.tsx`)

- 相手セレクタに「キャラ同士の会話」を追加。選ぶと参加者のトグル(キャラ色の枠 + アバター)が
  ヘッダーに並ぶ。2 人以上で「進める」が押せる。会話が始まったら参加者は固定表示。
- 入力欄は**演出の指示**(空でもよい)。右に「次に話す人(順に / ○○から)」と「発言数(1 / 2 / 4 / 6)」、
  主ボタンは「進める」。Enter でも進む。指名は 1 回きり(送ったら「順に」に戻る)。
- 吹き出しは発言者ごとにアバター・枠色・名前(枠色の 10px)。recall は「○○ が記憶をたどった」。
- ホバー操作: 発言は「声で読む(本人の声)」「送った内容を見る」「削除」、**最後の発言だけ
  「消して同じ人にもう一度話させる」**。演出指示は「書き直して以降を作り直す」「以降の発言を作り直す」「削除」
  (2026-10-04 ユーザー要望で編集・作り直しを追加)。どちらも `replace_from` でその位置まで履歴を巻き戻してから
  進める(編集はその位置に新しい指示を積む、作り直しは指示を残して次の位置から)。作り直す発言数は入力欄の
  「n 発言」の設定。話者の順は巻き戻した履歴から数え直す。
- 読み上げ: 発言ごとに `voice.begin({charId: speaker, mode: 'roleplay'})` で声の主を替える
  (`useChatVoice` の `begin` / `speakText` に override を足した)。（）のト書きは語り手の声。
- コンテキスト使用量は**参加者のうちシステムプロンプトが一番長い人**で数える(`_usage_text`)。
- 候補チップは演出指示の定型(`ROOM_TEMPLATES`: 挨拶から / 探り合い / 言い合い など)。
  内容ベースの生成は使わない。

### 8.4 実験中の注意

- 31B でも「相手の台詞まで書く」「演出指示に返事する」ことがある。厳守ルールに書いてあるが、
  起きたら発言を消して作り直す。頻発するなら枠組みの文言を直す。
- 1 発言 = キャラ 1 人分のシステムプロンプト(記憶 15 件込み)+ 会話ログなので、
  相談チャットより使用量の伸びが早い。長く続けるときはリングを見る。
