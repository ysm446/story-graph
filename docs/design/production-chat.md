## ハーネスの制御（2026-10-12 08:40 追加）

[plan.md「制作ハーネスの精度向上」](../plan/plan.md) の第1弾。モデル別検証で観測した癖（適用済み操作の再試行、
同じ取得の反復、同じ引数エラーの反復、空回答、全文置換での既存内容の取りこぼし、取り消された依頼の実行、
登録した資料のシーンへの未設定）を、プロンプトの言い回しではなく `backend/production_guard.py` がサーバー側で扱う。
制作の権限（変更範囲・保護・相談/実行）はこれまでどおり `production_policy.py` が持ち、ガードは権限を広げない。

- **反復の停止**（`RunMonitor`）。実行中の同じ読み取り（ツール名と引数が同一）は2回目に前回の結果へ
  「2回目で結果は同じ」という注意を添えて返し、3回目で作業を止める。確定した変更の後は本文が変わるので数え直す。
  適用済みの書き込み（reasonを除いて同一）は、エラーではなく保存済みの結果に `already_applied` を付けて返し、
  それでも繰り返せば止める。同じツール・同じ文面のツールエラーは2回目に直し方（patch_sceneの正しい形など）を添え、
  3回目で止める。別のエラーや成功で数え直す。止めた作業の終了理由は `stalled`。
- **終了理由の区別**。`completed` / `limit`（16ステップ）/ `stalled` / `empty` / `truncated` / `error` / `interrupted`。
  空応答（ツール呼び出しも本文もない）は1回だけ注記を添えて判断し直し、続けば `empty` で終える。
  通常の文章で終わっても `finish_reason` が `length` なら報告が途切れているので `truncated` とし、完了として記録しない。
  `completed` 以外では作業メモの見直しを行わず、引継ぎ記録の `status` に終了理由を保存する。
  履歴には終了理由と確定済み変更の件数を残し、SSEの `done` に `outcome` / `summary` / `changes` / `tool_errors` / `steps` を付ける。
  画面の完了表示は `summary`（例「同じ操作の反復が続いたため停止しました（変更 1 件・ツールエラー 3 件）」）を使う。
- **全文置換での既存内容の保持**。`update_scene` に `rewrite`（boolean）を追加。元の本文が80文字以上で、
  元の文（句点・改行区切り）のうち新しい本文に残る割合（完全一致または類似度0.75以上）が50%未満なら、
  `rewrite: true` が無い限り保存せず、patch_sceneか明示の書き直しを求める。新しい本文が元の一部そのもの
  （分割のために前半へ縮める操作）は通す。`patch_scene` はサーバーが全文を組み立てるので対象外。
- **途中指示の照合**。実行中に途中指示を取り込むたびに、当初の依頼・全途中指示・確定済み操作・シーン一覧を
  構造化出力（`cancelled_node_ids` / `remaining`）で照合する。取りやめになったシーンへの
  `update_scene` / `patch_scene` / `delete_scene` / `reconnect_scene` はサーバーが拒否し、照合結果（取りやめ対象と残作業）を
  以後のシステム指示に渡す。照合に失敗したら何も禁止しない（失敗で権限は広がらない）。相談モードでは照合しない。
  照合結果は「途中指示を照合しました。取りやめ: …。残作業: …」として履歴に残す。
- **完了前の点検**。モデルが通常の文章で終えようとしたとき、今回登録したキャラクター・場所がどのシーンにも
  使われていなければ、1回だけ注記（cast / location を設定するか、依頼に含まれない旨を報告する）を添えて判断を続ける。
  2回目以降は注記せず完了を受け付ける。保存成功だけでは分からない取りこぼしのうち、決定的に判定できるものから入れた。
- **検証の指標**。SSEに `tool_call`（ツール名と対象IDのみ）を追加し、`scripts/production_metrics.py` が
  ステップ数・終了理由・ツールエラー（文面別）・同じ取得の反復・同じ対象への再書き込みを集計する。
  3つの実機検証スクリプトは `metrics.json`（または結果JSONの `metrics`）と `METRICS` 行を出す。合否条件は従来どおり各スクリプトが持つ。

## 送信時の選択ノード（2026-10-11 22:22 追加）

- キャンバスで選択中の実ノードIDを、通常の依頼・途中指示・送信前の使用量計測へ `selected_node_ids` として渡す。複数選択可。章カードは対象外とし、入力欄で案内する。
- 送信操作時にIDを固定し、待機列・生成・作業対象への追従で画面の選択が変わっても、その依頼に添付した対象は変えない。
- サーバーで存在を確認し、ID・名称・種別を発言の `selected_nodes` に保存する。本文は保存済みの内容を `get_beats` で取得する。未保存の下書きは添付しない。
- 「このシーン」はその発言の選択を参照するようLLMへ指示する。選択なしや複数選択で対象が不明なら確認し、過去の選択を今回の選択に代用しない。
- 選択情報は参照対象を伝えるもので、編集権限ではない。「相談する」では書き込まず、変更範囲・AI保護の判定も維持する。
- 途中指示は各発言の対象を持ち、再送時は同じ指示ID・本文・選択を使う。受付後に改名・削除されても、同一依頼の再送は受付済みの対象情報を返す。
- 入力欄上に現在の選択、各依頼の履歴に送信時の選択を表示する。旧履歴に選択情報を推測で付けない。

## 作業メモの大きな差分の照合（2026-10-11 12:43 追加）

終了時の照合入力（メモ・依頼・途中指示・確定操作・終了報告・前回照合後の差分）が
JSON化後40,000文字以内なら、従来どおり1回でメモを見直す。
超える場合は一律に失敗させず、次の手順で処理する。

1. 資料庫の確定操作は、変更していない項目を照合用入力から除く（元の操作履歴は維持）。資料の種類と対象ごとに分け、長い単一資料は7,000文字の連続断片にする。対象名・断片順・総数を付け、変更内容を切り捨てない。
2. JSON化後24,000文字以内の束にまとめ、各束から3,000文字以内の照合用要約を生成する。
3. 元のメモ全文と全要約が最終入力上限に収まらない場合は、要約をさらに束ねて統合する。
4. 元のメモ全文と統合した要約で最終照合し、従来の世代・資料・メモ版の競合確認後に保存する。

要約では対象ID、作者の決定、完了・未解決の区別、手動変更と削除を保持するよう指示する。
終了報告だけを根拠に完了扱いにせず、古い内容を戻す予定を残さない。
要約の不正・出力打ち切り・圧縮不成立はエラーとし、部分結果をメモや照合基準へ保存しない。
各LLM呼び出し前に途中指示・手動切替を確認し、中断時の既存の保護も維持する。
処理回数に応じて時間は増える。実モデルでの要約品質と所要時間は未検証。

2026-10-11 12:57: 各束の確認件数、要約統合の回数・件数、最終確認をSSEで逐次通知する。
配信の中断時は照合タスクも停止し、途中結果を保存しない。
新しい制作発言・操作報告は記録時刻をUTCで保存し、画面ではローカル時刻を秒まで表示する。
進行状況にも通知時刻を付ける。旧履歴の不明な時刻は推測しない。

## 資料庫へのアクセス（2026-10-10 06:30 追加）

- 制作チャットの `read_library` でキャラクター・場所の一覧、固定設定の全文、構造化された参照先を取得する。
  IDは名前から推測せず一覧で確認する。通常の相談チャット・キャラクターチャットの権限は変更しない。
- 「制作を実行」で `create_character` / `update_character` / `delete_character` と
  `create_place` / `update_place` / `delete_place` を有効にする。制作内の「相談する」では読み取りだけを許可。
- 人物は名前・プロフィール・外見・口調・読み・色、場所は名前・説明・雰囲気・読み・色を扱う。
  編集は指定項目だけを更新し、省略項目と画像・音声設定を保持。物語中の変化や記憶は固定設定と分ける。
- 新規IDはアプリが発行し、同名の重複登録を拒否する。登録後のIDをシーンの `cast` / `location` に使える。
  `location` は登録済みIDまたはnull（親から引継ぐ）。更新時の省略は元の指定を保持する。
- 削除は未使用の資料だけを許可する。登場人物、場所の継承、イベント、章まとめ、記憶、会話、派閥所属、
  清書の視点、朗読台本、画像参照などを調べ、使用中なら参照先を返して拒否する。
  名前が散文に書かれているだけの関係は構造化された参照としては検出しない。
  削除のために参照や会話を勝手に消して回避しないようモデルへ指示する。手動削除の既存仕様は変更しない。
- 資料を参照する保護・範囲外シーンがあるときは設定編集を拒否する。設定変更は既存Storeと同じ清書のstale化を行う。
- 作業前スナップショット、途中指示、同一操作の重複防止、履歴・作業メモの引継ぎに統合する。
  資料庫がモデルの判断中に更新された場合は古い操作を破棄して読み直す。1件の登録・編集・削除はトランザクションで確定。
- 資料の操作通知は `entity_type` / `entity_id` を持ち、シーンの `node_id` と区別する。
  設定の変更前後をチャット内で展開表示し、確定ごとに資料を再取得する。資料操作ではキャンバスを移動しない。
- 派閥、画像生成、音声設定、資料庫での制作途中の手動編集切替は今回の対象外。

検証: pytest 439件、build、Python構文確認成功。Electronと模擬LLMでキャラクター・場所の登録/編集/削除、
設定保持、履歴表示、登録直後のシーンへの使用、資料庫画面の更新を確認。
追加でGemma-4-31B-it Q4_K_Mによる登録・部分編集・未使用資料削除・使用先確認・相談のみを検証済み。
場所の説明のLLM向け引数は `place_description` とし、保存時に既存の `description` へ変換する。
Gemmaの会話テンプレートが `description` という引数名を除外するための互換性対策。
読み取り結果・DB・手動編集APIの項目名は維持し、異なる値での新旧引数の二重指定は拒否する。
再検証時のpytestは451件成功。詳細は [実モデルの検証記録](../reference/production-scenario-validation.md)。

## 送信モードとキーボード（2026-10-10 07:06 変更）

- 「相談する／制作を実行」の2ボタンを、送信モードのプルダウンと共通の「送信」ボタンに変更した。
- 初期値は相談。Enterまたは送信ボタンで選択中のモードとして送信する。Shift＋Enterは改行。
- IME変換中・変換確定キー（keyCode 229）・キーの長押しでは送信しない。

## 1. 目指す制作体験（合意した方向性）

作者がローカルLLMと会話し、LLMが実際のノードの作成・編集・削除・接続変更を使って、
試行錯誤と再構成を繰り返しながら物語の構成を作る。作者による直接編集も引き続き可能にする。
確定した草案を順番にノード化するだけでなく、既存の構成を読み直して組み替えることも対象とする。

完成結果だけを一括表示せず、作業の進行とともにキャンバスへ反映する。
作者はその様子を見ながら途中指示を出し、方針を調整できる。

例:

1. 作者が「主人公の裏切りが唐突なので、動機を補強して」と依頼する。
2. LLMが関連シーンと接続関係を読み、変更の方針と対象を伝える。
3. 葛藤のシーンを追加し、既存シーンを修正する。変更が順次キャンバスに現れる。
4. 作者が「妹との別れは残して」と途中指示を出す。
5. LLMが指示を取り込み、必要な接続変更や重複シーンの削除を行う。
6. 組み直した流れを点検し、変更点と残る課題を報告する。

## 2. 相談と制作の境界

**相談中に作品を編集し始めないことは必須。** 既存の相談チャットと制作チャットは役割と履歴を分ける。

| 種類 | 役割 | 物語への書き込み |
|---|---|---|
| 相談（編集者） | 読み解く、意見を出す、構想を練る | なし |
| キャラクターとの会話・会話室 | 指定経路・時点のキャラクターと話す | なし |
| 制作 | 構想を相談し、依頼に応じて実際の構成を編集する | 作業依頼の範囲で可能 |

制作チャットでも「どう思う？」「まず案を考えて」は提案までに留める。
「その案で直して」「この草案で作って」などの作業依頼を受けて編集を始める。
一度依頼された範囲では、ノード操作ごとの確認を必須にせず、進行を見せながら作業を続ける。
依頼範囲を越える変更や、意図が定まらない箇所は相談へ戻す。

画面案は、既存のチャット領域に「相談／制作」の切り替えを設け、どちらもキャンバスを見ながら使う形。
「この方針で制作を始める」で相談内容を引き継ぐ導線も候補とする。
引き継ぎには決定事項・未確定の案・対象範囲を含め、相談のすべての発言を編集指示とは扱わない。
具体的な配置・名称はUI設計時に詰め、実装時は [style-guide.md](style-guide.md) に従う。

## 3. 読み取り範囲と変更範囲

制作LLMは正史だけでなく、枝・別の結末・未接続ノードと接続関係を参照する。
全体を読めることと、全体を自由に変更してよいことは分ける。作業ごとに依頼対象と保護条件を持つ。
「この章を組み直す」「このシーンは残す」などの条件を実行時にも照合する。

物語の現状はDBのグラフを正とする。本文・接続を作業メモへ複写して正本にしない。
状態は対象ノードまでの経路をfoldして取得し、別の枝の出来事や記憶を一つに混ぜない。
キャラクター用の記憶と制作LLM用の作業メモは別の情報として扱う。

LLMは展開と接続を判断し、キャンバス上の座標配置は既存の配置処理を利用する案を基本とする。
下書き分岐での試作は選択肢とするが、毎回必ず新しい枝を作ることや、正史へ自動採用することは前提にしない。

## 4. 作業ループとツール（実装案）

基本の流れは「最新状態を読む → 次の変更を決める → 検証して適用 → 表示・記録 → 再確認」。
一回のLLM出力で全作品を置き換えず、意味のある小さな変更単位で進める。

| ツールの役割 | 想定する操作 |
|---|---|
| 読み取り | 全体の接続図、指定シーンの本文、経路ごとの状態、出所付き記憶を取得 |
| 作成 | シーンの追加・挿入、下書きの枝や独立ノードの作成 |
| 編集 | シーン本文・登場人物・場所などの変更 |
| 構造変更 | 接続・切断・親の付け替えによる順序変更 |
| 削除 | 指定ノードの削除と、影響する接続の処理 |
| 点検 | グラフの整合性、イベント、依頼条件との一致を確認 |
| 作業メモ | 決定・提案・保留・進捗を読み書き |

ツール名や引数は未確定。既存のStore・生成・イベント抽出を共通の操作層から利用し、
LLMにSQLや任意ファイル操作を直接させる方式にはしない。
相談・キャラチャットには書き込みツールを公開せず、制作側でも作業開始前には書き込みを実行できないようにする。

シーン変更時はイベントの抽出・更新と、下流状態のdirty化、記憶の再構築、清書のstale化を
既存の規則に従って行う。抽出未完了の本文を、状態まで更新済みとして次の判断に使わない。
循環・多重親・章の境界・結末などの制約は、プロンプトだけでなくバックエンドでも検証する。
削除時に下流を残すか再接続するかなどは、操作の引数と検証結果で明示する。

### 4.1 追加の検討（2026-10-10 04:26、提案）

- **「共通の操作層」はまだ無い。** いま書き込みの後始末は二か所に分かれている。
  `store.py` 側は付け替え・dirty 伝播・記憶の再同期(`delete_node` / `update_node` など)、
  `app.py` のエンドポイント側は自動スナップショット・音声 GC・検証(`PATCH /nodes/{id}` /
  `DELETE /nodes/{id}` の冒頭)。制作ツールが Store を直接呼ぶと後者が抜け、エンドポイントを
  呼ぶと作業中に自動スナップショットが乱発する。段階1の最初の作業として、書き込み操作を
  サービス関数に寄せ、エンドポイントと制作ツールの両方がそれを呼ぶ形にする(§8)。
- **ループの形は相談と分ける。** 相談は `MAX_TOOL_STEPS = 8` で全履歴と全ツール結果を
  積み上げる形だが、再構成では一作業でツール呼び出しが 20〜30 回になり、31B のコンテキストが
  先に尽きる。各ステップを「最新状態を読む → 変更を 1 つ JSON で決める → 適用」の独立した
  短いプロンプトにし、会話履歴に積むのは作者とのやり取り(依頼・途中指示・報告)だけにする。
- **ツール数は 6 個程度に抑える。** 上の表の 7 区分をそのまま十数個のツールにすると 31B では
  選択ミスが増える。読み取りは既存 3 つを流用し、書き込みは「後ろに挿入 / 本文更新 / 削除 /
  つなぎ替え」程度から始める。「点検」は LLM のツールではなく、適用のたびにバックエンドが
  自動で行う検証として持つ。

## 5. リアルタイム表示・途中指示・手動編集（実装案）

- 作業状況、生成中の本文、検証済み変更の反映をSSEなどで逐次通知する。
  生成途中の表示とDBへ確定した内容を区別し、中断時に不完全なノードや接続を残さない。
- 作業中のノードを示し、追加・編集・削除・接続変更とその短い理由をチャットに残す。
  作者の閲覧位置を不用意に移動させず、作業対象を追う表示は切り替えられる形を検討する。
- 作業中も途中指示を受け付け、「受け付けた」「次の変更から反映した」を区別して伝える。
  最初は、現在の生成・変更が安全な区切りに達したところで指示を取り込む方式とする案。
- 停止では以後の適用を止める。未確定の生成は破棄でき、確定済みの変更は残して再開できるようにする。
  すでに反映した変更を戻す操作は停止とは分ける。
- 手動編集は同じグラフへ反映する。LLMが読んだ後に作者が対象を変更した場合、
  古い内容による上書きを防ぎ、最新版を読み直して計画を調整する。

変更前の版番号と操作IDを持つ案を検討する。競合検出、通知の取りこぼし後の再同期、
再送時の二重作成防止に使う。作業をバックエンドで管理し、画面の接続が切れても実行状況を確認できるようにする。
既存のLLM処理キューとの統合、ライブラリ切り替え・アプリ終了時の停止方法も実装時に決める。

### 5.1 追加の検討（2026-10-10 04:26、提案）

- **キューはフロント側にある。** LLM を使う処理の逐次実行は `src/renderer/src/tasks.ts` が
  主体で、llama-server は 1 リクエストずつしか受けない([overview.md](overview.md) §5)。
  制作の一作業は「方針 → シーン本文 → イベント抽出 → 次」で LLM 呼び出しが十数回以上になり
  数分かかるので、その間は生成・清書・相談がすべて待ちになる。制作作業は `tasks.ts` に
  **1 タスクとして載せ**、他の操作がステータスバーで「待機」になる既存の見せ方に乗せる。
- **「接続が切れても実行状況を確認できる」は初期段階の要件から外す。** ローカル単一ユーザーの
  Electron では接続断はほぼアプリ終了と同義で、終了時には llama-server も止める。
  段階1〜3 では制作作業を既存の生成・相談と同じく **SSE ストリームに結び付いた処理**にし、
  ストリームが切れたら停止扱いにする。これで版番号による再同期・通知の取りこぼし・
  再送時の二重適用の設計がかなり軽くなる。バックエンド常駐のジョブ管理は段階4以降に回す。
- **競合検出はノード単位で十分。** ライブラリ全体の版番号ではなく、ノードごとの更新番号
  (既存の `updated_at` か、新設の rev 列)を書き込みツールの引数に取らせ、不一致なら
  ツールがエラーを返して LLM に読み直させる。手動編集との共存はこれだけで成立し、
  テストも書きやすい。
- **自動スナップショットは作業中に止める。** 作業開始時に「制作: <依頼の要約>」のラベルで
  1 回だけ保存し(`kind` は manual 扱いにして世代管理で消えないようにする案)、作業中は
  エンドポイント側のスロットル付き自動保存を抑止する。

## 6. 制作LLMの作業メモ（当初の検討案・実装状況は冒頭参照）

長い会話や再起動をまたいで方針を引き継ぐため、会話履歴とは別に作業メモを保持する案。
ユーザーからMarkdownファイルの案が出ていた。以下は当初の検討で、実装ではSQLiteを正本、Markdownを書き出し用とした。
現時点の実装案は、ライブラリのSQLiteに保存し、Markdownとして閲覧・編集できる形。
外部 `.md` ファイルを正本にするか、書き出しだけ可能にするかは今後決める。

| 区分 | 内容例 |
|---|---|
| 作者との決定事項 | 結末は和解するが、主人公は故郷へ戻らない |
| 保護条件 | 妹との別れのシーンを残す |
| LLMの提案 | 裏切り役を変更する案。未採用 |
| 保留事項 | 第3章の視点人物は未定 |
| 作業計画・進捗 | 第2章の再構成中。動機の補強は完了 |
| 判断の理由 | 正体の判明が早すぎるためシーンを後ろへ移した |

LLMの提案を作者の決定へ勝手に昇格させない。根拠となる発言・関連ノード・更新履歴を残し、
作者も確認・修正できるようにする。作業の区切りで更新し、再開時は実際のグラフと照合する。
ライブラリ共通の方針と個々の作業の進捗を区別し、変更を取り消した場合は完了記録も整合させる。
制作メモをキャラクターのプロンプトや物語内の記憶へ混ぜない。

### 6.1 追加の検討（2026-10-10 04:26、提案）

- **作業メモと作業記録を分ける。** 上の表は「決定事項・保護条件・保留事項」(方針)と
  「作業計画・進捗・判断の理由」(経過)が混ざっている。前者は毎回プロンプトに入るので
  小さく構造化して保つ。後者は適用した操作のログ(ツール名・引数・対象ノード・理由・時刻)として
  別テーブルに残し、チャット内の「追加した / 削除した」行と対応させる。このログがそのまま
  §7 の「作業単位で何を変えたか」の履歴になり、部分取り消しの土台にもなる。
- **保護条件は自由文のままではバックエンドで照合できない。** 「妹との別れを残す」を
  ノード ID に落とす段が要る。作者が選ぶか、LLM が候補ノードを挙げて作者が確定し、
  **ロック済みノードの集合**として保持する。ロック済みノードへの本文更新・削除・切り離しは
  ツール側で拒否する。自由文のままの条件はプロンプトにだけ渡し、機械的な保証はしないと割り切る。
- **保存先は SQLite、`.md` は書き出しのみ。** 外部ファイルを正本にすると、ライブラリ切替・
  バックアップ・スナップショットの外に正本が出て、復元で食い違う。閲覧・編集は Markdown の
  見た目で行い、保存はライブラリの DB に置く。

## 7. 変更履歴と復旧

何を変えたかを作業単位で追い、失敗や中断から復旧できることを要件とする。
既存の [snapshots.md](snapshots.md) は、操作単位のundoではなくライブラリ全体を戻す設計。
初期実装では作業開始前のスナップショットを利用する案を基本とし、既存設計を無断で置き換えない。

全体復元では作業開始後の手動編集や会話・メモも戻る可能性がある。
「LLMの変更だけを取り消す」と同じ機能として表示しない。
手動編集を残した部分取り消しには別途変更履歴と競合処理が必要であり、後続段階として検討する。
復旧に使う履歴の保存先・保持期間と、スナップショット復元時の扱いを設計時に詰める。

### 7.1 追加の検討（2026-10-10 04:26、提案）

- 初期の「変更履歴」は §6.1 の操作ログで足りる。逆操作は持たず、何をしたかを追えるだけにする。
- 作業開始前のスナップショットは §5.1 のとおり 1 回だけ、manual 扱いで保存する。
  チャットの作業報告からそのスナップショットへ飛べる導線(「この作業の前に戻す」)を
  設定画面のバックアップ一覧とは別に置くと、全体復元であることを明示したまま使いやすくなる。

## 8. 先に決める論点（2026-10-10 04:26、提案）

§4〜7 の「追加の検討」のうち、段階1の設計そのものに影響するものをまとめる。
いずれも提案であり、ユーザーの判断で確定する。

| 論点 | 提案 | 決めないと困ること |
|---|---|---|
| 共通の操作層 | 書き込みの後始末(dirty・記憶・スナップショット・GC・検証)をサービス関数に寄せ、エンドポイントと制作ツールが共用する | ツールが Store 直叩きになり、後始末の抜けや自動スナップショットの乱発が起きる |
| キューとの関係 | 制作作業を `tasks.ts` の 1 タスクとして載せる | 制作中に生成・清書・相談が llama-server で衝突する |
| 接続断への耐性 | 段階1〜3 では要件から外し、SSE ストリームに結び付いた処理にする | 版番号・再同期・二重適用防止の設計が重くなる |
| ループの形 | ステップごとに独立した短いプロンプト。履歴に積むのは作者とのやり取りだけ | 相談と同じ積み上げ型では 31B のコンテキストが尽きる |
| ツール数 | 6 個程度。点検はツールにせずバックエンドの自動検証にする | 31B のツール選択ミスが増える |
| 保護条件 | ロック済みノード ID の集合。自由文はプロンプト専用 | バックエンドで照合できない |
| メモと記録 | 方針(決定・保護・保留)はメモ、経過は操作ログとして別テーブル | メモが肥大化し、毎回のプロンプトを圧迫する |
| 競合検出 | ノード単位の更新番号をツール引数に取らせる | ライブラリ全体の版管理は過剰で、手動編集のたびに作業が止まる |

### 8.1 段階0: 縦割りの検証（2026-10-10 04:26、提案）

この機能の最大の不確定要素は「31B が実際に一貫した再構成をツール呼び出しでやれるか」で、
基盤を作っても分からない。段階1の前に薄い縦割りを 1 つ作り、実機で確かめる。

| 項目 | 段階0 の範囲 |
|---|---|
| ツール | 既存の読み取り 3 つ + 書き込み 3 つ(後ろに挿入 / 本文更新 / 削除) |
| 実行 | 相談と同じ SSE ストリーム内で同期実行。`tasks.ts` に 1 タスクとして載せる |
| 安全網 | 作業開始時にスナップショット 1 回。作業中の自動スナップショットは抑止 |
| 操作 | 停止のみ。途中指示・メモ・保護条件・競合検出は持たない。実装では制作中の手動編集を禁止する |
| 後始末 | 挿入・更新後のイベント抽出と dirty 伝播は既存処理を呼ぶ(操作層の切り出しはここで最小限だけ行う) |
| 確認 | 「動機を補強して」程度の依頼で 2〜4 シーンの追加・修正が一貫して行えるか。ツールの引数ミス・範囲外変更の頻度 |

結果によって段階1以降の形が変わる。品質が足りなければ、LLM は計画(追加・修正・削除の一覧)を
JSON で 1 回出すだけにし、適用はバックエンドが順に行う方式へ寄せる。
その場合も §1 の「進行をキャンバスで見せる」「途中指示」は適用側で実現できる。

## 9. 段階的な実装順序

以下は依存関係に基づく実装案。既存のPhase 6とは別の追加機能として管理し、着手順・日程は未確定。
段階0は実装・限定的な実機検証済み。段階1〜5は未完了で、一部の基盤を段階0で先行実装した。段階0の当初案は §8.1、実装範囲は冒頭を参照。

| 段階 | 実装内容 | 完了の確認 |
|---|---|---|
| 1. 作業基盤 | 書き込みの操作層の切り出し、相談との分離、制作の会話・作業状態、対象範囲、開始・停止、スナップショット、ノード単位の競合検出 | 相談では書き込めず、古い版への適用と範囲外変更を防げる |
| 2. 作成・編集の一巡 | 読み取りと作成・編集ツール、イベント処理、逐次表示、作業記録 | 指示から複数シーンが順次作られ、途中で止めても確定内容が残る |
| 3. 再構成 | 削除・接続変更・再点検、途中指示の反映、手動編集との共存 | 既存の構成を組み直し、保護条件とグラフの整合性を保てる |
| 4. 継続作業 | 作業メモ、相談からの引き継ぎ、中断・再起動後の再開、バックエンド常駐のジョブ管理の要否 | 決定と提案を区別し、最新グラフを踏まえて続きから進められる |
| 5. 実用調整 | 長い物語での情報量・速度、変更履歴の見せ方、部分取り消しの要否を検討 | 実機で長めの制作を行い、作業経過と修正理由を追える |

最小構成は段階1〜2。ただし、ユーザーが求める「試行錯誤して再構成する」体験は段階3までを必要とする。
メモの自動要約や高度な取り消しを先行させず、まず一連のノード操作と逐次表示を実機で検証する。

## 10. 検証観点

- 相談・キャラ会話からの書き込みができず、制作でも案への質問だけでは編集を開始しない。
- 正史・枝・未接続ノードの流れを読み、指定対象だけを変更する。

## 停止・接続断の記録（2026-10-10 19:25 修正）

- 停止ボタンや接続断は、LLM応答待ちの途中なら `CancelledError`、`yield` で止まっていれば
  Starletteが生成器を閉じる際の `GeneratorExit` として `stream()` に届く。
  従来は前者だけを扱い、変更確定直後などの停止では「作業を停止しました」の履歴と
  途中指示の「未反映のまま終了」への更新が抜けることがあった。両方を同じ扱いにした。
- 終了処理は `finally` で1回だけ `run.close()` → 引継ぎ記録の保存 → `policy_after` の保存 → 履歴保存の順に行う。
  `done` を送る直前にも閉じ、送信後に届く途中指示を受け付けない。
- 競合検出 `NodeVersions.check` は判断開始時と現在の接続をまとめた隣接表で祖先・子孫を辿る。
  比較項目は `production_policy.CONTENT_FIELDS` を保護判定と共用する。

## 本文の部分編集（2026-10-10 08:27 追加）

  `append` は末尾へ指定文字列をそのまま連結、`replace` は一意な `old_text` を `text` へ置換する。
  置換時の空文字列は指定部分の削除。結果の本文全体が空になる変更は拒否する。

- 部分編集は本文だけを扱い、タイトル・登場人物・場所・接続を変更しない。
  本文全文はサーバー側で組み立て、既存の更新処理で候補DBのイベント抽出・検証後に確定する。

  全体の書き直し用の `update_scene` は維持する。依頼の意味を理解したかどうかを機械的に保証する仕組みではない。

## 追加候補の前後照合と終了報告（2026-10-10 09:12 追加）

## 相談モードの入力待ち（2026-10-10 09:57 修正）

相談時は制作の編集手順・作業メモの更新指示をプロンプトへ含めず、参照用のメモだけを渡す。

## 制作からの章操作（2026-10-12）
