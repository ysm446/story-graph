# はじまり / 結末ノード方式 — 正史の導出と「可能性の共存」

作成日時: 2026-08-01 13:19
更新日時: 2026-08-02 13:20

「正史を選ぶ」のではなく、**結末(エンド)ノードをつなぎ、そこから根へさかのぼった道を
正史とみなす**方式の設計メモ。2026-08-01 のユーザー発案。実装前の設計段階。

動機(ユーザーの言葉から):

- 正史は結末からの逆引きで決めたい。**switch ノードのようなもの**(分岐点)も作りたい
- 現在は正史じゃないノードが「非アクティブ(draft の破線・薄い表示)」な扱いだが、
  **普通に可能性として存在させていていい**。分岐は下書きではなく「別のルート」
- ポインタ(結末ノード ID を設定に持つ)方式は、指し先のノードを消したときが
  ややこしそう → **物理ノードなら既存のグラフ操作が追従を勝手に面倒みてくれる**
- 結末ノードは章のあとでも普通のノードのあとでも自然につなげる。
  **対称にスタートのノードもあったほうがいい**(2026-08-01 追記)

## 1. なぜこの方式が筋が良いか

このアプリのグラフは「親は必ず 1 つ」の木構造なので、**末端を 1 つ指定すれば根までの
道は一意**に決まる。つまり正史は本来、エッジごとの `is_canon` フラグの集合ではなく
「結末はここ」という 1 点の情報で表せる。

現在の実装(`make_canon` が分岐点ごとにフラグを貼り替え)は整合性の保守が必要で、
実際にバグの温床になってきた:

- 分岐の根の削除で正史エッジが二重になる(2026-07-29 修正済み)
- **正史の根が「created_at 最古のルート」で決まる**(progress.md 既知課題。
  本編の根を消すと、より古い島へ正史が飛ぶ)

結末方式なら両方とも構造的に起こらない(フラグの貼り替えも根の推測も不要)。

## 2. 方式: はじまり / 結末の物理ノード + アクティブ結末

### はじまり・結末は「本物のノード」としてグラフにつなぐ

`nodes.kind = 'start' | 'ending'`(冪等 ALTER で列追加。NULL = 通常シーン)を持つ
特別なノード。カードは小さく(🏁 + 名前のみ)、beat・イベント・清書は持たない。
UI 上の呼び名は**「はじまり」「結末」**とする(アプリの語彙(正史・清書・章)に合わせた
和語。内部 kind は start / ending)。

- **結末**: シーンの葉に子としてつなぐ。複数あってよい(複数エンディング)。
  「唯一の終末ノードに switch で合流させる」案も検討したが(2026-08-01)、合流 =
  終末ノードに親が複数できることになり、「親は必ず 1 つの木構造」という根本前提
  (fold・path_to・正史の逆引きが依存)が崩れるため不採用。switch ノードを終盤に
  置き、**各ルートの先に結末を 1 つずつ**つなげば同じ構図が木構造のまま実現でき、
  結末ごとに名前も付けられる(トゥルーエンド / バッドエンドなど。title を使う)
- **はじまり(スタート)**: 本編の木の根に 1 つ。最初のシーンはその子になる。
  **これにより冒頭の分岐(別のオープニング)が作れるようになる** — 現在の木構造では
  分岐は「親の複数の子」としてしか作れず、親のいない最初のシーンだけは代替案を
  並べられなかった。はじまりノードが共通の根になることで、書き出しから switch 的な
  ルート分岐が可能になる(結末側と完全に対称)
- 正史の導出だけならはじまりは必須ではない(結末からの遡りで根まで一意)が、
  本編の根が画面上も明示され、「created_at 最古のルートに正史が飛ぶ」問題の残り香が
  完全に消える

**ポインタ案でなく物理ノードにする理由**(ユーザーの指摘を採用):

| 操作 | ポインタ案 | 物理ノード案 |
|---|---|---|
| 結末直前のシーンを削除 | 指し先の追従ルールを自前で実装 | **既存の削除処理(子を親へつなぎ直す)で勝手に追従** |
| 部分木の切り離し / つなぎ替え | 同上 | 既存のグラフ操作がそのまま面倒を見る |
| 複数の結末 | ポインタの配列管理 | 葉に結末ノードを複数つなぐだけ(画面にも見える) |
| 代償 | — | 「結末ノードを除外する」処理が数カ所必要(§5) |

### アクティブ結末

結末ノードは複数あってよい(= 複数エンディングの共存)。そのうち 1 つが
**アクティブ**(`settings.active_ending` に結末ノード ID)。

- **正史 = アクティブ結末から根へさかのぼったノード列**(結末ノード自身は含めない)
- `edges.is_canon` / `nodes.status` は**導出キャッシュ**として結末から再計算する
  (既存の API・UI・章グループ・清書の互換を保つ。`_resync_status` の置き換え)
- アクティブでない結末への道は「別のルート」。draft ではなく**可能性**として扱う
  (§6 の表示変更)

## 3. 操作の対応

| 操作 | 挙動 |
|---|---|
| **結末を作る** | 葉(または任意のシーン)の右クリック「ここを結末にする」→ 子として結末ノードを追加。最初の結末は自動でアクティブに |
| **正史の切替** | 結末ノードをクリック →「この結末にする」。= `active_ending` の差し替え + status/is_canon の再導出。従来の `make_canon` はこの操作に置き換わる(API は残してよい: 対象ノードの子孫の結末を探してアクティブ化、無ければその場に結末を作る) |
| **シーンを正史末尾に追加** | 「末尾」= アクティブ結末の親。結末ノードの直前に挿す(既存の `insert_node_after` の形) |
| **結末ノードの削除** | 複数あるときだけ許可(**最後の 1 つは削除不可**)。アクティブだった結末を消したら、残りのどれかをアクティブにする |
| **シーンの削除・切り離し・つなぎ替え** | 既存処理のまま。結末ノードは子として自動追従する |
| **結末のつなぎ替え**(2026-08-01 追加) | 結末のエッジも切断・接続できる(はじまりは不可)。結末だけ浮かせて別のシーンにつなげば正史の終点が動く。浮いている間は「はじまり」から繋がっている canon 連鎖を正史として使い、**勝手に結末を作り直さない**(`_canon_chain_from_start`) |
| **浮いた結末を作る**(2026-08-01 追加) | ノードエリアの空きスペースを右クリック →「🏁 結末をここに置く」。どこにも繋がない結末をその位置に置き、あとでシーンからドラッグしてつなぐ(`POST /endings`) |
| **はじまりノード** | ライブラリごとに自動で 1 つ作られる(§7)。**常に 1 つ・削除不可**(右クリックに出さない)。「+ シーン」で最初のシーンを作るとその子になる |
| **switch 的な分岐点** | 追加実装は不要: 複数の子を持つシーンがそのまま分岐点(はじまりノードの複数の子 = 冒頭の分岐)。各ルートの先に結末ノードをつなげば「ルート A / ルート B」が対等に共存する |

## 4. 導出ルール(store)

```
canon_path():
  ending = settings.active_ending が指す kind='ending' ノード(生きているもの)
  ending が無い → 従来のフォールバック(is_canon エッジ辿り)…移行期間のみ
  path = ending から親を遡って逆順にした列(ending 自身は除く)
```

- `is_canon` / `status` は正史の導出後に貼り直す(既存の導出キャッシュと同じ扱い)。
  貼り直しの契機は「アクティブ結末の変更」と「グラフ構造の変更」
  - **ノードを増やす経路も「グラフ構造の変更」**(2026-08-02 修正。ユーザー報告
    「正史でない章の中で + シーンを押すと実線で繋がる」): `append_node` /
    `insert_node_after` / `create_group`(マーカーの挟み込み)は `is_canon` を
    その場の当て推量や決め打ちで書いたまま貼り直していなかった。とくに
    `append_node` の「親に連鎖の子が居なければ延長 = canon」は、**島や正史でない
    章の中ではどのエッジも `is_canon=0` なので必ず真**になり、正史でないのに
    実線のエッジができていた。3 経路とも最後に `_resync_canon()` を通す
- fold / state_cache / stale / 章グループは canon_path() を読むだけなので**無変更で動く**

## 5. はじまり / 結末ノードの除外が必要な箇所

`kind` があるノードを弾く述語を store に 1 つ持ち(`is_scene(node)`)、以下で使う:

- 清書対象(`list_renders` / 一括清書)と鑑賞モードのシーン列
- シーン生成の「直近のビート」、チャットの get_beats、コンテキスト使用量
- 章グループ(結末ノードは章に入れない)
- 検証(validation)・イベント抽出の対象
- シーン数の表示・Markdown エクスポート

fold は結末ノードにイベントが無いので通しても無害(状態が素通りするだけ)だが、
`canon_path()` が最初から含めないので考慮不要。

## 6. 表示: 「非アクティブ」から「可能性」へ

- 結末ノード: 小さいカード(🏁 + 結末名)。アクティブな結末はアクセント色、
  他は通常色。クリックで「この結末にする」
- **非正史ノードの表示を格上げする**: 現在の draft(破線 + 透明度 0.85)は
  「未確定の下書き」の含みが強い。ルートとして対等に見せるため、実線 + 通常の
  濃さにし、アクティブなルート上のノードだけ**わずかに強調**(枠色 or 背景)する方向。
  draft バッジは「提案カードから挿入された未検討シーン」など別の意味に残すか要検討(§8)
- 章ビューとの関係: 章は正史区間のみ(従来どおり)。別ルートは章ビューでは
  未分類ノードとして見える

## 7. 移行

1. 冪等 ALTER: `nodes.kind TEXT`(NULL = シーン)
2. ライブラリを開いたとき、結末ノードが 1 つも無ければ**現在の正史末尾に自動で
   結末ノードを 1 つつないでアクティブにする**(名前は「結末」)。あわせて、
   はじまりノードが無ければ**現在の正史の根の親として自動でつなぐ**(名前は「はじまり」)。
   以後は結末方式で導出
3. `edges.is_canon` / `status` は導出キャッシュとして残す(API・UI の互換)
4. 既存の `make_canon` API は §3 の意味に置き換えて残す(フロントの変更を最小に)

不変条件: **はじまりは常に 1 つ(削除不可)、結末は常に 1 つ以上(最後の 1 つは
削除不可)**。この 2 つがあるので「結末が無い = 正史が導出できない」状態は
存在せず、フォールバックは移行時の一度きりで済む(2026-08-01 決定)。

## 8. 未解決の論点

- **draft の意味の再定義**: status = canon/draft を「アクティブなルート上か」の導出に
  変えたとき、「提案カードから挿した未検討シーン」を区別する必要が残るか。
  残すなら別フラグ(source ベースでも導出できる可能性)
- ~~結末の名前~~ → **決定**(2026-08-01): 結末ノードは title に名前を持てる
  (「トゥルーエンド」など。省略時は「結末」)。UI の呼び名は「はじまり / 結末」
- **fold の始点**: はじまりノードは空 state の起点になるだけ(イベント無し)。
  はじまりの子が複数あるとき、各オープニングは兄弟分岐として独立に fold される
  (既存の分岐と同じ)
- **複数ルートの清書の共存**: renders はノード単位なのでルートごとの清書は自然に
  共存できる。鑑賞モードに「どの結末で読むか」の切替を出すか(将来の
  インタラクティブ読書・switch 選択の入口になり得る)
- **島との関係**: 島にも結末ノードは置ける(島の中の正史、という概念は無いので
  当面は飾り)。本編へつないだときにアクティブ候補になる
- 実装順: ~~① kind 列 + ノード作成・表示 → ② canon_path 導出切替 + 移行 →
  ③ make_canon 置き換え~~ → **①〜③ 実装済み(2026-08-01)**。
  残り: ④ 鑑賞モードの結末切替(任意)と、§6 の「非正史ノードの表示の格上げ」
  (draft の破線・薄い表示をルート対等の見た目に変える件。draft の意味の再定義と
  あわせて次のタイミングで)
