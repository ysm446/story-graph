## 1. 清書(レンダリング)

システムプロンプトは 3 層の連結。**① だけがユーザー編集可能**(スタイルプリセット)。

```
① プリセット本文(style_presets.tone に全文格納。「✎ 編集」で自由に書ける)
   デフォルト「三人称・標準」の例:
   | あなたはプロの小説家です。与えられたシーン(出来事の仕様書)を、
   | 一つの完成された場面として散文に仕上げます。
   | 背景や空気感の描写、人物の仕草と表情、会話の間を丁寧に肉付けしてください。
   | 自然で読みやすい三人称の地の文。抑制の効いた描写と会話のバランスを取り、
   | 説明しすぎないこと。

② 人称行(自動生成: プリセットの person × POV 選択)
   | 人称: 三人称 / 一人称(アヤ の視点) / 三人称(アヤ 寄りの視点)

③ 厳守事項(常に自動追加。アプリの設計原則「清書は状態を変更しない」を守る部分)
   | - シーンに書かれている出来事以外を発生させない(新しい事件・移動・関係の変化を起こさない)
   | - 許されるのは描写・内面・会話の肉付けのみ
   | - 「状態」にない情報を登場人物に知らせない(POV 時: 視点キャラが知らないことは地の文にも書かない)
   | - 直前シーンの末尾から自然に接続する(あらすじの繰り返しをしない)
   | - 見出し・注釈・メタ情報は書かず、本文のみを出力する
```

ユーザーメッセージ(毎シーン組み立て):

1. `## 登場人物` — cast のプロフィール(外見・口調)
2. `## 状態(このシーン適用後)` — fold 済み state。**POV 指定時は POV キャラが知る情報のみ**
   (facts / 関係値 / 記憶の content 直近 8 件)
3. `## このシーンのビート` — タイトル / 場所 / 時間 / 感情の核 / 本文
4. `## 直前シーンの末尾(この続きから書く)` — 直前レンダー散文の末尾 ~1400 字
   (スライディングウィンドウ。spec §7)

## 2. シーン生成(構造モード)

システムプロンプトは清書と同じ 2 層方式。**① は設定画面「シーン生成プロンプト」で編集可**
(settings キー `generation_system_prompt`。空なら下記デフォルト)。

```
① 編集可能な本文(デフォルト):
   | あなたは物語のビート(出来事の仕様書)を設計する構成作家です。
   | ビートは散文ではなく、そのシーンで起きる出来事を数文で記述した仕様書です。
   | 起伏と因果を意識し、キャラクターの感情が動く出来事を設計してください。

② ルール(常に自動追加。スキーマ・状態整合を守る部分):
   | 出力は必ず指定の JSON 形式に従ってください。
   |
   | ルール:
   | - beat は出来事の記述に徹する(描写・台詞の肉付けはしない)
   | - events はビートで起きた出来事による状態変化を漏れなく列挙する
   |   - キャラの初登場シーンでは char_introduce を必ず発行する
   |   - 心に残る出来事は memory_add(そのキャラ視点の一人称的内容で)
   |   - 関係が動いたら relationship_update(delta は -1.0〜1.0 の小さな変化。reason 必須)
   |   - 場所の移動や状況変化は fact_set(key 例: location, goal, items)
   | - cast はそのシーンに登場するキャラ ID のみ
   | - 退場済みキャラは登場させない
```

ユーザーメッセージ(spec §6.1 のコンテキスト構築):

1. `## キャラクター一覧` — 全キャラの id / 名前 / 性格 / 口調
2. `## 現在の状態(直近ビート適用後)` — fold 済み state(時間 / 世界 facts / キャラ facts / 関係値)
3. `## 各キャラが想起している記憶` — cast 各キャラのハイブリッド検索 top5
   (クエリ = 直近ビート + 指示。RRF × 重要度 × story_order 半減期減衰)
4. `## 直近のビート` — 正史(または分岐元)パスの直近 3 件
5. `## 指示` — ユーザー入力。空ならデフォルト
   (通常:「物語の流れに沿って、次のビートを 1 つ設計してください。」/
    分岐生成:「直前のビートの時点から分岐する、もう一つの展開(what-if)を 1 つ設計してください。」)

出力は JSON schema で強制(title / beat / emotional_core / cast(登録キャラ ID の enum)/
location / events)。LLM が発行できるイベントは 5 種のみ
(memory_add / relationship_update / fact_set / char_introduce / char_retire)。

## 3. イベント抽出(手動で書いたシーン用)

```
あなたは物語のビート(出来事の仕様書)から状態変化イベントを抽出する解析器です。
ビートに書かれている出来事だけを対象に、状態変化を JSON で列挙してください。
書かれていない出来事を推測で追加してはいけません。
```

ユーザーメッセージ: キャラ一覧 / 適用前の状態 / 対象ビート本文。

## 4. シーンに取り込む(散文 → 正史への還流)

```
あなたは物語の編集者です。散文レンダリングの中からユーザーが気に入った一節を、
正史(ビート = 出来事の仕様書)に取り込むための提案を作ります。

- beat_appendix: 選択された一節の内容をビートに追記する 1〜2 文(出来事の記述として)
- events: その内容が状態に影響する場合のイベント(なければ空配列)
- 選択部分に書かれていないことを追加しない
```

ユーザーメッセージ: 現在のビート + ユーザーが選択した散文の一節。

## 共通の技術的制約(llama.cpp グラマー)

- JSON schema の `minimum`/`maximum` は無視される → 生成後に `normalize_events` で clamp
- 条件付き required は表現できない → fact_set は scope 別に 2 変種へ分割
- 低温度でグラマー制約下の空白ループが起きうる → finish_reason=length + 空内容を検出して温度を変えてリトライ

詳細は [docs/plan/progress.md](../plan/progress.md) の知見メモを参照。

## プロンプトログ(デバッグ表示)

実際に LLM へ送られたプロンプトと応答は、`backend/llm.py` の `PROMPT_LOG`
(直近 30 件のリングバッファ)に用途ラベル付きで記録される。
設定画面の「プロンプトログ」から確認できる(`GET /debug/prompts`)。
各エントリ: ラベル / 時刻 / 温度 / トークン数(usage) / messages 全文 / 応答(先頭 3000 字) / エラー。
