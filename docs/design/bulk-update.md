# まとめて更新

作成日時: 2026-11-10 22:27
更新日時: 2026-11-11 04:30

出かける前や寝る前に 1 回押すと、古くなったイベント・章のまとめ・清書・朗読台本(話者と感情)を順に作り直していく機能の設計。
印の仕組みは [event-staleness.md](event-staleness.md)。

**状態(2026-11-11): 段階 1(章のまとめと清書)と台本(話者と感情)を実装済み。段階 2(イベント)は未実装。**

## 1. 目的

- 本文を直すと、イベント・章のまとめ・清書がそれぞれ古くなる。いまは 1 つずつ自分で押して回る必要がある。
- LLM の処理は 1 件ずつしか走らないので、件数が多いと待ち時間が長い。人が席にいない時間に回したい。
- 無人で走るので、**何をどこまでやるかを始める前に自分で選べる**こと、**あとで戻せる**こと、
  **戻ってきたときに何が起きたか分かる**ことを重視する。

## 2. 決めたこと(2026-11-10 ユーザー決定)

- 更新する項目は、ダイアログのチェックで選ぶ。選ぶ単位は項目(種類)で、シーンを 1 件ずつ選ぶ画面は作らない
  (触ってほしくないシーンは、先に「このままでよい」で印を消しておく)。
- 清書は、**いま選んでいる文体プリセットと視点の組だけ**を対象にする(`reader_preset_id` / `reader_pov_char` / `reader_target_chars`)。
- 範囲は**正史の道だけ**を既定にし、チェックで分岐・島も含められるようにする。
- イベントは正史を変えるので、既定ではチェックを外しておく。
- 自分で押して始める。操作が無いときに自動で始める形は作らない。

## 3. 対象の拾い方

| 項目 | 拾う条件 | 既定 |
|---|---|---|
| イベント: 要更新 | シーンの `events_status` が `stale` | オフ |
| イベント: 未作成 | シーンの `events_status` が `missing` | オフ |
| 章のまとめ: 要更新 | 章の `digest_stale` が 1(まとめを一度も作っていない章は拾わない) | オン |
| 清書: 要更新 | いまの組の最新の清書が `stale` | オン |
| 清書: 未清書 | いまの組の清書が無く、本文が空でないシーン | オン |
| 台本: 清書を作り直した | いまの組の最新の清書の台本に LLM で付けていないが、この組の前の清書の台本には付けてあった | オン |
| 台本: まだ付けていない | いまの組の清書があり(本文が空でない)、この組の清書のどれにも LLM で付けていない | オフ |

- はじまり / 結末などのマーカーは拾わない。
- **範囲**: 既定は正史の道(`Store.canon_path()`)に乗っているシーンと、そのシーンが属する章。
  「分岐・島も含める」にチェックを入れると、すべてのシーンと章を対象にする。
- まとめを作っていない章を拾わないのは、まとめを作るかどうかが作者の判断だから
  (作ると、次の章から先でその章の記憶がまとめに置き換わる)。
- **台本**(2026-11-11 ユーザー要望で追加)の相手は、いまの組の**最新の清書**(要更新の清書でも、読み上げに
  使うのはそれなので拾う)。台本には stale の印が無い([voice.md](voice.md) §4.1)ので、「LLM で付けたか」
  (`voice_scripts.source = 'llm'`)で数える。手で直しただけの台本(`rule` で保存)は付けていない扱い。
  清書を作り直すと新しい清書には台本の保存が無く、前の台本から同じ文の行を引き継ぐだけになるので、
  付け直しの対象になる。付け直しても、作者が台本で手直しした行(`edited`)はそのまま残る(annotate の決まり)。
  まだ付けていないシーンを既定でオフにしたのは、読み上げを使うかどうかで要るかが分かれ、件数も多くなりがちなため。

## 4. 実行の順番

**イベント → 章のまとめ → 清書 → 台本**。チェックの順には左右されない。

1. **イベント**: 上流から順に(`POST /nodes/reextract` と同じ並び)。手で足したイベントは残す(`keep_user_events`)。
2. **章のまとめ**: 物語の順に。イベントが変わるとその章のまとめが要更新になるので、**1 のあとで数え直す**。
3. **清書**: 物語の順に。イベントやまとめが変わるとその先の清書が要更新になるので、**2 のあとで数え直す**。
4. **台本**: 物語の順に、1 シーンずつ `POST /renders/{id}/voice_script/annotate`。清書を作り直すと台本が
   付け直しになるので、**3 のあとで数え直す**。

ダイアログの件数は開いた時点のもの。イベントやまとめにチェックがあるときは、清書の件数の横に
「イベント・まとめの更新後に増えます」と添える。実際に何件やるかは、各段の直前に数え直して決める。

イベントを作り直す段では、下流の清書が広く要更新になることがある(状態が変わった場合)。
清書の件数が大きく増えうることは、ダイアログの注意書きで伝える。

## 5. 画面

### 入口

モード切替の行の右端、「チャット」の左に「まとめて更新」のボタンを置く(二次ボタン)。作品全体が相手なので、
構造モードの中ではなく、どのモードからも押せる場所にした。
古いものが 1 件も無いときも押せる(開くと「更新するものはありません」と出る)。実行中と制作中は押せない。

### ダイアログ

```
まとめて更新

イベント
  ☐ 要更新のシーン            3 件
  ☐ 未作成のシーン            5 件
章のまとめ
  ☑ 要更新のまとめ            1 件
清書(硬質な三人称 / POV なし)
  ☑ 要更新の清書              8 件
  ☑ まだ清書していないシーン  12 件
台本(話者と感情)
  ☑ 清書を作り直したシーン    2 件
  ☐ まだ付けていないシーン    6 件

☐ 分岐・島も含める
☑ 終わったらモデルを解放する

上から順に実行します。始める前に、いまの状態を保存します(設定の「スナップショット」から戻せます)。
                                              [ 取り消し ] [ 始める ]
```

- 0 件の項目はチェックできない。選んだ項目がすべて 0 件なら「始める」は押せない。
  ただし清書の 2 項目は、まとめを選んでいる間は 0 件でも選べる(まとめの更新で増えるため)。
  台本の 2 項目も同じく、清書を選んでいる間は 0 件でも選べる(清書の作り直しで増えるため)。
- 「分岐・島も含める」を切り替えると、件数を数え直す。
- 清書の見出しに、いまの文体プリセットと視点の名前を出す(何が作られるか分かるように)。
  プリセットが 1 つも無いときは、清書の項目を押せなくして理由を出す。
- イベントにチェックを入れたときだけ、注意書きを足す:
  「イベントを作り直すと物語の状態が変わり、その先の清書が要更新になることがあります。手で足したイベントは残ります。」
- **モデルの解放**は、アプリが起動した llama-server のときだけ選べる。外部で起動したサーバーは
  アプリから止めない決まりなので、その場合は押せなくして理由を出す。
- チェックの状態は次に開いたときのために覚える(画面ごとの好みなので `localStorage`)。
  ただし**イベントの 2 項目は毎回オフから始める**(うっかり正史を変えないため)。

部品はスタイルガイドの既存のモーダル・チェック・ボタンの型を写す。新しい型が要れば実装後にガイドへ追記する。

### 実行中

- 実行キュー(`tasks.ts`)に「まとめて更新」を **1 件**積む。ステータスバーに段の名前と進み具合
  (例: `清書 4/20 第三章の夜`)が出て、そこから中止できる。
- 中止すると、書きかけの 1 件は保存せず、残りはやらない。済んだ分はそのまま残る。
- 実行中も画面は操作できる(ロックしない)。清書中にシーンを編集した場合は、既存の仕組みで
  その清書が要更新として保存される。
- 処理中のシーンは、いまと同じく枠が光る。

### 終わったあと

結果のダイアログを出し、閉じるまで残す(戻ってきたときに読めるように)。

```
まとめて更新が終わりました(1 時間 12 分)

イベント    8 件作り直し
章のまとめ  1 件更新
清書        27 件(うち失敗 2 件)

失敗したもの
  清書  第三章の夜  — TimeoutError: ...
  清書  帰り道      — ...
```

- 中止したとき・途中で止まったときも、そこまでの結果を同じ形で出す。
- 最後の結果は `localStorage` にも残し、次に「まとめて更新」を開いたときに「前回の結果」として見られる。

## 6. 失敗と中断

- **1 件失敗しても続ける。** イベントは既存の作り直しが失敗を飛ばして続ける。清書はいまの `/render` が
  1 件の失敗で全体を止めるので、**1 シーンずつ呼ぶ**(`node_ids` に 1 件)。前のシーンの清書の末尾に
  つなげる仕組みは、保存済みの清書を読むのでそのまま働く。
- **上流の清書が失敗したシーンの下流も続ける。** 前の清書が古いままでも書けるので、止めない。
- **3 件続けて失敗したら止める。** サーバーが落ちたまま残り全部を失敗させても意味が無い。
  止めた理由を結果に書く。失敗の理由は見分けない(届かない失敗かどうかを確実に見分ける手がかりが無く、
  理由の違う失敗が 3 件続くことはまず無いため)。
- **自分で中止したときは、モデルを解放しない**(人が席にいるので)。
- **アプリを閉じると止まる。** キューは画面側にあるため。再開の仕組みは作らない
  (もう一度押せば、残っている古いものだけが拾われる)。
- **PC のスリープ**: 実行中は Electron の `powerSaveBlocker`(`prevent-app-suspension`)でスリープを止め、
  終わったら外す。画面が消えるのは止めない。

## 7. 安全

- 始めるときに必ずスナップショットを取る(ラベル「まとめて更新の前」。間引きなし)。選択肢にはしない。
- イベントの段は、既存の作り直しと同じ経路を通す(下流の清書の要更新、章のまとめの要更新、指紋の記録が同じに働く)。
- 清書は状態を変えない(設計原則 4)。章のまとめは、作者が一度作った章だけを作り直す。

## 8. 実装の分け方

### バックエンド

- `GET /bulk-update/plan?include_branches=true|false` — 対象を数えて返す(`bulk_update.plan`)。
  `{ preset, pov, target_chars, include_branches, digests: [{id, title}], renders: [{id, title, status}] }`。
  `status` は `stale` / `missing`。台本は `scripts: [{id, title, render_id, status}]`(`id` はシーン、
  `render_id` は付ける相手の清書)。件数だけでなく ID を返し、画面はそれを各段の直前に取り直して使う(数え方を 1 か所にする)。
  どれも実行する順に並べて返す。段階 2 でイベントの一覧を足す。
- `POST /bulk-update/start` — スナップショットを取る。取れなければ 500 を返し、画面は何も書き替えずに止める。
- 実行そのものは既存の口を使う: `POST /groups/{id}/digest/generate?snapshot=false`、`POST /render`、
  `POST /renders/{id}/voice_script/annotate`(段階 2 で `POST /nodes/reextract`)。`snapshot=false` は、章ごとの自動保存を積まないため
  (自動保存は 30 件までなので、章の数だけ積むと古いものが押し出される)。

### 画面

- `BulkUpdateDialog.tsx`(選ぶ・結果を見る。`App` に 1 つ置く)、`bulkUpdate.ts`(実行の本体。キューの runner と、
  ダイアログの開閉・前回の結果)。
- 実行の本体はモジュールに置く(ダイアログを閉じても、モードを切り替えても続くように。`tasks.ts` と同じ考え方)。
- スリープ止めは main に IPC を 1 つ足す。

### 段階

1. **段階 1**(済み): 章のまとめと清書だけ(イベントの項目は出さない)。対象の数え方、ダイアログ、実行、結果、スリープ止め。
2. **段階 2**: イベントの項目を足す(数え直し、注意書き)。

段階 1 だけでも「寝る前に清書を回す」用途は満たせる。段階 2 は正史を変えるので、段階 1 を実際に使ってから足す。
