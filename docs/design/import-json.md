# 取り込み JSON — 外部の LLM に作品データを書いてもらう

作成日時: 2026-10-14 02:21
更新日時: 2026-10-14 02:55

**状態: 最初の版を実装済み(2026-10-14)。** 2026-10-13 のユーザーとの相談をまとめたもの。直列の作品を、
空のライブラリへ取り込める。実装したものは §9、まだ決まっていない点は §8。

- 外部の LLM に読ませる仕様書: [docs/reference/import-format.md](../reference/import-format.md)
- 完成例: [docs/reference/import-example.json](../reference/import-example.json)

## 1. 目的

既存の物語(映画など)を、このアプリのデータとして取り込む。

- **きっかけ**: 既存作品の構成を分析したい。取り込んだ後、登場人物と話せたら面白い
- **変換は外部の LLM に任せる**: 作品の知識と長い文脈が要る仕事で、ローカルの LLM には向かない。
  Claude Code や Codex のような外部の LLM にデータを書いてもらう
- **取り込んだ後はローカルで動く**: 登場人物との会話・清書・相談は、いまの仕組みがそのまま使える

## 2. 方針

外部の LLM には **取り込み用の JSON ファイルを 1 つ書いてもらい、アプリがそれを検査してから一括登録する**。

| 方式 | 採否 | 理由 |
|---|---|---|
| 取り込み用の JSON を挟む | **採用** | 取り込む前に誤りを弾ける。ファイルを直して入れ直せる。外部の LLM はアプリの内部を知らなくてよい |
| API を直接叩いてもらう | 補助 | いまの API(§4)だけで登録はできる。ただし何十回も呼ぶことになり、途中で失敗すると半端な状態が残る |
| DB(SQLite)へ直接書く | 不採用 | 検索用の索引・埋め込み・変更履歴が作られない。接続の向きや章の所属の検査を通らない。テーブルの形に縛られる |
| MCP サーバーにして対話しながら編集 | 見送り | 作れるが、最初の用途には大きすぎる |

取り込みの流れ:

1. 外部の LLM が、仕様書(§6)を読んで JSON を書く
2. 検査コマンドで誤りを確かめ、直す(LLM が自分で繰り返す)
3. アプリの取り込み機能がもう一度検査し、スナップショットを取ってから、既存の保存の経路で一括登録する

## 3. 書いてもらうもの

| 種類 | 中身 | 何に効くか |
|---|---|---|
| キャラクター | 名前、読み、プロフィール、外見、口調 | 人物像と話し方の土台 |
| 場所 | 名前、読み、説明、雰囲気 | シーンの舞台 |
| 設定資料(世界) | タイトル、分類、本文、扱い、AI への参照方法 | 世界のルール、組織、用語、時代背景 |
| シーン | タイトル、本文(要約)、感情の核、登場人物、場所、前のシーンからの経過 | 物語の並び |
| イベント | そのシーンで起きたこと・人物が知ったこと・関係の変化 | 時点ごとの記憶と関係 |
| 章 | 幕や大きな区切りごとのシーンのまとまり | 構成の見通し |

**イベントが要る理由**: キャラクターのプロフィールは「物語が始まる前のその人」しか表せない。
「このシーンの時点で何を知っていて、誰をどう思っているか」は、イベントを先頭から積み上げて作られる
([node-inheritance.md](node-inheritance.md))。イベントが無いと、どの時点で話しかけても同じ答えになる。
本文からローカルの LLM で抽出することもできるが、数十シーン分は時間がかかり精度も落ちるので、
外部の LLM に書いてもらうのが一番効く。

質を左右する点:

- **口調**はプロフィールとは別に、実例の言い回しを添えて具体的に書く
- **シーン本文**は要約で足りる。脚本の再現は要らない
- **前のシーンからの経過**(§5.3)を入れる。未設定のシーンを挟むと、それより前の記憶の時期が分からなくなる。
  特に章の先頭のシーンに入れる

## 4. いまの API でできること(参考)

取り込み機能が無くても、次の API で同じ内容を登録できる。取り込み機能はこれらと同じ保存の経路を使う。
バックエンドはローカルの HTTP サーバーで、認証は無い。

| 対象 | API | 主な項目 |
|---|---|---|
| キャラクター | `POST /characters`、`PATCH /characters/{id}` | name / profile / appearance / voice / color、PATCH で reading |
| 場所 | `POST /places`、`PATCH /places/{id}` | name / description / atmosphere / color、PATCH で reading |
| 設定資料 | `POST /setting-documents` | title / category / body / status(confirmed・draft・reference)/ scope / ai_mode(search・always・never) |
| シーン | `POST /nodes`(末尾に追加。`parent_id` でその後ろ)、`POST /nodes/{id}/insert_after` | title / beat / emotional_core / cast(キャラ ID)/ location(場所 ID)/ elapsed_unit / elapsed_count / events |
| イベント | シーン作成時の `events`、`PUT /nodes/{id}/events`(全件置換) | type と payload(§5.4) |
| 章 | `POST /groups` | title / node_ids |

制作チャットの実行中は、書き込みの API は 409 で拒否される。

## 5. JSON の形(案)

### 5.1 決めごと

- **ID を書かせない。** 人物と場所は名前で参照し、ID は取り込み時にアプリが振る。LLM に ID を作らせると参照の食い違いが増える
- **シーンは配列の順に並べる。** 直列の作品なら、接続の指定そのものが要らない
- **アプリ内部の項目を出さない。** 座標、版番号、索引、正史かどうかなどは取り込み側で補う
- **省略できる項目は省略できる。** 必須は、人物と場所の名前、シーンの本文くらいに絞る

### 5.2 例

```json
{
  "format": "story-graph-import",
  "version": 1,
  "title": "取り込む作品の名前",
  "characters": [
    {
      "name": "アヤ",
      "reading": "あや",
      "profile": "港町で育った測量士。慎重だが、一度決めると引かない。",
      "appearance": "二十代後半。短い黒髪、日に焼けた肌。",
      "voice": "一人称は「私」。短く言い切る。例: 「それは後でいい。先に橋を見る。」"
    }
  ],
  "places": [
    { "name": "港", "description": "古い石造りの防波堤がある小さな港。", "atmosphere": "潮と油の匂い。朝は霧が出る。" }
  ],
  "documents": [
    { "title": "測量組合", "category": "組織", "body": "…", "status": "confirmed", "ai_mode": "search" }
  ],
  "chapters": [
    { "title": "第一幕", "scenes": ["出発", "橋の上"] }
  ],
  "scenes": [
    {
      "title": "出発",
      "beat": "アヤは夜明け前に港を出る。見送りに来たケンに、戻る日を告げない。",
      "emotional_core": "言えなかった別れ",
      "cast": ["アヤ", "ケン"],
      "location": "港",
      "events": [
        { "type": "memory", "who": "アヤ", "text": "戻る日を言わずに港を出た", "importance": 0.7 },
        { "type": "memory", "who": "ケン", "text": "アヤが何も言わずに出ていくのを見送った", "importance": 0.6 },
        { "type": "relation", "who": "ケン", "toward": "アヤ", "change": -0.2, "label": "置いていかれた", "reason": "理由を聞かされなかった" }
      ]
    },
    {
      "title": "橋の上",
      "elapsed": { "unit": "day", "count": 3 },
      "beat": "…",
      "cast": ["アヤ"],
      "location": "港"
    }
  ]
}
```

### 5.3 前のシーンからの経過

シーンの `elapsed` は、1 つ前のシーンからどれだけ経ったか。アプリの項目(`elapsed_unit` / `elapsed_count`)に対応する。

| unit | 意味 | count |
|---|---|---|
| (省略) | 未設定。決めていない | — |
| `immediate` | 直後。ひとつながりの場面 | 不要 |
| `same_day` | 同じ日。場面は変わるが日はまたがない | 不要 |
| `hour` / `day` / `week` / `month` / `year` | 時間後 / 日後 / 週間後 / か月後 / 年後 | 1 以上の数 |

- **先頭のシーンは省略する。** 前のシーンが無いので使われない
- 未設定と「直後」は別。本文に手がかりが無ければ省略し、推測で `immediate` にしない
- 何時間後かが分かるなら `hour`。同じ日のうちだが時間は決まらないなら `same_day`

### 5.4 イベント

アプリの内部では、イベントは `type` と `payload` の組で、主なものは次のとおり。

| 内部の type | payload | 意味 |
|---|---|---|
| `memory_add` | char / content / emotion(-1〜1)/ importance(0〜1)/ refs | その人物の記憶 |
| `relationship_update` | char / target / delta(-1〜1)/ reason / label | 関係の変化(増減) |
| `relationship_set` | char / target / value / label | 関係を絶対値で置く |
| `fact_set` | scope(char・world)/ char / key / value | 人物の事実、または誰もが知る世界の事実 |
| `char_retire` | char / reason | 退場(死亡・その場を去る) |

§5.2 の例では、これを書きやすい形(`memory` / `relation` と、`who`・`toward` のような名前)に言い換えている。
内部の形をそのまま書かせるか、言い換えた形で受けて取り込み側で変換するかは未決定(§8)。

書き方の決まり(シーン生成の LLM に渡しているものと同じ考え方):

- 記憶は、**その場に居た人物ごとに**書く。行動した本人だけでなく、見た・聞いた・気づいた人物にも出す
- 人から聞いた話は、見たことと区別できる書き方にする(誰から聞いたかを含める)
- 重要度の目安: 人生を変える出来事 0.8〜1.0 / 当事者の重要な体験 0.5〜0.7 / 目撃・伝聞 0.3〜0.5 / 些細なこと 0.1〜0.2
- 関係の変化は小さく(±0.3 程度)。±1.0 は人生を変える出来事だけ
- そのキャラだけが知る秘密は、世界の事実ではなく、知っている人物の事実として書く
  (世界の事実に置くと、知らないはずの人物まで知っていることになる)
- 誰がどこに居るかは、シーンの登場人物と場所で決まる。事実として場所を書かない

## 6. 外部の LLM への説明のしかた

毎回こちらで説明文を書かずに済むよう、アプリに次の 4 つを持たせる。

1. **仕様書(Markdown 1 枚)**: 各項目の意味と書き方の決まり。形式だけでなく、§3 と §5.4 のような、
   質を左右する判断の基準を書く
2. **小さな完成例**: 3〜4 シーンの短い話を、全項目を埋めた JSON で付ける。LLM は説明文より例に強く従うので、
   ここが最も効く
3. **JSON Schema**: 必須項目・型・選択肢を機械的に確かめる
4. **検査コマンド**: ファイルを渡すと、取り込まずに誤りだけを返す。「3 番目のシーンの登場人物『田中』が
   人物の一覧に無い」のように、直し方が分かる文で返す

4 が要。外部の LLM は「書く → 検査する → 直す」を自分で繰り返せるので、仕様書の読み落としがあっても
最終的に正しいファイルになる。

頼み方の例(Claude Code や Codex で、リポジトリを開いた状態):

> docs/reference/import-format.md を読んで、映画『○○』の取り込みファイルを作ってください。
> あらすじは synopsis.txt にあります。書いたら検査コマンドを通してください。

- Claude Code だけで使うなら、これをスキルにすれば `/import-movie ○○` のように呼べる。
  他のツールでも使うなら、仕様書と検査コマンドの形にしておく方が共通で使える
- チャットだけの LLM(ブラウザ版など)は検査を自分で回せない。仕様書と例を貼って JSON を書いてもらい、
  アプリの取り込み画面で検査結果を見て、誤りを貼り返して直してもらう。そのため、検査は取り込み画面からも
  同じ内容で使えるようにする

## 7. 映画を取り込むときの考え方

- **直列でよい。** 映画は観た順に 1 本の直列で入れる。分岐や正史の道筋の指定は要らない
- **並べる順を選ぶ必要がある。** このアプリは、並び順をそのまま「起きた順」として記憶・事実・関係を積み上げる

  | 並べ方 | 向いている用途 |
  |---|---|
  | 上映順 | 構成の分析。どこで何を明かすかが、そのまま見える |
  | 物語内の時間順 | 登場人物との会話。「この時点の本人が知っていること」が正しくなる |

  回想が少ない作品なら両者はほぼ同じ。時系列の入れ替えが作品の核になっているものだけ、どちらかを選ぶ。
  回想(時間が戻る場面)を表す仕組みは、いまは無い
- **群像劇や並行する筋も直列でよい。** 記憶は場面に居合わせた人物ごとに積み上がるので、
  別の場所の出来事を知らない状態は、分岐を使わなくてもイベントの書き方で表せる
- **分岐は取り込んだ後に活きる。** 「ここで別の選択をしていたら」という枝を足して、その先の人物と話せる
- **時点を選んで話せる。** 「中盤のこの場面の直後の主人公」と話せば、結末を知らない状態で答える

注意点:

- 外部の LLM も、記憶だけでは場面の順序や細部を間違える。あらすじを渡して書かせる方が確実
- 実在作品の台詞や脚本をそのまま入れるのは避ける。公開されているあらすじや、自分でまとめたメモを元にし、
  要約と自分の言葉での人物像にとどめる。用途は構成の分析や習作に限る

## 8. 決まっていないこと

実装した版で決めた点: イベントは書きやすい形で受けて変換する。取り込めるのは、シーンが 1 つも無いライブラリだけ。
直列だけ(分岐は未対応)。章のまとめと書き出しは含めない。以下は、その先で決める点。

- **イベントの書かせ方**: 内部の type・payload をそのまま書かせるか、§5.2 のような書きやすい形で受けて変換するか。
  書きやすい形は LLM が間違えにくいが、変換の実装と、仕様書に 2 つの形を持つ手間が増える
- **既存の作品への追加**: 空のライブラリへの取り込みだけにするか、既存の作品に足せるようにするか。
  足す場合は、同じ名前の人物・場所をどう扱うか(上書き・別物として追加・拒否)を決める
- **分岐のある作品**: 直列以外(ゲームのシナリオなど)を取り込むなら、シーンの接続の書き方が要る
- **章のまとめ**: 章ごとの要約記憶(まとめ)も取り込むか。長い作品では、登場人物に渡る記憶の量に効く
- **書き出し**: 同じ形でアプリから書き出せるようにするか。できれば、外部の LLM に既存の作品を読ませて
  直してもらう往復に使える
- **仕様書・検査コマンドの置き場所と名前**: §6 の例では `docs/reference/import-format.md` としているが仮
- **大きさの上限**: 1 ファイルで何シーンまでを想定するか(2 時間の映画で 40〜60 場面)

## 9. 実装(2026-10-14)

| もの | 場所 |
|---|---|
| 検査と一括登録 | [backend/importer.py](../../backend/importer.py)(`validate` / `check_target` / `apply`) |
| 検査コマンド | [backend/import_check.py](../../backend/import_check.py)(`.venv/Scripts/python.exe backend/import_check.py 作品.json`) |
| API | `POST /import/validate`(書き込まない)、`POST /import/apply` |
| 画面 | 設定 → この作品 →「取り込み」(`SettingsMode.tsx` の `ImportSection`) |
| 仕様書と完成例 | `docs/reference/import-format.md`、`docs/reference/import-example.json` |

決めたこと:

- **検査は DB を見ない純粋な処理**(`validate`)。コマンドと画面が同じものを使う。メッセージは
  「scenes の 2 番目「橋のひび」: "location" の「山の上」が places にありません。places に足すか、名前を合わせてください」
  のように、場所と直し方が分かる文にする。画面には、誤りの一覧を LLM に貼り返すための「誤りをコピー」がある
- **知らない項目は誤りにする。** 綴りの誤り(`emotion_core` など)を黙って捨てない
- **イベントは書きやすい形で受ける**: `memory`(who / text / importance / emotion)、`relation`(who / toward / change か value / label / reason)、
  `fact`(who か world / key / value)、`retire`(who / reason)。登録時に内部の `memory_add` / `relationship_update` /
  `relationship_set` / `fact_set` / `char_retire` へ変換する。source は `llm`
- **取り込めるのは、シーンが 1 つも無いライブラリだけ。** 同じ名前の人物・場所・設定資料があるときも止める
- **登録は 1 つの区間でまとめて確定する**(`node_operations.atomic_store`)。途中で失敗したら全部を取り消す。
  登録の前に、API がスナップショット(「取り込みの前: 作品名」)を取る
- **登録の最後に、アプリの検査**(退場した人物の再登場など、ファイルだけでは分からない誤り)を全シーンに通す。
  通らなければ、シーンの番号と名前を付けて誤りを返し、全部を取り消す
- **シーンは、画面の「+ シーン」と同じ経路で末尾へ足す**(`append_node`)。章はシーンをすべて足してから作る
- **登録の最後に配置を自動レイアウトへ戻し、画面は読み直す。** 空のライブラリを画面に出した時点で
  「はじまり」「結末」の位置が保存され、画面もその位置を持ち続けるので、データだけを読み直すと、
  結末が先頭の近くに残ったまま章が並ぶ。画面ごと読み直すと正しく並ぶ(空のライブラリなので、失う編集中の内容は無い)
- **分岐への拡張の余地**: シーンは任意の `key` を持てる(いまは、同じタイトルのシーンを章から区別して指すために使う)。
  分岐に対応するときは、シーンに「どのシーンの後ろか」を `key` で指す項目(`after`)を足す想定。
  いま `after` を書くと、「まだ対応していません」という誤りになる
